**Текущая модель S3.16 / интерфейс S3.17:** групповая отправка и атомарное прибытие доступны через Производство → Группы → Маршруты. Создание/просмотр/расформирование — в Группах; заправка каждого участника — в Перелётах. Разделы ниже описывают последовательные этапы; прежние запреты любого transit участника и отсутствие группового UI не текущий контракт. Баланс топлива не менялся.

Первый шаг S3 — чистая фиксированная галактика с двумя сторонами и проверяемыми командами. [Реализация](../src/domain/campaign.ts) не импортирует Phaser, корабли, хранилище, часы или RNG. S3.2 подключает её к карте [MainScene](../src/scenes/MainScene.ts) через [CampaignPanel](../src/ui/CampaignPanel.ts). Это локальная песочница, ещё не законченная кампания.

S3.3 добавляет чистый [слой пошаговой партии](../src/domain/campaignSession.ts) над той же галактикой: ресурсы, доход колоний и завершение хода. **С S3.4 карта использует CampaignSession и проверяет очередность всех игровых команд.** Наблюдаемая сторона выбирается локально, но это не меняет активную сторону. S3.5–S3.8 добавляют производство и размещение; S3.9–S3.13 — одиночные перелёты, топливо и UI заправки. S3.14–S3.17 — группы, модель и интерфейс группового перелёта. Снабжение, AI, победа и сохранение кампании ещё не реализованы.

## Сценарий

Карта содержит шесть систем и двусторонние переходы. Координаты — условная раскладка стратегической карты, не расстояние полёта или тактические координаты.

| Система | Координаты | Пригодность | Начальный владелец |
| --- | --- | --- | --- |
| Сол (sol) | 0, 0 | Да | blue |
| Эдем (eden) | 1, 1 | Да | Нет |
| Разлом (rift) | 1, −1 | Нет | Нет |
| Узел (nexus) | 2, 0 | Да | Нет |
| Пыль (dust) | 2, −2 | Нет | Нет |
| Вега (vega) | 3, 0 | Да | red |

Переходы: Сол—Эдем, Сол—Разлом, Эдем—Узел, Разлом—Пыль, Пыль—Узел, Узел—Вега. Это небольшой проверочный сценарий, не сбалансированная карта и не генератор галактик. Blue начинает с разведанным Солом, red — с разведанной Вегой; остальные системы изначально неизвестны обеим сторонам.

## Контракты и владение данными

- `getGalaxyDefinition()` возвращает независимую полную карту: стороны, дома, системы, переходы. Она предназначена для доверенной модели/инструментов, не для отображения скрытой информации игроку. Мутация результата не меняет внутренний сценарий.
- `createCampaignState()` каждый раз создаёт новое независимое состояние. Запись системы содержит `id`, `ownerId` (blue/red/null) и `exploredBy`. Статические имена/координаты/пригодность не дублируются в состоянии.
- `campaignStateSchema` строго проверяет ровно шесть уникальных известных систем, допустимые стороны, уникальность разведавших сторон и инвариант колонии: система пригодна и разведана владельцем. Порядок записей не задаёт их идентичность; поиск идёт по ID.
- `CampaignCommand` — строгий discriminated union с `kind: explore | colonize`, `factionId`, `systemId`. Лишние поля, неизвестные идентификаторы, пропущенные значения и неверные типы не преобразуются автоматически.
- `executeCampaignCommand(state, command)` принимает неизвестные входы и сначала проверяет состояние, затем команду. Возвращает `{ ok: true, state }` либо `{ ok: false, code, message }`. При любом исходе входы неизменны. При успехе всё состояние независимо скопировано, а содержательно меняется только целевая система; вызывающий код принимает новый `state` только при `ok`.
- `getCampaignView(state, factionId)` выдаёт независимую проекцию стороны; неверные аргументы запроса вызывают ZodError. Это отличается от команд, возвращающих типизированный отказ.

Схема состояния — runtime-инварианты фиксированного сценария, **не версия формата сохранения кампании**. Нет ID партии, миграций, localStorage, восстановления боя, фракционного AI или авторизации. В локальной модели вызывающий код явно передаёт действующую сторону; это не сетевой протокол безопасности.

## Предусловия команд

В S3.1 команды мгновенные, без флота, стоимости, дальности, топлива, очереди или хода. Эти упрощения явные: добавление экономики/перелётов позже потребует новых контрактов, а не объявления нынешних команд готовыми миссиями кораблей.

| Команда | Предусловия | Единственное содержательное изменение |
| --- | --- | --- |
| explore | Цель ещё не разведана действующей стороной; имеет прямой переход хотя бы к одной разведанной ею системе | Добавить действующую сторону в `exploredBy` цели |
| colonize | Цель разведана действующей стороной, свободна, пригодна и имеет прямой переход к её собственной колонии | Установить `ownerId` цели |

Разведку можно продолжать через нейтральные, вражеские и непригодные системы: владение для неё не требуется. Колонизация требует соседнюю **собственную колонию**, одного разведанного пути недостаточно. Чужую или уже свою колонию повторно колонизировать нельзя; захвата нет. Стороны разведывают одну систему независимо.

Коды отказов: `INVALID_STATE`, `INVALID_COMMAND`, `ALREADY_EXPLORED`, `OUT_OF_REACH`, `NOT_EXPLORED`, `OCCUPIED`, `UNINHABITABLE`. Для колонизации видимость проверяется раньше владельца/пригодности: скрытая система не раскрывает эти сведения через причину отказа. Отказ ничего не меняет и не возвращает частично изменённое состояние.

## Видимость

Топология, имена и координаты звёзд публичны. `CampaignSystemView` — union:

- `unknown`: только id/name/x/y/visibility, **нет полей** ownerId/habitable;
- `explored`: дополнительно текущие ownerId и habitable.

Нельзя отдавать UI полный `CampaignState` или `GalaxyDefinition` вместо этой проекции для отображения скрытых данных. Разведка постоянна, сенсорной дальности и исчезновения видимости пока нет. Уже разведанная система показывает актуального владельца, даже если он изменился позже: это не сохранённый снимок «последний раз видели». Проекция не раскрывает `exploredBy` других сторон. Полная модель всё равно доступна доверенному локальному коду — это разграничение представлений, не защита от клиента в multiplayer.

### Карта: общие правила интерфейса

В меню кнопка «Галактика» запускает новую локальную партию. Выбор — кнопкой с названием системы; круг отмечает выбранную. Цвет/маркер обозначают только видимое владение/разведку. Справа — сведения выбранной системы, «Разведать»/«Колонизировать» и ответ модели. Команды намеренно доступны даже при недопустимой цели: модель возвращает причину отказа, UI не дублирует предусловия.

MainScene владеет CampaignSession и вызывает executeSessionCommand; принимает новое состояние только при ok. CampaignPanel получает лишь CampaignSessionView, выбранный ID/сообщение и callbacks. При переключении стороны выбор сохраняется, но проекция и сообщение заменяются: прежние сведения не остаются в тексте, цвете или маркере. Это локальный режим наблюдения/управления обеими сторонами, не AI; право командовать определяется очередностью модели. До S3.4 карта использовала только базовый sandbox API.

«Новая партия» и «Меню» требуют подтверждения потери текущей партии. Пока оно открыто, прочие кнопки неинтерактивны. ESC отменяет подтверждение; без него закрывает вкладку производства, а на карте запрашивает выход, не выходит сразу. Сброс возвращает blue/Сол и начальную карту. Выход уничтожает панель, снимает ESC и освобождает модель; повторный вход новый. Панель пересоздаётся только по действиям, не каждый кадр; старые callbacks после destroy бездействуют. UI рассчитан на существующий логический canvas 1280×720 с Phaser FIT.

Партия не сохраняется: закрытие/перезагрузка вкладки теряет её без beforeunload. Корабельная библиотека/localStorage не изменяются действиями кампании. Производство и интерфейс очереди описаны ниже. [План](../reports/2026-09-07/plan.md), [история S3.1](../reports/2026-09-08/12-campaign-domain.md).

## Экономика и пошаговая партия S3.3

`CampaignSession` содержит единственную `galaxy: CampaignState`, номер `turn` и `treasuries` двух сторон. Статические системы и правила разведки/колонизации не дублируются. `createCampaignSession()` создаёт независимые партии и вложенные казны. Это пока не версионированный формат сохранения.

### Начальные правила

| Величина | Правило |
| --- | --- |
| Ресурсы | Целые кредиты и минералы, каждый в пределах 0..1 000 000 000; без преобразования строк и без отрицательных остатков |
| Стартовая казна каждой стороны | 100 кредитов и 50 минералов; начальный доход дополнительно не начисляется |
| Доход одной колонии | 10 кредитов и 5 минералов при завершении хода её владельца |
| Ход | Одно окно действий стороны: 1 — blue, 2 — red, 3 — blue и т.д. Не полный раунд обеих сторон |
| Предел номера хода | 1..1 000 000 000; активная сторона вычисляется по чётности, не хранится вторым изменяемым полем |
| Разведка/колонизация | Прежние географические правила, бесплатные и без лимита действий, но только активной стороной |

Числа — предварительные параметры, не результат балансировки. Кредиты/минералы не связаны с тактической энергией, cargo-партиями и неисполняемыми служебными модулями. В S3.3 расходов не было; S3.5 добавляет оплату заказов и возврат за отмену. Содержание, рост населения и ресурсные залежи ещё не реализованы.

### Команды и атомарность

В S3.3 `SessionCommand` — строгий union explore/colonize/endTurn; S3.5 добавляет enqueueProduction/cancelProduction с payload, описанным ниже. Каждая команда содержит `factionId` и обязательный `expectedTurn`; у двух географических команд также `systemId`. `endTurn` не принимает systemId или произвольные поля. `executeSessionCommand` проверяет в порядке: схема партии → схема команды → совпадение номера хода → активная сторона → правила действия.

- Разведка/колонизация делегируются `executeCampaignCommand`; из запроса удаляется только поле слоя сессии expectedTurn. Доменные причины отказа сохраняются. Номер хода и казны не меняются; результат галактики принимается лишь при успехе.
- `endTurn` берёт колонии, принадлежащие завершающей ход стороне **в текущем состоянии**, прибавляет доход только её казне и увеличивает номер хода на один. Новая колония приносит доход уже при первом завершении своего хода; разведанная нейтральная/чужая система не приносит дохода. Ноль колоний означает нулевой доход, не поражение.
- Оба ресурса и номер хода проверяются до записи. Если хотя бы один ресурс превысит предел или номер хода нельзя увеличить, возвращается отказ целиком — без части дохода, clamp или смены стороны. До расходов на производство ресурсный лимит может остановить дальнейшие ходы; это явная техническая граница прототипа, не условие победы.
- Успех возвращает полностью независимую копию `{ ok: true, state }`; отказ — `{ ok: false, code, message }` без state. Входные объекты никогда не меняются.

Помимо кодов карты добавлены `STALE_TURN`, `NOT_ACTIVE_FACTION`, `RESOURCE_LIMIT`, `TURN_LIMIT`. Повтор старого endTurn на **обновлённом** состоянии не начисляет доход снова, даже когда та же сторона вновь активна. Вызывающий код обязан принять возвращённое состояние: повтор функции на старом снимке закономерно воспроизводит прежний результат. expectedTurn — не ID партии/запроса и не сетевой протокол дедупликации; команды той же стороны внутри текущего хода не получают отдельной revision. Клиентский state не является доверенной multiplayer-авторизацией.

### Проекция и интеграция

`getCampaignSessionView(state, factionId)` возвращает проекцию галактики, публичные номер хода/активную сторону и **только собственные** казну/расчётный доход запрошенной стороны. Запрос не начисляет доход и не меняет состояние. Противоположные казна/доход не раскрываются даже после разведки её колоний. Возвращаемые объекты независимы; неверные state/faction бросают ZodError, как запрос базовой модели.

UI хранит CampaignSession и вызывает только executeSessionCommand; прямой вызов executeCampaignCommand сценой обошёл бы проверку очередности. Базовый API остаётся внутренним географическим слоем сессии и самостоятельным контрактом тестов карты, но больше не используется сценой напрямую.

## Пошаговая экономика в интерфейсе S3.4

- Над картой показаны номер хода и активная сторона; справа — наблюдаемая сторона, только её кредиты/минералы и ожидаемый доход при завершении **её** хода. После колонизации доход обновляется сразу, баланс — лишь после успешного endTurn.
- «Завершить ход» передаёт endTurn через общий исполнитель. После успеха наблюдаемая сторона и выбор системы остаются прежними: можно увидеть начисление. Для управления следующей стороной нажмите «Сменить сторону · локально». Эта кнопка сама не меняет номер хода и не начисляет доход.
- Действия неактивной стороны намеренно не скрыты: модель отклоняет их сообщением «Сейчас ход другой стороны». Географические отказы, устаревший номер хода и переполнение также показаны без замены состояния при ошибке. UI не дублирует игровые проверки.
- При создании панели callback захватывает показанные expectedTurn/factionId/systemId, а не читает изменяемые поля сцены в момент позднего вызова. После перерисовки старый callback блокируется disposed-защитой панели; после reset/выхода он не исполняется даже при совпадении номера хода новой партии. expectedTurn дополнительно защищает от изменения номера хода вне текущей панели.
- Подтверждение новой партии/выхода блокирует также завершение хода. Reset восстанавливает turn1/blue/Сол, обе казны100/50 и доход10/5; выход снимает ESC и освобождает сессию. Перерисовка происходит по действиям, не по кадрам.

### Правила заказа

| Параметр | Принятое правило |
| --- | --- |
| Проект | Снимок schemaVersion2, `validateDesign(..., 'flight')`; гражданские без оружия допустимы. Боевой валидатор не ослабляется |
| Кредиты | `ceil(calculateShipStats(design).cost / 100)` |
| Минералы | `ceil(calculateShipStats(design).mass / 10)` |
| Срок | `max(1, ceil(credits / 50))` собственных завершений хода |
| Оплата | Полностью при постановке, до будущего дохода. Нехватка любого ресурса отклоняет весь заказ |
| Очередь | До3 заказов на колонию. Один первый заказ продвигается на один шаг за свой endTurn; остаток мощности следующему не передаётся |
| Готовность | После последнего шага заказ удаляется из очереди и один раз добавляется в completed с тем же ID/проектом/владельцем/колонией; это не runtime-корабль |
| Отмена | Только незавершённый свой заказ в указанной своей колонии; возврат каждого ресурса `floor(cost * remainingTurns / totalTurns)` |
| Вместимость | До100 pending+completed на сторону, резервируется при заказе. Готовая запись уже имеет место, поэтому завершение не блокируется переполнением списка |

Эти коэффициенты явно переводят цену/массу корабельного расчёта в стратегические единицы; не меняют формулы корабля и не моделируют реальные залежи/снабжение. Старт остаётся100/50, доход10/5; дорогие проекты требуют накопления. Баланс предварительный, боевая полезность и длительность партии не измерялись.

### Данные и команды

- `CampaignSession.production = { lastOrderId, orders, completed }` обязательно. Каждый заказ — `{ id, factionId, systemId, design, remainingTurns }`; готовая запись — те же поля без remainingTurns. Производные цена/масса/срок не сохраняются, вычисляются из независимого design. Правки каталога/верфи не меняют оплаченный заказ. Изменение формул в будущем потребует решения о версиях правил; нынешняя runtime-схема не формат save.
- ID — монотонное целое1..1e9 внутри партии без часов/RNG. После отмены не переиспользуется; исчерпание блокирует новые заказы, не отмену. Из массива orders проверяются возрастание ID, уникальность ID во всех списках, счётчик не меньше выданных, лимиты, допустимый flight-проект, remainingTurns1..срок. У ожидающих за первым заказов прогресс запрещён. Сессия дополнительно проверяет принадлежность колонии каждой записи; захват колоний пока не реализован.
- `enqueueProduction` содержит factionId/expectedTurn/systemId/design; `cancelProduction` — factionId/expectedTurn/systemId/orderId. Строгие схемы отвергают произвольные cost/refund/progress. Общие проверки expectedTurn/активной стороны идут до производства. Отказ чужой/неизвестной/нейтральной цели одинаковый `NOT_OWN_COLONY`; детали владельца не раскрываются.
- Ошибки дополнительно: `INVALID_DESIGN` (структурно корректен, но не flight), `INSUFFICIENT_RESOURCES`, `QUEUE_FULL`, `PRODUCTION_LIMIT`, `ORDER_NOT_FOUND`, `ORDER_ID_LIMIT`. Неверная структура — INVALID_COMMAND/INVALID_STATE. Quote/refund-запросы бросают ZodError на неверный вход.
- `endTurn` проверяет предел номера и оба итога дохода, затем на независимой копии начисляет доход, продвигает первые заказы своих колоний и увеличивает turn. Переполнение дохода отменяет также прогресс/готовность; переполнение возврата отменяет отмену целиком. MAX_TURN блокирует endTurn, но не все остальные действия.
- Повтор отмены уже удалённого ID отклоняется. Старый endTurn не завершает заказ снова. Два валидных enqueue одного проекта в одном ходу — **два отдельных оплаченных заказа**, не повтор одного request-id. expectedTurn не является сетевой дедупликацией; панель S3.6 блокирует повтор старых callbacks после перерисовки, как карта.
- `getCampaignSessionView` дополнительно выдаёт production с собственными orders/completed без глобального lastOrderId; чужие проекты/очереди не передаются, даже после разведки колонии. Собственные ID глобальной последовательности могут иметь пропуски; это не обещание защиты от косвенного анализа активности противника в multiplayer. Все вложенные снимки отделены.

### Интеграция и границы

Сессия продвигает заказы на endTurn. Общий command callback CampaignPanel намеренно допускает только explore/colonize/endTurn; S3.6 подключает производство отдельными callbacks с проектом/ID. Новые команды нельзя собрать из одного kind без payload. Старые сессии без production отвергаются; кампании не сохранялись, миграция/import не добавлены. При разработке после HMR старой модели начать новую партию; состояние предыдущей runtime-схемы не поддерживается.

Ограничение100 производственных записей включает completed: после заполнения новые заказы блокируются. С S3.7 размещение через доменную команду освобождает место completed; S3.8 подключает кнопку в UI. У ships собственный предел100 на сторону. Содержание, бой, AI, исследования и save остаются вне шага.

Совпадающие названия не служат идентификатором выбора: используется позиция в снимке.

## Стратегическое размещение S3.7

[campaignShips.ts](../src/domain/campaignShips.ts) определяет `CampaignShip = { id, factionId, systemId, design, transit? }` и строгую схему списка (поле transit добавлено S3.9, описано ниже). `CampaignSession.ships` обязателен, новая партия содержит пустой список. Проект проверяется общим `flightDesignSchema`, без требования оружия; это не тактический экземпляр DesignedShip и не ShipState. Нет HP, энергии, боезапаса, груза, тактического движения, группировки флота или содержания.

### Атомарная команда

`deployProduction` принимает только `factionId`, `expectedTurn`, `systemId`, `orderId`. Порядок проверки: схема state/command → совпадение хода → активная сторона → своя колония → свой completed с этим ID именно в указанной колонии → предел кораблей стороны. Нельзя задать другой проект, destination, цену или параметры runtime.

При успехе одна запись переносится из completed в ships с прежними ID/стороной/системой/проектом, без transit. Входные state/command не меняются, весь результат независимо скопирован. Казны, номер хода, галактика, pending и остальные completed не меняются. Размещение бесплатно, повторно не оплачивает постройку и не начисляет доход. Порядок размещения свободный, не FIFO: ships могут иметь невозрастающие ID. Корабль размещается в своей колонии; S3.9 разрешает последующий перелёт между собственными соседними колониями.

Отказы — прежние INVALID_STATE/INVALID_COMMAND/STALE_TURN/NOT_ACTIVE_FACTION/NOT_OWN_COLONY, плюс `COMPLETED_NOT_FOUND` и `SHIP_LIMIT`. Проверка чужой/неизвестной колонии не раскрывает содержимое её completed. Незавершённый, отменённый, отсутствующий, уже размещённый или чужой ID не размещается. Перенести проект в другую собственную колонию этой командой также нельзя.

### ID, вместимость, приватность

- ID корабля — ID его производственного заказа. Отдельный счётчик/sourceOrderId не нужен; `production.lastOrderId` остаётся общим источником выдачи. Размещение не увеличивает его и работает при MAX_ORDER_ID; MAX_TURN запрещает только endTurn, не размещение активной стороной.
- Строгая сессия проверяет уникальность ships, отсутствие пересечения с orders/completed, ID≤lastOrderId, flight-проект, известную сторону/систему и собственную колонию. Это проверка текущей согласованности, не доказательство истории оплаты: локальный state не multiplayer-авторитет.
- До100 ships на каждую сторону, максимум200 вместе, отдельно от100 pending+completed на сторону. При достижении ship cap следующий перенос отклоняется без удаления completed. Успех освобождает производственное место; последующий enqueue выдаёт следующий ID, не переиспользует ID корабля. Удаления/потерь кораблей пока нет.
- Повтор на обновлённом state не создаёт дубликат: ID больше нет в completed. При смене хода старый запрос получает STALE_TURN. На старом снимке чистая функция повторяет тот же результат; caller обязан принимать новый state. Это не network deduplication.
- `getCampaignSessionView(...).ships` содержит только собственные глубоко отделённые записи, даже если чужая колония разведана. Глобальные ID собственных кораблей могут иметь пропуски — не гарантия защиты от косвенных multiplayer-утечек.

Старые runtime-сессии без ships отвергаются; сохранения кампании/миграции не добавлены, после HMR начать новую партию. S3.8 подключает размещение и отображение ships в ProductionPanel. В MainScene отдельное сообщение нового типа команды, generic callback панели не расширен без payload.

## Интерфейс размещения S3.8

В своей колонии откройте «Производство». Внизу «ГОТОВО К РАЗМЕЩЕНИЮ» стрелками выберите запись и нажмите «Разместить». Это бесплатный перенос в ту же колонию, без смены хода. При успехе запись исчезает из готовых; текущая страница ограничивается оставшимся списком. Нет готовых — кнопка неактивна. При неактивной стороне/лимите кораблей кнопка доступна и показывает доменный отказ, ничего не расходуя и не удаляя.

«Корабли: N» переключает нижнюю часть на размещённые корабли выбранной колонии, «Готово: N» — обратно. Оба списка по одной записи (страница/ID/имя); отдельная подсказка показывает общий счётчик своих кораблей из100, включая transit. После размещения просмотр кораблей открывается на новом экземпляре. Кнопок перелёта и боя пока нет — это явно подписано; модель перелёта добавлена S3.9. Чужие ships не передаются UI, даже если их колония разведана.

Контрактные детали:

- `production-deploy` замыкает ID показанного completed. MainScene добавляет захваченные factionId/systemId/expectedTurn и вызывает deployProduction. Поздний callback не выбирает новый элемент по текущему индексу.
- Старые callbacks блокируются disposed после redraw/страницы/refresh/вкладки/стороны/reset/выхода. Новое нажатие на новую кнопку может разместить следующий готовый проект в том же ходу — это намеренное отдельное действие.
- `showShips`, `shipsPage`, `completedPage` принадлежат сцене; render ограничивает обе страницы текущими списками. Смена колонии/стороны сбрасывает страницы и возвращает режим готовых. Переключение списка не читает библиотеку и не меняет сессию.
- Pending блокирует размещение, переключение списка и страницы. ESC отменяет pending, иначе возвращает всю вкладку производства на карту. Reset/shutdown очищают новые поля вместе с прежним каталогом и дочерней панелью.
- Длинное имя готового проекта ограничено570 px до кнопки, корабля745 px; многоточие рассчитано по text.width. Полный snapshot не меняется. Счётчик лимита стоит в начале подсказки, чтобы не потеряться при обрезке.

## Ограниченный перелёт S3.9

Это предварительный транспорт **одного корабля одной командой** между двумя соседними собственными колониями. Нет группировки, движения через несколько переходов, отмены/перенаправления, топлива или содержания; тактическая скорость/батарея/груз не используются. Несколько кораблей можно отправить отдельными командами за один ход.

### Состояние и совместимость

- Без `transit` корабль стоит в `systemId`. При наличии `transit = { destinationId, remainingTurns: 1 }` он в пути: `systemId` — исходная колония, **не физическое присутствие** в ней. Не дублируются status/sourceId. Ноль оставшихся ходов не хранится: при прибытии systemId заменяется целью, transit удаляется.
- Строгая ship-схема проверяет известные ID, literal1, запрет лишних полей и прямой переход в другую систему. `areSystemsAdjacent` использует те же двусторонние lanes, что географическая модель, не отдельную копию карты. Сессия требует свои колонии на обоих концах. Потеря ownership любого конца делает такую сессию недопустимой; захват не реализован.
- ID, проект, сторона, порядок и количество кораблей при отправке/прибытии сохраняются. Transit учитывается в общем пределе100 кораблей стороны; вылет не освобождает место для размещения. ID не переиспользуется, не пересекается с pending/completed.
- Прежние стационарные записи S3.8 без transit остаются валидными, поле не заполняется автоматически. Сессии без обязательных ships/production по-прежнему отвергаются. Это расширение runtime-схемы, не новый формат save и не миграция кампании.

### Команда и прибытие

`sendShip` принимает только `kind`, `factionId`, `expectedTurn`, `systemId` (источник), `shipId`, `destinationId`. После проверки схемы/номера хода/активной стороны идут:

1. Собственная исходная колония; иначе `NOT_OWN_COLONY`.
2. Свой размещённый ID именно в указанном источнике; иначе `SHIP_NOT_FOUND`. Чужой/отсутствующий/ещё готовый проект не отправляется.
3. Отсутствие transit; повтор/перенаправление — `SHIP_IN_TRANSIT`.
4. Собственная целевая колония; чужая/нейтральная — `NOT_OWN_COLONY` без раскрытия владельца, до проверки маршрута.
5. Прямой двусторонний переход в другую систему; одинаковая/несоседняя собственная цель — `INVALID_ROUTE`.

Успех добавляет только независимый transit. Отправка бесплатна, не меняет ход/казны/производство/галактику/счётчик ID. Новая колония и только что размещённый корабль могут сразу участвовать. MAX_ORDER_ID и MAX_TURN не блокируют отправку; на MAX_TURN завершение хода невозможно — явное техническое ограничение.

**Первый успешный собственный endTurn завершает все собственные перелёты**, в том числе отправленные в текущем окне действий. Чужой endTurn их не продвигает. Доход, FIFO-производство, прибытия и turn+1 применяются одной операцией: RESOURCE_LIMIT/TURN_LIMIT отменяет всё, а не только доход. `advanceShipTravel` копирует и проверяет список; endpoint ownership и очередность проверяет session API, helper не заменяет командную границу.

### Проекция и UI

### Атомарность и команды

`sendShip` сохраняет прежний payload. После ownership/ID/transit/назначения/adjacency проверяется fuel≥1, иначе `INSUFFICIENT_FUEL`. Успех одновременно уменьшает fuel на1 и создаёт transit, казны неизменны. Неверная цель не расходует топливо. Отказ более позднего endTurn не откатывает уже успешный send: корабль остаётся в пути с оплаченным топливом. Ресурсы казны не заменяют пустой бак автоматически.

`refuelShip` принимает только `kind`, `factionId`, `expectedTurn`, `systemId`, `shipId`. Порядок: strict state/command → STALE_TURN → NOT_ACTIVE_FACTION → NOT_OWN_COLONY → SHIP_NOT_FOUND → SHIP_IN_TRANSIT → FUEL_FULL → INSUFFICIENT_RESOURCES. Полный бак — отказ без оплаты даже при нулевой казне. Недостаток любого ресурса отменяет всю операцию; частичного наполнения нет. Успех списывает оба ресурса и устанавливает fuel3 на независимом state. Чужие/готовые/отсутствующие ID не заправляются; refuel не перемещает корабль.

`getRefuelQuote(fuel)` проверяет число и возвращает независимые `{amount, cost:{credits,minerals}}`; неверный query бросает ZodError. Доступность/ownership/turn проверяет сессия, не quote. Клиент не передаёт amount/cost/fuel/capacity/design; лишние поля запрещены. Лимиты100 ships/MAX_ORDER_ID/MAX_TURN не запрещают заправку, но терминальный turn блокирует последующее прибытие. Повтор refuel после успеха получает FUEL_FULL; replay старого snapshot детерминирован, не network deduplication. `expectedTurn` не revision каждой команды внутри хода.

### Совместимость, проекция, интерфейс

Текущий `CampaignShip = {id, factionId, systemId, design, fuel, transit?}`. Производственные записи не содержат fuel. SessionView выдаёт запас только своих кораблей, вместе с независимыми проектами/transit; чужой запас скрыт даже после разведки. Локальная модель не multiplayer-авторитет и не доказывает историческую оплату.

**Старые runtime-записи кораблей без fuel отклоняются как INVALID_STATE**, не получают полный бак автоматически. Пустые новые партии остаются валидны. После HMR старой схемы начать новую партию; сохранений/миграции кампании нет. Библиотека ShipDesign v2, корабельные формулы/тактические состояния и формат completed не менялись.

В UI исправлены подписи расхода и границы «заправка пока только через API», добавлено корректное сообщение refuel. Запас/цена/кнопка заправки намеренно ещё отсутствуют; send пустого корабля показывает доменный отказ. В текущем пользовательском UI после трёх переходов нельзя заправиться — это следующий S3.13, не завершённый топливный интерфейс.

## Стационарные группы S3.14

[campaignFleets.ts](../src/domain/campaignFleets.ts) определяет чистую группу `CampaignFleet = {id, factionId, systemId, shipIds}`. Это список ссылок на стратегические корабли, не тактический флот и не копия ShipDesign/топлива/боевого состояния. Членство хранится только здесь: поля fleetId на ship нет.

| Правило | Ограничение |
| --- | --- |
| Состав | 2–10 уникальных собственных размещённых кораблей, стоящих в одной своей колонии |
| Членство | Каждый ship максимум в одной группе; transit не допускается |
| Количество | До20 групп на сторону,40 вместе; участники по-прежнему входят в лимит100 ships |
| Идентификаторы | Отдельная глобальная последовательность групп1..1e9, не production/ship ID; после расформирования не переиспользуются |
| Цена/время | Создание и расформирование бесплатны, не меняют ход, топливо, казны и производство |

`CampaignSession.fleets = {lastFleetId, items}` обязательно, новая партия содержит0 и пустой массив. Items строго возрастают по ID, выданные ID не больше счётчика; порядок shipIds сохраняет входной порядок. Сессия дополнительно проверяет существование каждого участника в ships, совпадение владельца/колонии и отсутствие transit. Чужой, готовый, несуществующий или стоящий в другой колонии корабль не может быть участником. Все схемы строгие, лишние поля отклоняются.

### Команды и совместимость

- `createFleet`: только kind/factionId/expectedTurn/systemId/shipIds. Общий порядок state→command→STALE_TURN→NOT_ACTIVE_FACTION→NOT_OWN_COLONY; затем каждый участник по входному порядку: SHIP_NOT_FOUND→SHIP_IN_TRANSIT→SHIP_IN_FLEET. После всех участников FLEET_LIMIT→FLEET_ID_LIMIT. Только после проверок выделяется ID и добавляется целая группа; частичной регистрации нет.
- `disbandFleet`: только kind/factionId/expectedTurn/systemId/fleetId. После общих проверок свой ID должен находиться именно в указанной колонии, иначе FLEET_NOT_FOUND. Удаляется только группа; все корабли остаются, lastFleetId сохраняется. Повтор получает отказ. MAX_TURN/MAX_ORDER_ID не мешают этим двум командам; исчерпание группового счётчика блокирует только создание.
- `sendShip` участника после own/source/transit проверок, но до проверки цели/маршрута/топлива, возвращает SHIP_IN_FLEET: сначала расформировать группу. Автоматического исключения участника или переноса группы нет.
- `refuelShip` участника работает по прежней цене и правилам, membership не меняет. Общего бака и групповой заправки нет. EndTurn не перемещает и не расформировывает группы; свободные корабли летают как раньше.

Успех — полностью независимый state, отказ — без state/мутаций входов. SessionView.fleets содержит только собственные независимые группы/массивы shipIds, без lastFleetId. Пропуски ID не гарантируют multiplayer-секретность; локальная схема не доказывает историческую оплату. `isShipInFleet` — селектор уже проверенного state/view, не самостоятельная командная граница.

### Контракты и жизненный цикл

- [FleetPanel](../src/ui/FleetPanel.ts) получает только SessionView/выбранную колонию/UI-state/callbacks, не полную сессию/каталог/хранилище. [ProductionPanel](../src/ui/ProductionPanel.ts) создаёт и уничтожает дочернюю панель.
- Сцена хранит черновик ID и три страницы: кандидатов/групп/участников. Render удаляет из черновика недопустимые ID и ограничивает страницы текущими списками. Групповое членство не дублируется в UI-state.
- Create захватывает независимый массив показанных ID, disband — показанный ID группы; MainScene добавляет показанные factionId/systemId/expectedTurn. При изменении state до клика модель отклоняет старый payload, а не выбирает другие корабли. После перерисовки старые callbacks инертны через disposed. Принимается только ok; отказ сохраняет ещё допустимый выбор.
- Успешное создание очищает draft и выбирает новую группу; расформирование сбрасывает страницу участника/ограничивает группу; успешный endTurn очищает выбор. Смена стороны/колонии/карты/перелётов, закрытие групп, reset/shutdown очищают draft/страницы. Каталог при этом не перечитывается.
- Pending блокирует все групповые controls и вкладки; отмена сохраняет выбор. ESC: отмена pending → группы в очередь → очередь на карту → запрос меню. Reset/exit освобождают панели/обработчики/состояние, повторный вход чистый.
- Текст имени сокращается только для показа по реальной text.width (кандидат745px, участник590px); snapshot проекта неизменен. Заголовок производства ограничен290px, не перекрывает кнопку групп.

## Групповой перелёт S3.16

`sendFleet` отправляет всю группу в соседнюю собственную колонию. Каждый участник платит TRAVEL_FUEL_COST=1 из своего бака; если хотя бы одному не хватает, **вся отправка отклоняется без списания и частичного вылета**. Казна/номер хода/ID/проект/состав не меняются. Нет общего бака, дополнительной платы, зависимости от корпуса/массы/тактической скорости.

### Единственный маршрут и согласованность

Маршрут хранится только в уже существующем `CampaignShip.transit = {destinationId, remainingTurns:1}`. У группы новых persisted полей нет; group.systemId и member.systemId в пути означают исходную колонию, не присутствие в ней. Сессия строго требует:

- Участники существуют, имеют одного владельца и systemId группы, членство уникально как прежде.
- Либо все стоят, либо все имеют transit с одной целью/remainingTurns. Частичный вылет/прибытие и разные даже индивидуально допустимые маршруты — INVALID_STATE.
- Оба конца маршрута свои, переход прямой по общим lanes. Потеря ownership/участника делает state недопустимым; захват/потери ещё не реализованы.

`getFleetTransit(fleet, ships)` возвращает независимую копию маршрута первого участника, `isFleetAtColony` исключает путешествующую группу из обеих колоний. Это селекторы **проверенной сессии/её проекции**, не самостоятельный обход unknown-валидации. Не добавлять второй маршрут в группу: согласованность проверяется в session boundary.

### Команда, отказы и прибытие

Payload: только kind/factionId/expectedTurn/systemId/fleetId/destinationId. Порядок проверки: state → command → STALE_TURN → NOT_ACTIVE_FACTION → своя исходная колония → свой ID именно там (FLEET_NOT_FOUND) → отсутствие перелёта (FLEET_IN_TRANSIT) → своя цель → прямой переход → топливо всех участников (INSUFFICIENT_FUEL). Клиент не задаёт список участников, топливо, стоимость или длительность.

Успех создаёт отдельный transit каждого участника и уменьшает каждый fuel на1 на глубоко отделённом state. Остаток0 валиден, целиком пустая казна не мешает. Повтор send/перенаправление и disband в пути получают FLEET_IN_TRANSIT до изменения маршрута/членства. Single send/refuel/create с участником в пути получают прежний SHIP_IN_TRANSIT. Стоящего участника можно заправить, single send требует предварительного disband.

На первый успешный **собственный endTurn** все участники и группа прибывают вместе: group.systemId/ship.systemId меняются на цель, member.transit удаляются. Membership/порядок/ID/проект сохранны, нового расхода/возврата/автозаправки нет. Доход, FIFO, свободные корабли и группы продвигаются одной атомарной командой. Чужой ход не двигает группу. RESOURCE_LIMIT/TURN_LIMIT не допускают частичных прибытий и не возвращают топливо, ранее потраченное успешной отправкой.

В пути группа и участники продолжают занимать места в лимитах20 групп/100 ships стороны. Исчерпание MAX_ORDER_ID/MAX_FLEET_ID не мешает отправке; MAX_TURN допускает вылет, но блокирует последующее завершение хода — прежняя техническая граница прототипа. После прибытия отправка обратно/расформирование требуют новую исходную колонию и очередь владельца.
