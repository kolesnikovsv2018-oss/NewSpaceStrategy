# Проект корабля и тактическое состояние — S2

S2 закрыт 2026-09-08 для канонического цикла «собрать → сохранить → загрузить → испытать → скорректировать». [Приёмочная сверка](../reports/2026-09-08/11-s2-acceptance.md) содержит доказательства и уточнение исходного объёма: legacy-совместимость сохраняется, топливо и исполнение служб не объявляются реализованными. S3 начат отдельной [моделью и картой галактики](CAMPAIGN.md), пока без интеграции кораблей.

## Граница модели

[shipDesign.ts](../src/domain/shipDesign.ts) не зависит от Phaser: ComponentDefinition → ShipDesign → вычисляемые ShipStats → отдельный [ShipState](../src/domain/shipState.ts) → readonly [ShipView](../src/entities/interfaces/ShipView.ts). [DesignedShip](../src/entities/DesignedShip.ts) создаёт независимый экземпляр. CombatShipFactory и все четыре пресета ShipFactory, включая добытчик, используют этот путь. createCustomShip использует legacy ShipComponents через явную границу совместимости; её удаление и автоматическая конвертация старого API не входят в принятую реализацию S2.

ShipState содержит позицию/скорость, движение/уничтожение, текущую энергию/корпус/щит, задержку восстановления, состояния орудий и партии груза. Старые публичные поля обращаются к нему через accessors без отдельной синхронизации. getState() отдаёт независимую копию вложенных объектов, включая партии. AI-цель и параметры компонентов остаются вне этого объекта; это не полный формат сохранения боя. В проекте runtime-поля не сохраняются. У legacy-корабля одна запись оружия legacy-aggregate, у проектного — реальные слоты. Сводный weaponStats.currentCooldown показывает наибольшую оставшуюся задержку, запись меняет её у всех орудий; для отдельных значений используется getWeaponState().

Компоненты: лучевое и снарядное оружие, двигатель с генерацией энергии, щит, броня, mining, repair, scanner и cargoExpansion. Поле kind определяет строгую схему Zod. Сохранение содержит входные параметры, корпус, слоты и ISO-строки дат; массу/цену/мощность вычисляют заново. Каталог является набором чертежей: каждый слот получает независимую копию.

## Единицы и правила

- Масса — тонны, цена — условные кредиты, расстояния/координаты/радиусы — тактические единицы (такт. ед.), скорость — такт. ед/с. Это не километры и не световые годы. update, задержка щита и cooldown используют секунды симуляции; только вход Phaser и duration менеджера боя — миллисекунды.
- Батарея и энергия выстрела — условные единицы энергии (ЭЕ); генерация и мощность — ЭЕ/с. Полная нагрузка оружия равна энергии выстрела × выстрелам в секунду. Генерация двигателя учитывается один раз. ЭЕ не объявлены физическими джоулями; численные формулы компонентов и формат сохранения v2 не меняются.
- Масса снарядного оружия включает исходный боезапас; при стрельбе уменьшается боезапас, не расчётная масса.
- Щит поглощает лучевой урон с сопротивлением; снаряды проходят к броне/корпусу. Регенерация после задержки расходует 3 энергии за пункт щита. Броня снижает урон согласно типу и коэффициенту 100/(100+armor).
- У каждого орудия собственная перезарядка, дальность, энергия выстрела и боезапас. Промах тоже расходует ресурсы. DPS в редакторе не учитывает криты и защиту цели.
- Все корпуса имеют восемь позиций: шесть прежних фиксированных типов и два универсальных служебных. Отличаются массой, допустимой массой/размером модулей, прочностью, батареей, ценой и масштабом. Это предварительная схема, не окончательный баланс ролей.
- Груз имеет независимые массу в тоннах, объём в м³ и количество единиц ресурса. Стратегическое топливо/снабжение не реализованы; нельзя трактовать тактическую батарею как запас межзвёздного топлива.

### Тактическая оценка полёта

[estimateFlight](../src/domain/flightEstimate.ts) — чистая непрерывная оценка **только движения**. ShipRuntime.getFlightEstimate передаёт текущую энергию E, генерацию G, мощность движения P и максимальную скорость v с текущим грузом. При P > G получаем t = E / (P − G) секунд и d = t × v тактических единиц. Например, 60 ЭЕ, генерация 2 ЭЕ/с, движение 5 ЭЕ/с и скорость 156.25 дают 20 с / 3125 такт. ед.

Результат — union, не число Infinity:

- limited: конечные seconds и distance; при пустой батарее без достаточной генерации оба равны нулю.
- sustained: G ≥ P, «Генерация покрывает движение», в том числе бесплатное движение.
- stationary: скорость равна нулю.
- unavailable: неверные числа/характеристики или переполнение вычисляемой оценки.

Модель не учитывает стрельбу, восстановление щита, служебные действия, конечную ёмкость между дискретными фазами update и размер timestep. Поэтому это не обещание фактического времени до остановки (особенно при малой батарее/большом шаге) и не стратегическая дальность. Старый getMaxRange сохранён как deprecated с историческими формулами, без генерации/груза и с возможным Infinity при нулевом расходе; UI вместо него использует новый запрос. Состояние запросом не изменяется.

### Проверяемые численные операции

[runtimeNumbers](../src/domain/runtimeNumbers.ts) задаёт общие проверки без преобразования строк/null в числа:

| Операция | Контракт отказа |
| --- | --- |
| consumeEnergy(amount) | amount конечен и ≥0; неверное значение/недостаток энергии → false без списания, нулевой расход допустим |
| update/rechargeEnergy(delta) | Неверный, бесконечный, отрицательный или нулевой шаг → без изменения состояния; большой конечный recharge насыщает батарею до ёмкости |
| startMoving(x, y) | Координаты конечные, в том числе отрицательные; неверный ввод/переполнение → false без смены движения. Math.hypot избегает переполнения квадратов |
| takeDamage(amount) | Неверный/нулевой amount или уже уничтоженный корабль → нулевой результат без hit/evaded/critical и без сброса задержки щита; большой конечный урон ограничен остатком защиты |
| setEnergy/currentEnergy/замена powerSource | Конечная энергия 0..capacity; иначе RangeError до записи. Legacy-конфигурация остаётся изменяемой, проектная — неизменяемой |
| Замена position/velocity | Проверка конечности обоих полей до записи, иначе RangeError |
| HP/щит/cooldown setters и замена соответствующих views | Конечные текущие значения ≥0, иначе RangeError до записи; новые верхние ограничения HP/щита не вводились |

Неверная позиция цели не запускает атаку и не тратит ресурсы. moveToTarget проверяет неотрицательный конечный optimalRange; undefined означает прежний default 0.8. Переполнение координат/расхода одного движения отклоняется до списания и изменения позиции; остальные стадии валидного update не откатываются. Полной проверки произвольных mutable legacy-компонентов, боевых summary-параметров, прямой записи position.x/velocity.x и полного входного ShipState нет. Снимок по-прежнему не является форматом восстановления боя.

## Груз и ограничения корпуса

[cargo.ts](../src/domain/cargo.ts) — чистые атомарные загрузка/выгрузка. Партия содержит resourceType, amount и **суммарные**, не удельные mass/volume. Значения положительные конечные, не более 10⁹ каждое; имя ресурса после обрезки пробелов — 1..80 символов. Максимум 1000 партий. Функции принимают уже валидный текущий список; новый груз проверяется схемой. При отказе список не меняется. Выгрузка проходит FIFO по всем партиям ресурса, сохраняя плотность каждой; недостаток суммарного количества отклоняет операцию целиком.

Интегральный трюм входит в исходную массу/цену корпуса, не является новым модулем или седьмым слотом. Параметры задаются таблицей HULL_CARGO:

| Корпус | Предел полезного груза, т | Объём, м³ |
| --- | --- | --- |
| fighter | 0 | 0 |
| corvette | 100 | 100 |
| frigate | 200 | 250 |
| destroyer | 350 | 400 |
| cruiser | 500 | 600 |
| battleship | 800 | 900 |

Фактический предел массы = max(0, min(предел трюма, maxMass корпуса − масса корпуса с модулями)). Эти предварительные игровые параметры добавляют возможность грузоперевозки старым проектам, но не меняют их массу/стоимость без груза. Интегральный трюм не занимает слот. Установленные cargoExpansion суммируют дополнительный объём, не увеличивая допустимую массу; собственная масса расширителей может уменьшить полезную нагрузку.

ShipStats описывает пустой корабль. DesignedShip.getTotalWeight добавляет текущий груз, а скорость пересчитывается той же формулой с полной массой. Успешная загрузка/выгрузка сразу меняет длину вектора скорости, сохраняя направление; топливо, стоимость груза и уменьшение манёвренности не моделируются. В legacy максимальная масса отсека по-прежнему совместно ограничивает оборудование и груз, но оборудование не занимает грузовой объём.

Ship.loadCargo/unloadCargo сохраняют boolean API; getCargoMessage сообщает результат. Старый ICargoItem.weight преобразуется в CargoItem.mass. ship.cargo теперь возвращает копию, usedSpace/currentWeight — вычисляемые readonly-показатели, а не команды изменения состояния. Переданные конструктору старые счётчики без партий не восстанавливают груз: API восстановления состояния отсутствует.

## Проверка проекта

### Служебные определения v2

service_1/service_2 принимают mining/repair/scanner/cargoExpansion; тип/размер проверяются тем же validateDesign. Оружие нельзя поставить в служебный слот, а служебный модуль — в engine/armor/weapon. Номиналы конечны 0..100000, efficiency/accuracy — доли 0..1, не проценты.

| Вид | Входные параметры | Производная масса / цена / мощность | Действие сейчас |
| --- | --- | --- | --- |
| mining | miningSpeed (s), efficiency (e) | 20 + 4s т; 1000 + 200s + 1250e ₡; 5s ЭЕ/с | Только номинал, добыча не исполняется |
| repair | repairRate (r) | 10 + 3r т; 500 + 400r ₡; 10r ЭЕ/с | Только номинал, ремонт не исполняется |
| scanner | range (d), accuracy (a) | 5 + 0.025d т; 250 + 2d + 1000a ₡; 0.05d ЭЕ/с | Только номинал, обнаружение не исполняется |
| cargoExpansion | bonusCapacity (v) | 5 + 0.3v т; 250 + 15v ₡; 0 ЭЕ/с | Пассивно добавляет v м³ |

Цена округляется как у прочих компонентов. Параметры предварительные, не измеренный баланс. Номинальная мощность первых трёх резервируется в peakPower для проверки проекта, но не списывается в update до реализации команд/систем. Модули не дают фиктивных орудий, щита, груза или лечения. Каталог и полёт показывают componentStatus; верфь также предупреждает о неисполняемых действиях. Каталог теперь имеет два ряда категорий, слоты — четыре ряда. Панель информации подгоняет длинные описания по высоте экрана без декоративных legacy-иконок поверх текста.

Единый validateDesign проверяет схему, точный набор слотов, совместимость типа/размера и массу. Режим draft разрешает неполную компоновку; flight требует двигатель, достаточную генерацию и батарею; battle дополнительно требует оружие. Загрузка не обязана давать боеготовый проект: сохранённый черновик можно доработать. Недопустимая установка не меняет исходный проект.

## Хранение и совместимость

[ShipDesignManager](../src/utils/ShipDesignManager.ts) использует документ orion_shipyard_v2 со schemaVersion: 2 у библиотеки и проектов. Максимум 100 проектов, 200 компонентов; импорт до 5 МБ. Данные проверяются до записи. Ошибки JSON, неизвестная версия, конфликт ID, блокировка хранилища и квота не подменяются успешным сохранением. Импорт объединяет библиотеку, но не перезаписывает отличающиеся записи с одинаковым ID. Экспортирует сохранённое, не несохранённый черновик.

При отсутствии v2 читается orion_shipyard_v1. Строгие v1DesignSchema/v1ComponentSchema принимают только прежние шесть слотов и пять типов, затем migrateV1Design добавляет два пустых служебных места. ID/даты/параметры/масса пустого проекта сохраняются. Загрузка не пишет; первая успешная запись создаёт только v2, исходный v1 остаётся дословно. При наличии повреждённого v2 отката к v1 нет. Импорт v1 также мигрируется; повторный импорт идентичных данных идемпотентен, после редактирования создаёт конфликт. Старый клиент v1 не может читать новые v2-модули; изменения старого ключа после появления v2 автоматически не сливаются.

При отсутствии обоих версионированных ключей читаются старые orion_ship_configs/orion_components. Поддерживаемые модули и слоты переносятся, даты остаются ISO-строками, оригинальные ключи сохраняются. Пустые неподдерживаемые слоты пропускаются; занятые отклоняются с ошибкой. Броня с прочностью/саморемонтом требует ручного переноса. Корпус и производные характеристики пересчитываются по новым правилам — старый баланс и произвольные параметры корпуса не сохраняются. Старые effect/проценты не преобразуются в служебные определения по догадке. Это ограниченная миграция, не универсальная обратная совместимость.

## Испытание

### Фабричные боевые проекты

[combatPresets](../src/domain/combatPresets.ts) содержит только входные параметры четырёх проектов. Их создаёт [CombatShipFactory](../src/entities/CombatShipFactory.ts), а кнопка «Готовые проекты» в верфи загружает тот же шаблон как новый независимый черновик. Его можно переоборудовать модулями каталога, сохранить, экспортировать и испытать без преобразования формата.

| Пресет | Корпус | Комплектация |
| --- | --- | --- |
| Истребитель | fighter | Двигатель, лазер |
| Фрегат | frigate | Двигатель, лазер, щит, броня |
| Крейсер | cruiser | Двигатель, два лазера, щит, броня |
| Дредноут | battleship | Двигатель, два лазера, пушка с 20 снарядами, щит, броня |

Все проекты проходят общий валидатор. Старые численные характеристики S1 не сохраняются: новый корпус, энергия, отдельные орудия и защита рассчитываются по правилам верфи. Неисполняемый прежде ремонтный модуль не объявляется способностью нового дредноута. Исторические боевые комплектации находятся только в тестовой фикстуре; production их не использует. Пределы интегрального трюма общие для фабричных и пользовательских проектов.

createFleet проверяет целочисленные количества и суммарный предел 128 кораблей до создания экземпляров; случайные флоты имеют тот же предел. Это защитный лимит API, не измеренная производительность. У обычного боя остаются два флота по восемь кораблей.

### Гражданские проекты

[civilianPresets](../src/domain/civilianPresets.ts) добавляет в «Готовые проекты» разведчик (corvette), грузовоз (cruiser) и добытчик (frigate). Все имеют двигатель, проходят flight и не проходят battle без оружия; фиктивных орудий/щита нет. ShipFactory использует те же проекты, а createWarship — боевой крейсер. Добытчик содержит mining в service_1 с именем Mk1 и номиналами 10 ед/с, эффективность 0.8. Масса модуля 60 т и цена 4000 совпадают с прежним Mk1, но баланс корабля теперь определяется каноническим корпусом/двигателем. Добыча не исполняется, модуль не подменён грузовым отсеком. createCustomShip сохраняет старый API и параметры, оставаясь legacy.

### Полёт и бой

Верфь передаёт снимок текущего проекта в полёт или бой. Полёт создаёт один корабль; бой — проект против стартового корвета. Бой ограничен 120 секундами симуляции; остановка без победителя допустима. Возврат восстанавливает первоначальный черновик, не повреждённый экземпляр. Превью и runtime используют общий drawBlueprint.

В полёте проекта кнопки загружают тестовую партию руды (10 единиц, 20 т, 10 м³) и выгружают 10 единиц. Отказ виден в сообщении; панель показывает массу/объём/скорость. Это диагностическое испытание, не экономика с внешним складом: тестовая руда создаётся кнопкой. Возврат и новое испытание не переносят груз в проект.

Параметры запуска потребляются один раз: init очищает Phaser settings.data после чтения. Поэтому последующий вход из меню без проекта создаёт обычные демонстрационные корабли, а не повторяет прошлое испытание.

AI пока держит дистанцию по максимальной дальности; короткобойное оружие смешанной комплектации может не участвовать. Math.random и переменный timestep не дают воспроизводимости результатов. Удаление записей библиотеки и разрешение конфликтов вкладок не реализованы. Старые демонстрации остаются доступны из меню.

### Защита несохранённого проекта

[shipDraft](../src/domain/shipDraft.ts) сравнивает нормализованное содержание проекта с независимым сохранённым снимком. Игнорируются updatedAt и порядок слотов; ID, createdAt, имя, корпус, установленное оборудование и его параметры значимы. Новый проект без сохранённого снимка всегда «Не сохранён», даже без правок. Откат содержания к сохранённому состоянию снимает этот признак. Каталог сравнивается и сохраняется отдельно, не очищает статус проекта.

[ShipBuilderPanel](../src/ui/ShipBuilderPanel.ts) показывает индикатор и хранит baseline после чтения/успешной записи. Ошибка записи, включая квоту, оставляет черновик и baseline прежними. «Новый», «Стартовый», «Копия», выбранный готовый проект или запись загрузки заменяют dirty-проект только после подтверждения. До выбора в списке подтверждение не требуется, закрытие списка ничего не меняет. Фабрики новых проектов вызываются только после согласия. Кнопки «Отмена · ESC» и «Продолжить без сохранения» не выполняют скрытое сохранение и не удаляют библиотечные записи.

[ShipyardModal](../src/ui/ShipyardModal.ts) обеспечивает один Phaser-overlay на сцену: затемнённая interactive-подложка блокирует фон, ESC отменяет окно, SHUTDOWN/destroy удаляют обработчики. Списки выбора используют тот же механизм. Подтверждение одноразовое; сохранённый callback после отмены/shutdown не выполняет действие. Сценовый ESC при открытом окне не выходит в меню. Выход через «Меню»/ESC без окна также требует согласия для dirty-проекта.

Испытания не уничтожают проект и не требуют подтверждения, но не запускаются поверх открытого окна. После возврата ShipyardScene сравнивает входящий черновик с записью библиотеки с тем же ID, а не объявляет его сохранённым. Сохранённый проект остаётся clean, изменённый/новый — dirty. При недоступной библиотеке baseline отсутствует: защита консервативно включена.

Это защита действий внутри верфи, не beforeunload, autosave или восстановление после перезагрузки/сбоя. Синхронизация с другими вкладками и защита несохранённого каталога при ошибке его записи отдельно.

## Граница старой фабрики

Для канонического полёта используется ShipFactory.createFromDesign(design, factionId = neutral): принимает только валидный flight-проект, не подбирает корпус или двигатель автоматически. Сюда направлены полёт из верфи и гражданские пресеты. Боевой CombatShipFactory.createFromDesign по-прежнему дополнительно требует оружие.

[LegacyShipFactory](../src/legacy/LegacyShipFactory.ts) создаёт старый Ship из имени и трёх enum-селекторов. ShipFactory.createCustomShip оставлен как deprecated-обёртка; [прежний импорт компонентной фабрики](../src/entities/ShipComponentFactory.ts) реэкспортирует тот же [LegacyShipComponentFactory](../src/legacy/LegacyShipComponentFactory.ts), включая единый счётчик ID. Все 36 сочетаний сохраняют массу/стоимость/мощность/скорость/трюм; это изоляция совместимости, а не автоматическая конвертация в ShipDesign.

[legacyShipConfig](../src/legacy/legacyShipConfig.ts) проверяет селекторы до выделения компонентов. Имя — 1..80 символов, не полностью пробельное, допустимые пробелы не обрезаются. Уровень оборудования — положительное безопасное целое, по умолчанию 1; выше Mk3 формулы продолжают работать без clamp, старые проценты не превращаются в канонические доли. Неверные типы, NaN/Infinity/дробные/отрицательные уровни отклоняются. Это не проверка всех будущих ручных мутаций IEquipment или Ship.

Legacy getDesign() возвращает undefined. Конфиг селекторов — не формат сохранения, ShipDesignManager не принимает legacy Ship. Автоматическое сопоставление старых компонентов корпусу изменило бы параметры и не реализовано.

## Runtime-контракты

[DesignedShip](../src/entities/DesignedShip.ts) наследует [TacticalShip](../src/entities/TacticalShip.ts) → [ShipRuntime](../src/entities/ShipRuntime.ts), без legacy Ship/CombatShip. Старый CombatShip использует withTactics(Ship) и сохраняет instanceof Ship. Mixin тактики содержит одну реализацию live-accessors HP/щита/cooldown, выбора ближайшей цели, движения на дистанцию и сводки боя. Он не инициализирует оружие и не задаёт формул урона, регенерации или update. Типизированный generic mixin сохраняет разные конструкторы; any ограничен необходимой для TypeScript сигнатурой конструктора, не данными компонентов.

[ICombatant](../src/entities/interfaces/CombatSystem.ts) описывает цели, атаку, урон и обновление. IFaction и BattleManager принимают этот структурный контракт: можно смешивать модели или предоставить реализацию без наследования от Ship. Текущий ShipState не раскрывается контрактом, обновляет модель только владелец симуляции.

[ShipView](../src/entities/interfaces/ShipView.ts) ограничивает ShipSprite/ShipInfoPanel readonly-полями и запросами, без update/installEquipment или mutable equipment. Имена установок доступны через getInstalledModuleNames. Readonly — гарантия типизации потребителя, не Object.freeze и не снимок: представление видит актуальные значения модели.

ShipRuntime — единственный владелец изменяемого состояния, копирующий входной ShipState и выдающий независимые getState/getCargo. Общие операции движения/энергии/груза используют state и getEnergyCapacity/getEnergyGeneration/getMovementPower/getCargoLimits, не старые компоненты. Проект получает createDesignState(stats) в конструкторе; синтетические powerSource/engine/cargoHold не передаются в super. Legacy Ship получает те же старые компоненты и сохраняет refit/числа.

[FlightShip](../src/entities/interfaces/FlightShip.ts) задаёт команды сцены без конкретной модели. loadCargoLot принимает строгую каноническую партию с mass; старый loadCargo(weight) и cargo с weight оставлены через явную [границу совместимости](../src/legacy/cargoCompatibility.ts). Смешивать или угадывать оба формата в одном запросе нельзя. Груз по-прежнему атомарен, скорость пересчитывается после успешной операции.

[DesignCompatibilityViews](../src/legacy/DesignCompatibilityViews.ts) предоставляет стабильные выходные powerSource/engine/cargoHold из проекта/stats/state. Конфигурация заморожена через Object.freeze; currentEnergy остаётся live-accessor с записью. Замена powerSource с прежними полями и новой текущей энергией поддержана, изменение генерации/ёмкости/другой конфигурации отклоняется: менять проект следует через ShipDesign. Старый mutable Ship не ограничен этим правилом. Aggregate combatStats/weaponStats пока остаются mutable, полного hardening всех публичных полей не заявляется.

Порядок оплаты движения сохранён явно: DesignedShip платит до изменения позиции, legacy Ship после. Обе модели сначала восстанавливают энергию. Численные команды защищены в указанных выше границах; формат v2, боевые формулы, сохранения и service-действия не менялись. ShipInfoPanel показывает новую тактическую оценку; текст и фон обеих веток вписываются по высоте/ширине, legacy-иконки располагаются ниже текста.
