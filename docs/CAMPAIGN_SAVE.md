## 1. Проверенные исходные факты

[CampaignSession](../src/domain/campaignSession.ts) содержит обязательные `galaxy`, `turn`, `treasuries`, `production`, `ships`, `fleets`. Все игровые команды карты работают с этой сессией; текущая [MainScene](../src/scenes/MainScene.ts) создаёт новую при входе и освобождает при выходе. Автоматического продолжения/чтения диска нет.

[ShipDesignManager](../src/utils/ShipDesignManager.ts) сохраняет **библиотеку**, не партию. Ключи библиотеки v2/v1 и старого редактора, её импортеры и миграции не подходят для кампании. Совпадение `schemaVersion` не означает совпадение формата.

Существующие схемы строгие, включая вложенные объекты: неизвестные поля не должны молча отбрасываться. Исключение преобразования, которое уже есть: `name` проекта/компонента проходит `.trim()`. Схема не доказывает достижимость партии историей команд: например, не закрепляет вечное владение домашними системами. Это проверка структурной согласованности, не античит.

## 2. Выбранный документ v1

Корень — строгий объект с **ровно четырьмя обязательными полями**:

| Поле | Контракт v1 |
| --- | --- |
| `format` | Строковый литерал `orion-campaign`; отделяет кампанию от произвольного JSON/библиотеки |
| `schemaVersion` | Числовой литерал `1`; структура документа/состояния |
| `rulesVersion` | Числовой литерал `1`; фиксирует игровые правила S3.22 |
| `session` | Полное состояние, принятое текущей `campaignSessionSchema`, а не проекция стороны |

Экспортированы четыре константы: `CAMPAIGN_SAVE_FORMAT = 'orion-campaign'`, `CAMPAIGN_SAVE_SCHEMA_VERSION = 1`, `CAMPAIGN_RULES_VERSION = 1`, `MAX_CAMPAIGN_SAVE_BYTES = 5_000_000`. Это реализованные значения кодека S3.24, не версия библиотеки верфи.

Не включать дату сохранения, UUID партии, checksum, RNG или журнал команд «на будущее». Первая версия не нуждается в часах/случайности для сериализации; номер хода пригоден для подписи слота. Даты внутри `ShipDesign` сохраняются по его действующей схеме. Контрольная сумма не обеспечила бы авторизацию локального JSON.

## 3. Версия правил и совместимость

`rulesVersion=1` закрепляет текущие карту/топологию/семантику владения, корпуса/слоты, формулы/округления/flight-валидацию проектов, цену и срок производства/refund, доход, топливо/заправку, содержание/дефицит, лимиты и порядок исполнения команд. Это версия набора правил, не версии пакета или Git SHA. Косметические тексты/раскладка UI не требуют её смены.

Особенно важно: [productionStateSchema](../src/domain/production.ts) заново вычисляет срок из снимка. Остаток головного заказа не больше актуального срока, ожидающие заказы должны иметь полный срок. При изменении формул старый снимок может изменить цену возврата или перестать проходить проверку. Нельзя просто принять старый `rulesVersion` текущими формулами или обнулить прогресс.

Первая реализация принимает **только пару schemaVersion1/rulesVersion1**. Любая другая положительная целая версия — явный неподдерживаемый формат/набор правил, без fallback. Версия отсутствует/не число/дробная/неположительная — испорченный конверт. Проверить версии до разбора `session` текущими схемами. При будущей смене формы — новая schemaVersion; при смене семантики — новая rulesVersion; при обоих изменениях — обе. Это ручной контракт разработчика, не автоматическое выявление изменений формул.

Не поддерживаются unversioned CampaignSession, старые корабли без fuel, сессии без fleets, `ShipDesign` v1, библиотечный JSON, сохранённый view и боевой runtime. Существующая миграция библиотеки не вызывается. Миграции кампании и несколько исполнителей разных rulesVersion проектируются отдельно. Документ не создаёт обещания совместимости с несуществовавшими ранее save-файлами.

### Будущий формат2/1 — выбран S3.30, не реализован

**Чистый кодек реализован S3.32, репозиторий — S3.33; исторический заголовок сохранён ради якоря. Только сценовая интеграция ещё будущая.** Полный контракт — [раздел7 управления кампанией](CAMPAIGN_CONTROL.md#7-новый-save-контракт--только-будущий-формат2). Меняется структура, не механика: строгий конверт содержит ровно `format='orion-campaign'`, `schemaVersion=2`, `rulesVersion=1`, прежнюю полную `session` и обязательный `control`. Последний — строго `{mode:'local'}` либо `{mode:'human-vs-ai',aiPolicy:'expansion-v1'}`; local не допускает policy/лишних полей. Policy ID фиксирует решения AI отдельно от версии тарифов; новая политика требует явной поддержки/миграции. Структурно корректный неизвестный ID (1..64 ASCII букв/цифр/дефисов, без trim/coerce) даёт `UNSUPPORTED_AI_POLICY`, неверная форма — `INVALID_SAVE`.

**Реализованный API [campaignRunSave](../src/domain/campaignRunSave.ts):** `CAMPAIGN_RUN_SAVE_SCHEMA_VERSION=2`; `CampaignRunSaveErrorCode = CampaignSaveErrorCode | 'UNSUPPORTED_AI_POLICY'`; `CampaignRunSaveFailure` ровно `{ok:false,code,message}`; `EncodeCampaignRunSaveResult` — `{ok:true,json}` либо failure, `DecodeCampaignRunSaveResult` — `{ok:true,run}` либо failure. `encodeCampaignRunSave(unknown run)` сначала проверяет целую `campaignRunSchema`, затем компактно сериализует пять полей и проверяет UTF-8 cap. Неверный вход/unknown policy/исключение refinement или stringify — `INVALID_STATE`, превышение размера — `SAVE_TOO_LARGE`. Caller не выбирает версии/метаданные. `decodeCampaignRunSave(unknown json)` возвращает независимый кандидат, не применяет его к сцене. Сообщения фиксированные русские, без partial run/сырых исключений/скрытого state.

Переиспользованы `CAMPAIGN_SAVE_FORMAT`, `CAMPAIGN_SAVE_SCHEMA_VERSION=1`, `CAMPAIGN_RULES_VERSION=1`, `MAX_CAMPAIGN_SAVE_BYTES` и прежний `decodeCampaignSave`, без изменения legacy-модуля. Единственная миграция — **полностью валидный строгий1/1 из четырёх полей → detached run с `control={mode:'local'}`**. Не bare session/run/view, missing fuel/fleets, отдельный design или библиотека;1/1 с control и2/1 без control отвергаются. Миграция не пишет bytes и не наследует AI-настройку другой партии; только следующий явный encode создаёт2/1 даже для local. Старые reader/менеджер отказывают на2/1 без удаления control; конкретный старый код может быть `INVALID_SAVE` из-за лишнего поля, не обязательно `UNSUPPORTED_SAVE_VERSION`.

**Точный приоритет decode:** тип string → UTF-8 cap5_000_000 до parse → JSON → базовые strict-ключи/format/конечные положительные целые версии/**own session** → schema → rules → version-specific наличие/форма control → policy → **весь run**. В базовой форме разрешён только дополнительный ключ control, его текущая форма и session ещё не проверяются. Missing session/лишние root-поля/неверные типы версий — `INVALID_SAVE` даже с будущими версиями; неизвестная положительная schema — `UNSUPPORTED_SAVE_VERSION`; поддержанная schema с rules≠1 — `UNSUPPORTED_RULES_VERSION` раньше control/session. Для1 наличие control — `INVALID_SAVE`; **лишь после этих новых guards вызывается старый `decodeCampaignSave`** с прежней полной валидацией и добавляется local. Для2 control обязателен/strict: malformed — `INVALID_SAVE`, структурно верная неизвестная policy — `UNSUPPORTED_AI_POLICY` раньше session, затем `campaignRunSchema` проверяет целый run и даёт `INVALID_STATE` при повреждении. Исключения JSON/base/control дают `INVALID_SAVE`, полной run-схемы/refinement — `INVALID_STATE`.

Полная валидация, независимые snapshots/ID/порядок/FIFO/fuel и прежняя нормализация имён сохранены; новых игровых defaults/ремонта нет. Ровно5MB допустимы, +1 отклонён. Даже строгий1/1 ровно на лимите может после добавления control не поместиться в2/1: decode-миграция успешна, явный encode получает `SAVE_TOO_LARGE`, без обрезки и без гарантии browser quota/вместимости любых400 снимков.

**Реализованный S3.33:** отдельный [CampaignRunSaveManager](../src/utils/CampaignRunSaveManager.ts) с `save(unknown)`/`load()` для целого run. `STORAGE_KEY = CampaignSaveManager.STORAGE_KEY`, тот же `orion_campaign_v1`; optional `providedStorage?: StoragePort` с type-only импортом. Constructor без IO, global storage разрешается заново внутри try каждой операции; injected порт не вызывает global getter. Load: один get, null → `SAVE_NOT_FOUND`, getter/read exception → `STORAGE_READ_FAILED`, иначе новый decode. Save: новый encode **до getter**, затем один set, getter/write exception → `STORAGE_WRITE_FAILED`, успех ровно `{ok:true}` только после возврата set. Экспортированы `LoadCampaignRunResult = DecodeCampaignRunSaveResult | CampaignStorageFailure` и `SaveCampaignRunResult = {ok:true} | CampaignRunSaveFailure | CampaignStorageFailure`; storage code/failure переиспользованы и реэкспортированы. Codec-union сохраняет `UNSUPPORTED_AI_POLICY` (decode; неверная policy при encode — `INVALID_STATE`). Сообщения фиксированные безопасные, без partial run/сырых исключений. Старый менеджер неизменен; нет read-before-save/reread/cache/fallback/remove/rollback/автоupgrade/нового слота/AI. Порт обеспечивает atomic set-or-throw, не менеджер; last successful writer wins не CAS. UI и autoscheduling не входят.

Decode никогда не запускает AI. **Будущая сцена**, не кодек S3.32 и не репозиторий S3.33, принимает session/control вместе, в AI-режиме наблюдает blue и ставит red-ход в paused до Resume-confirm (blue — idle). Ticket/generation/pending/summary/состояние автомата не сохраняются. Подтверждение занятого слота остаётся ответственностью caller; переход сцены на run-менеджер — отдельная задача. Новый кодек не меняет действующие кнопки save/load1/1.

## 4. Полная валидация и сохранение семантики

### Решение S3.27: ручной AI не меняет save

[Контракт AI](CAMPAIGN_AI.md), спроектированный S3.27, **реализован чистыми planner/executor S3.28 и ручным UI S3.29**. Одно явное поручение наблюдаемой активной стороне выбирает существующие команды; нет persisted controller/config/seed/журнала/курсора и новых механик. Поэтому **schemaVersion1/rulesVersion1 сохраняются**; версия политики не сериализуется. Равенство loaded/uninterrupted проверено при одной версии политики/правил, а не обещается между будущими сменами стратегии AI.

Пакет≤3 команды исполняется на отдельном candidate и возвращает state только после успешного endTurn, окончательной schema/turn+1 и проверки строгой фактической квитанции/ожидаемого платежа; ошибка, в том числе конечный RESOURCE_LIMIT, отбрасывает весь пакет. Сохранять можно до/после принятия, не между внутренними командами; executor не обращается к слоту. Последующая ошибка отдельного save не откатывает уже принятый ход. Load/вход/reset ничего не запускают автоматически, summary/план/квитанция в save не попадают. Сам полный документ по-прежнему запрещён как вход планировщика: он содержит скрытые сведения. **UI S3.29** использует inline confirm, captured request/source/generation/disposed и pending-защиту: save/load/reset/ручные команды заблокированы до отмены/подтверждения. До confirm нет планирования; confirm один раз вызывает executor и атомарно принимает state, не промежуточные `scene.execute`. Ошибка/отмена сохраняют партию/drafts. Успешный load очищает AI-summary и старые callbacks, но не запускает AI; save и отмена load сводку не сбрасывают. Наблюдение после AI не переключается, следующая сторона не запускается.

### Проверка существующей сессии

После проверки конверта использовать **существующую целую** `campaignSessionSchema`, не набор независимо проверенных фрагментов. Нельзя ослаблять runtime-схемы для удобства импорта.

- Все6 известных систем ровно по разу; exploration без дублей; колония пригодна и разведана владельцем. Не добавлять home-ownership/историческую достижимость, которых текущая схема не требует.
- [Производство](../src/domain/production.ts): pending+completed суммарно до100 на сторону/200 на партию; pending до3 на колонию. Все ID уникальны и не больше `lastOrderId`; orders строго возрастают по ID. Только голова своей колонии имеет прогресс; completed **не обязаны** быть отсортированы по ID.
- [Корабли](../src/domain/campaignShips.ts): до100 на сторону/200 вместе; уникальные ID **не больше** `production.lastOrderId`, не пересекаются с orders/completed. Пропуски выданных ID допустимы. `lastOrderId` не восстанавливать по максимуму оставшихся записей: отменённые ID уже выданы.
- [Группы](../src/domain/campaignFleets.ts): до20 на сторону/40 вместе,2..10 уникальных участников, один ship максимум в одной группе. Fleet ID возрастают, не больше `lastFleetId`; namespace групп независим, значения могут совпадать с ship/order ID. Счётчик не уменьшать после disband.
- Производство/ships/fleets требуют свои колонии; у кораблей в пути оба endpoints свои и смежны. В группе каждый участник существует и имеет те же сторону/source, а маршруты либо отсутствуют у всех, либо одинаковы. `systemId` во время transit — **источник**, не присутствие. Сохраняется route каждого ship, `remainingTurns` ровно1, отдельного маршрута группы нет.
- `flightDesignSchema` общая с производством/кораблями, не battle. Гражданские проекты без оружия допустимы. Не восстанавливать snapshot по каталогу, не менять компоненты/ID/fuel/remainingTurns и не переносить данные в тактические объекты.

Save/load не являются игровыми командами и не продвигают ход, FIFO, маршруты, доход или содержание. Нулевое топливо в пути допустимо: оно уже списано при вылете. После reload первый **собственный успешный** endTurn завершает маршрут и платит содержание один раз; загрузка сама ничего не начисляет и не возвращает.

Допустимо сохранить/загрузить согласованное состояние на MAX_TURN, с MAX_ORDER_ID/MAX_FLEET_ID, мягким дефицитом либо ошибкой будущего gross cap. Валидность состояния не означает возможность выполнить endTurn/новый заказ. Прогноз пересчитывается после загрузки, `TURN_LIMIT`/`RESOURCE_LIMIT` остаются видимыми, баланс не насыщается до cap и загрузка не лечит технический тупик.

### Нормализация и независимость

Используется результат Zod parse, не исходный объект. Единственная предусмотренная нормализация имён — существующий `.trim()` проекта/компонента; для обычных уже разобранных состояний round-trip сохраняет все значения. Сырые внешние имена с краевыми пробелами становятся каноническими по общей схеме; не обещать байтовое равенство произвольного входного JSON. Даты не обновляются. Новых default/coerce/ремонта/миграции нет.

Разные decode/load возвращают глубоко независимые состояния, включая slots/components/shipIds/transit. Ни входная сессия, ни буфер результата, ни прежняя активная партия не мутируются кодеком/репозиторием. Равенство JSON не требует сохранения пробелов/порядка ключей, но порядок массивов и численные значения сохраняются.

## 5. Размер и внешние входы

Выбран `MAX_CAMPAIGN_SAVE_BYTES = 5_000_000` **байт UTF-8**, включая конверт и пробелы входного текста. Это не `.length` JS-строки и не сжатый размер. Для decode сначала проверить тип string и быстрый отказ при `.length > limit`, затем точное `TextEncoder`-измерение до `JSON.parse`. Выход — компактный `JSON.stringify` проверенного документа, затем та же проверка UTF-8 перед записью. Ровно limit разрешён, limit+1 отвергается. Не обрезать, не сжимать, не разделять запись на части.

Лимит — самостоятельная политика ресурса, **не доказанный максимум** любого runtime-valid state. В партии возможно200 production records плюс200 ships, то есть400 полных снимков. Имя ограничено80 UTF-16 единицами после trim, ID128; кириллица, emoji и JSON escaping меняют байтовую длину. Даты `z.string().datetime()` не имеют отдельного `.max()` длины. Поэтому утверждения «любой save занимает320KB» или «всегда помещается в localStorage» необоснованны. Точный верхний размер и скорость не измерялись; oversized согласованное состояние получает явный отказ сохранения, не потерю части записей.

5MB UTF-8 не гарантируют доступность browser quota: localStorage зависит от браузера, origin и остальных ключей, включая библиотеку. Ошибка квоты не повод удалить библиотеку/старый слот. Кодек не обещает защиту от произвольных JS getters/proxy; внешний файловый/слотовый вход — строка JSON, вход encode — JSON-совместимая сессия владельца. Не использовать `eval`, merge внешних полей в сцену или интерпретацию имён как разметки.

## 6. Реализованный чистый API S3.24

API экспортирован из [campaignSave.ts](../src/domain/campaignSave.ts):

- `encodeCampaignSave(inputState: unknown)` → `{ok:true, json:string}` либо `{ok:false, code, message}`. Проверяет полную сессию, формирует текущий строгий конверт, сериализует, проверяет размер. Не принимает версию/quote/дату от caller, не читает часы/Phaser/storage.
- `decodeCampaignSave(inputJson: unknown)` → `{ok:true, state:CampaignSession}` либо `{ok:false, code, message}`. Проверяет строку/размер → JSON → конверт/версии → полную сессию. Возвращает независимый state, не меняет активную партию.
- Кодек — отдельный domain-модуль, без циклического импорта в campaignSession; с S3.26 подключён к игровому entry через менеджер/сцену, но сам не содержит UI. Строгая `envelopeSchema` проверяет форму и обязательное наличие `session` через `hasOwnProperty`; затем проверяются версии, после них `readSession` применяет существующую целую `campaignSessionSchema`. Игровые команды о save не знают.
- Экспортированы `CampaignSaveErrorCode`, `CampaignSaveFailure`, `EncodeCampaignSaveResult`, `DecodeCampaignSaveResult`: discriminated union по `ok`, при успехе только `json` либо `state`, при отказе только `code`/`message` и `ok:false`.
- `readSession` перехватывает исключения refinement и возвращает `INVALID_STATE`; encode также перехватывает исключение сериализации как `INVALID_STATE`. Результат схемы, включая прежний `name.trim()`, используется вместо исходного объекта. Кодек не читает часы/storage/каталог/библиотеку, не вызывает игровые команды и не содержит UI.

| Код отказа | Значение/порядок |
| --- | --- |
| `INVALID_SAVE` | Вход decode не строка, JSON синтаксически неверен, root не объект или неверен конверт/format/типы версий/набор полей |
| `SAVE_TOO_LARGE` | Сырой текст больше byte cap до JSON parse; либо закодированный документ превышает cap до записи |
| `UNSUPPORTED_SAVE_VERSION` | Конверт имеет верную форму, но положительная целая schemaVersion не1 |
| `UNSUPPORTED_RULES_VERSION` | schemaVersion поддержана, положительная целая rulesVersion не1 |
| `INVALID_STATE` | Поддерживаемый конверт, но session не проходит полную схему; либо encode получил неверную сессию |

Конверт проверяется структурно с `session` как обязательным unknown-полем (отсутствие поля явно проверять), затем schemaVersion, rulesVersion, затем содержимое session. При нескольких ошибках соблюдать этот порядок. Например: unsupported schema + invalid session → UNSUPPORTED_SAVE_VERSION; missing session даже с будущей версией → INVALID_SAVE. JSON null в обязательном session → INVALID_STATE при поддержанных версиях. Вложенные лишние поля → INVALID_STATE, а не молчаливое удаление. Штатные ошибки JSON/валидации/сериализации возвращаются результатом, не необработанным исключением. Сообщения русские, без полного содержимого save и сырых stack traces.

## 7. Хранилище S3.25 — реализованный однослотовый API

[CampaignSaveManager](../src/utils/CampaignSaveManager.ts) экспортирует `static readonly STORAGE_KEY = 'orion_campaign_v1'`. Конструктор принимает необязательный `providedStorage?: StoragePort` и **не обращается к хранилищу**. `StoragePort` импортирован из ShipDesignManager только как тип; его методы/ключи/миграции не используются. На каждой явной операции порт разрешается заново: внедрённый либо `globalThis.localStorage`, внутри соответствующего `try`. Внедрённый порт исключает доступ к global getter, кеша нет. Версия ключа не заменяет версию документа.

- `load(): LoadCampaignResult` делает один `getItem` одного ключа; null → `SAVE_NOT_FOUND`. Исключение global getter или чтения → `STORAGE_READ_FAILED`. Иначе вызывает настоящий `decodeCampaignSave` и возвращает его результат без изменения. **Никогда не пишет**, не создаёт новую партию, не удаляет испорченный слот и не перебирает другие ключи.
- `save(inputState: unknown): SaveCampaignResult` сначала полностью выполняет настоящий encode **даже до разрешения global getter**. Ошибка кодека возвращается без storage-операций. Только успех вызывает один `setItem`; исключение getter/записи → `STORAGE_WRITE_FAILED`, успех — ровно `{ok:true}` после возврата set. Нет чтения перед записью; входная/активная сессия не меняется.
- Экспортированы `CampaignStorageErrorCode`, `CampaignStorageFailure`, `LoadCampaignResult`, `SaveCampaignResult`. Load объединяет результат decode с storage failure, save — `{ok:true}` с codec/storage failure. Отказ имеет только `ok:false`, `code`, короткое фиксированное русское `message`, без сырых exception/stack/payload; `SecurityError`, `QuotaExceededError`, обычный Error и брошенная строка обрабатываются одинаково по виду операции.
- Контракт порта: `setItem` атомарно заменяет значение или бросает без изменения прежнего; стандартный localStorage предоставляет такую границу одной записи. Произвольный тестовый/будущий порт обязан её соблюдать. Не заявлять транзакцию между несколькими ключами или между сценой и диском; не применять «remove → set», rollback-записи и cleanup чужих ключей.
- Явный вызов save заменяет и существующий, и повреждённый слот без предварительного чтения. **Подтверждение перезаписи выполняет сцена S3.26, не менеджер**: для занятости она использует load и прерывает запрос при STORAGE_READ_FAILED; сам save такого чтения не делает. Нет автоматического чтения/сохранения при создании менеджера или входе в сцену, ремонта/удаления слота либо библиотеки.
- Межвкладочные конфликты в v1 не решены: last successful writer wins. Нет CAS, блокировки, storage-event синхронизации или обещания отсутствия потери изменений между вкладками. Не добавлять скрытое автообновление текущей партии.

JSON import/export UI, multi-slot, удаление слота и миграции — последующие задачи. Сам кодек обеспечивает формат, но кнопки обмена файлами не считаются реализованными.

## 8. Интеграция со сценой S3.26 — не реализована, будущая атомарная замена

**Реализовано 2026-09-10; заголовок оставлен для совместимости якоря.** Ручные «Сохранить кампанию»/«Загрузить кампанию» находятся сверху: `campaign-save` x475/y24, `campaign-load` x675/y24. Кнопки верфи не менялись. Используется прежнее inline-подтверждение с «Продолжить»/«Отмена · ESC», без второго modal или ESC-handler. Конструктор, вход, reset и shutdown не выполняют storage IO; при каждом входе новая партия, загрузка только по явному запросу. Сохранение разрешено при наблюдении неактивной стороны, записывает **обе** стороны целиком и не выдаёт NOT_ACTIVE_FACTION: это операция владельца локальной партии, не команда фракции.

Сцена фиксирует `structuredClone(this.campaign)` **до** чтения занятости через `CampaignSaveManager.load()`. SAVE_NOT_FOUND → немедленный `save(candidate)`; валидный, повреждённый, неподдерживаемый по версиям или oversized слот → подтверждение. STORAGE_READ_FAILED → ошибка без записи/подтверждения; нет второго presence API, JSON-парсера или обхода кодека. Подтверждённая запись использует только `manager.save(candidate)`, не текущую live-сессию.

Загрузка: прочитать/декодировать кандидат в отдельную переменную **до** предложения заменить партию. При ошибке текущий state, панели/выбор/черновики и слот остаются прежними; допускается только показ сообщения ошибки. После успешной проверки показать подтверждение потери текущей несохранённой партии. Отмена/ESC удаляет только кандидат/pending; подтверждение применяет именно проверенный снимок, без повторного чтения изменившегося слота.

Пока открыто подтверждение, блокировать команды/переключение/повторный save/load/reset. Сохранение поверх занятого слота также требует подтверждения; если слот изменился к подтверждению, это ограничение last-writer-wins, не гарантированная блокировка. Снимок для записи фиксировать при запросе. Для async-файлов в будущем нужен отдельный жизненный цикл; он не добавляется в синхронный localStorage шаг.

При успешном применении загрузки:

1. Не вызывать `endTurn`, `deploy`, `refuel` и не проигрывать журнал. Принять независимый проверенный state одной заменой владельца.
2. Удалить старые панели/callbacks/pending candidate, закрыть бюджет/production/travel/groups, очистить draft и страницы. `expectedTurn` новых callbacks берётся из загруженного state.
3. Наблюдать активную сторону загруженного turn. Выбор системы: первая собственная в порядке статического определения карты; если собственных нет — домашняя система этой стороны как допустимый ID, **не** выдавая ей ownership/exploration. Не сохранять наблюдение/выбор в save.
4. Сбросить кеш каталога для будущего ленивого чтения, не читать/не записывать библиотеку ради загрузки. Пустая/повреждённая библиотека не блокирует кампанию с автономными снимками.
5. Пересоздать own view/forecast; сообщение «Кампания загружена», без старой квитанции. Не сохранять ни paid, ни shortfall предыдущего хода.

Защита от поздних callbacks реализована: загруженная партия может иметь **тот же turn**, поэтому expectedTurn недостаточно. Уничтоженные панели блокируют старые callbacks через disposed; сцена проверяет disposed, идентичность операции, generation и identity исходной сессии. Reset/shutdown/успешная замена инвалидируют кандидат; замена source даже на равный same-turn state запрещает старое подтверждение. Это неперсистентная защита UI, не поле CampaignSession/сетевой дедупликатор. Доменная загрузка проверяет state, но не обеспечивает сама lifetime сцены.

## 9. Альтернативы

| Вариант | Решение |
| --- | --- |

### Основная приёмка persistence: настоящий localStorage и два reload

Исходно localStorage и sessionStorage пусты; менеджер использует настоящий браузерный localStorage, **без внедрённого порта**. Обе стороны обычными `execute`-командами сцены разведывают/колонизируют, накапливают доход до29, оплачивают по два пресета и проходят FIFO до45. Записей в gameplay state или подстановки готовых кораблей нет.

1. Blue размещает2/1 → группа[2,1] → send. Событие `pointerdown` настоящей кнопки save записывает4058 UTF-8 байт в слот. **Реальный reload страницы** → вход создаёт новую turn1 без автозагрузки → load/отмена без изменений → load/подтверждение восстанавливает канонически равный state. Кнопочный endTurn даёт ожидаемое blue-прибытие на46.
2. Red размещает4/3 → группа[4,3] → send. Save/отмена перезаписи сохраняет старый слот; повтор/подтверждение заменяет его. **Второй реальный reload** → снова свежая партия → load/подтверждение выбирает активную red. Кнопочный endTurn даёт47: обе казны188/258, ships[2,1] в Эдеме/[4,3] в Узле, всем fuel2, transit отсутствует.

Фактически загруженные состояния и следующий результат сравнены с непрерывной веткой через канонический JSON кодека. Временный ключ sessionStorage хранил **только ожидаемые снимки/oracle для проверки**, не использовался для записи слота или игрового state; сохранённый документ не воспроизводился вручную после reload. Библиотечные ключи оставались неизменными/пустыми; заполненная и повреждённая библиотека покрыты тестами, не этим browser persistence-циклом.

После проверки удалены **только созданный campaign-слот и временный проверочный ключ**, исходная пустота обоих хранилищ восстановлена; reset turn1,1panel/1ESC/1canvas. Это действия очистки проверки, не функция удаления слота в игре.

Mouse-попытки основного прогона не сработали в автоматизации, поэтому использованы события настоящих кнопок. **Не полный mouse E2E; физический Escape не подтверждён** (прежнее ограничение доставки клавиши), тесты Phaser ESC проходят. Нет заявления о заполнении реальной квоты, производительности, облаке, CAS/межвкладочной защите или миграциях будущих версий. Принят только описанный ручной локальный цикл; AI/победа и весь S3 открыты.
