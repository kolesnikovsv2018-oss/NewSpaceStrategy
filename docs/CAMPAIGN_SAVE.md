# S3.23 — Контракт сохранения кампании

- Дата решения: 2026-09-09.
- Статус: **проектирование завершено; ни кодек, ни хранилище, ни UI ещё не реализованы**.
- Основание: [план](../reports/2026-09-07/plan.md), [кампания](CAMPAIGN.md), [содержание](CAMPAIGN_UPKEEP.md).
- Область v1: один ручной локальный слот полной мирной партии, отдельный от библиотеки проектов. JSON-кодек общий для слота и будущего обмена файлами; файловый UI, autosave, облако, история слотов, AI и восстановление тактического боя вне первой реализации.

## 1. Проверенные исходные факты

[CampaignSession](../src/domain/campaignSession.ts) содержит обязательные `galaxy`, `turn`, `treasuries`, `production`, `ships`, `fleets`. Все игровые команды карты работают с этой сессией; текущая [MainScene](../src/scenes/MainScene.ts) создаёт новую при входе и освобождает при выходе. Автоматического продолжения/чтения диска нет.

[ShipDesignManager](../src/utils/ShipDesignManager.ts) сохраняет **библиотеку**, не партию. Ключи библиотеки v2/v1 и старого редактора, её импортеры и миграции не подходят для кампании. Совпадение `schemaVersion` не означает совпадение формата.

Существующие схемы строгие, включая вложенные объекты: неизвестные поля не должны молча отбрасываться. Исключение преобразования, которое уже есть: `name` проекта/компонента проходит `.trim()`. Схема не доказывает достижимость партии историей команд: например, не закрепляет вечное владение домашними системами. Это проверка структурной согласованности, не античит.

## 2. Выбранный документ v1

Корень — строгий объект с **ровно четырьмя обязательными полями**:

| Поле | Контракт v1 |
| --- | --- |
| `format` | Строковый литерал `orion-campaign`; отделяет кампанию от произвольного JSON/библиотеки |
| `schemaVersion` | Числовой литерал `1`; структура документа/состояния |
| `rulesVersion` | Числовой литерал `1`; фиксирует игровые правила S3.22 |
| `session` | Полное состояние, принятое текущей `campaignSessionSchema`, а не проекция стороны |

Будущие константы: `CAMPAIGN_SAVE_FORMAT`, `CAMPAIGN_SAVE_SCHEMA_VERSION`, `CAMPAIGN_RULES_VERSION`, `MAX_CAMPAIGN_SAVE_BYTES`. Значения в этом документе — выбранный контракт, не существующие экспорты.

Не включать дату сохранения, UUID партии, checksum, RNG или журнал команд «на будущее». Первая версия не нуждается в часах/случайности для сериализации; номер хода пригоден для подписи слота. Даты внутри `ShipDesign` сохраняются по его действующей схеме. Контрольная сумма не обеспечила бы авторизацию локального JSON.

### Данные состояния

| Область | Сохраняется | Не дублируется |
| --- | --- | --- |
| `galaxy` | Все6 систем: `id`, `ownerId`, `exploredBy` обеих сторон | Определения карты, координаты, имена, пригодность, линии переходов |
| `turn` | Целое1..10⁹; это текущее окно действий | Активная сторона: нечётный blue, чётный red |
| `treasuries` | Обе казны, credits/minerals0..10⁹ | Доход, резервы, долг, суммы будущего содержания |
| `production` | `lastOrderId`, упорядоченные `orders` с `remainingTurns`, `completed` | Quote, refund, кеш характеристик, боевые экземпляры |
| `ships` | ID, сторона, source/system, полный оплаченный `design`, fuel0..3, optional `transit` | ShipState, скорость/HP/батарея, отдельный fleetId |
| `fleets` | `lastFleetId`, `items` с ID/стороной/systemId и упорядоченными `shipIds` | Копии проектов/топлива, отдельный group.transit |

Полный `ShipDesign` v2 сохраняется **в каждой** производственной/корабельной записи. Не подменять его ссылкой на библиотеку или текущим пресетом: библиотека может отсутствовать/измениться, одинаковый design.id не гарантирует одинаковое содержимое снимков. Стратегические ID уникальны по своим правилам; повторяющиеся design.id/component.id между независимыми экземплярами допустимы. Не дедуплицировать и не сортировать массивы при загрузке.

Не сохраняются: `CampaignSessionView`, `income`, `economyForecast`, `endTurnEconomy`, последнее сообщение/ошибка, наблюдаемая сторона, выбранная система, страницы, открытые панели, draft группы, pending modal, каталог, Phaser-объекты, callbacks и `expectedTurn`. Проекция остаётся только собственным срезом UI, полный save содержит скрытые сведения обеих сторон и не является безопасным сетевым представлением.

## 3. Версия правил и совместимость

`rulesVersion=1` закрепляет текущие карту/топологию/семантику владения, корпуса/слоты, формулы/округления/flight-валидацию проектов, цену и срок производства/refund, доход, топливо/заправку, содержание/дефицит, лимиты и порядок исполнения команд. Это версия набора правил, не версии пакета или Git SHA. Косметические тексты/раскладка UI не требуют её смены.

Особенно важно: [productionStateSchema](../src/domain/production.ts) заново вычисляет срок из снимка. Остаток головного заказа не больше актуального срока, ожидающие заказы должны иметь полный срок. При изменении формул старый снимок может изменить цену возврата или перестать проходить проверку. Нельзя просто принять старый `rulesVersion` текущими формулами или обнулить прогресс.

Первая реализация принимает **только пару schemaVersion1/rulesVersion1**. Любая другая положительная целая версия — явный неподдерживаемый формат/набор правил, без fallback. Версия отсутствует/не число/дробная/неположительная — испорченный конверт. Проверить версии до разбора `session` текущими схемами. При будущей смене формы — новая schemaVersion; при смене семантики — новая rulesVersion; при обоих изменениях — обе. Это ручной контракт разработчика, не автоматическое выявление изменений формул.

Не поддерживаются unversioned CampaignSession, старые корабли без fuel, сессии без fleets, `ShipDesign` v1, библиотечный JSON, сохранённый view и боевой runtime. Существующая миграция библиотеки не вызывается. Миграции кампании и несколько исполнителей разных rulesVersion проектируются отдельно. Документ не создаёт обещания совместимости с несуществовавшими ранее save-файлами.

## 4. Полная валидация и сохранение семантики

После проверки конверта использовать **существующую целую** `campaignSessionSchema`, не набор независимо проверенных фрагментов. Нельзя ослаблять runtime-схемы для удобства импорта.

- Все6 известных систем ровно по разу; exploration без дублей; колония пригодна и разведана владельцем. Не добавлять home-ownership/историческую достижимость, которых текущая схема не требует.
- [Производство](../src/domain/production.ts): pending+completed суммарно до100 на сторону/200 на партию; pending до3 на колонию. Все ID уникальны и не больше `lastOrderId`; orders строго возрастают по ID. Только голова своей колонии имеет прогресс; completed **не обязаны** быть отсортированы по ID.
- [Корабли](../src/domain/campaignShips.ts): до100 на сторону/200 вместе; уникальные ID **не больше** `production.lastOrderId`, не пересекаются с orders/completed. Пропуски выданных ID допустимы. `lastOrderId` не восстанавливать по максимуму оставшихся записей: отменённые ID уже выданы.
- [Группы](../src/domain/campaignFleets.ts): до20 на сторону/40 вместе,2..10 уникальных участников, один ship максимум в одной группе. Fleet ID возрастают, не больше `lastFleetId`; namespace групп независим, значения могут совпадать с ship/order ID. Счётчик не уменьшать после disband.
- Производство/ships/fleets требуют свои колонии; у кораблей в пути оба endpoints свои и смежны. В группе каждый участник существует и имеет те же сторону/source, а маршруты либо отсутствуют у всех, либо одинаковы. `systemId` во время transit — **источник**, не присутствие. Сохраняется route каждого ship, `remainingTurns` ровно1, отдельного маршрута группы нет.
- `flightDesignSchema` общая с производством/кораблями, не battle. Гражданские проекты без оружия допустимы. Не восстанавливать snapshot по каталогу, не менять компоненты/ID/fuel/remainingTurns и не переносить данные в тактические объекты.

Save/load не являются игровыми командами и не продвигают ход, FIFO, маршруты, доход или содержание. Нулевое топливо в пути допустимо: оно уже списано при вылете. После reload первый **собственный успешный** endTurn завершает маршрут и платит содержание один раз; загрузка сама ничего не начисляет и не возвращает.

Допустимо сохранить/загрузить согласованное состояние на MAX_TURN, с MAX_ORDER_ID/MAX_FLEET_ID, мягким дефицитом либо ошибкой будущего gross cap. Валидность состояния не означает возможность выполнить endTurn/новый заказ. Прогноз пересчитывается после загрузки, `TURN_LIMIT`/`RESOURCE_LIMIT` остаются видимыми, баланс не насыщается до cap и загрузка не лечит технический тупик.

### Нормализация и независимость

Используется результат Zod parse, не исходный объект. Единственная предусмотренная нормализация имён — существующий `.trim()` проекта/компонента; для обычных уже разобранных состояний round-trip сохраняет все значения. Сырые внешние имена с краевыми пробелами становятся каноническими по общей схеме; не обещать байтовое равенство произвольного входного JSON. Даты не обновляются. Новых default/coerce/ремонта/миграции нет.

Разные decode/load возвращают глубоко независимые состояния, включая slots/components/shipIds/transit. Ни входная сессия, ни буфер результата, ни прежняя активная партия не мутируются кодеком/репозиторием. Равенство JSON не требует сохранения пробелов/порядка ключей, но порядок массивов и численные значения сохраняются.

## 5. Размер и внешние входы

Выбран `MAX_CAMPAIGN_SAVE_BYTES = 5_000_000` **байт UTF-8**, включая конверт и пробелы входного текста. Это не `.length` JS-строки и не сжатый размер. Для decode сначала проверить тип string и быстрый отказ при `.length > limit`, затем точное `TextEncoder`-измерение до `JSON.parse`. Выход — компактный `JSON.stringify` проверенного документа, затем та же проверка UTF-8 перед записью. Ровно limit разрешён, limit+1 отвергается. Не обрезать, не сжимать, не разделять запись на части.

Лимит — самостоятельная политика ресурса, **не доказанный максимум** любого runtime-valid state. В партии возможно200 production records плюс200 ships, то есть400 полных снимков. Имя ограничено80 UTF-16 единицами после trim, ID128; кириллица, emoji и JSON escaping меняют байтовую длину. Даты `z.string().datetime()` не имеют отдельного `.max()` длины. Поэтому утверждения «любой save занимает320KB» или «всегда помещается в localStorage» необоснованны. Точный верхний размер и скорость не измерялись; oversized согласованное состояние получает явный отказ сохранения, не потерю части записей.

5MB UTF-8 не гарантируют доступность browser quota: localStorage зависит от браузера, origin и остальных ключей, включая библиотеку. Ошибка квоты не повод удалить библиотеку/старый слот. Кодек не обещает защиту от произвольных JS getters/proxy; внешний файловый/слотовый вход — строка JSON, вход encode — JSON-совместимая сессия владельца. Не использовать `eval`, merge внешних полей в сцену или интерпретацию имён как разметки.

## 6. Предлагаемый чистый API — следующий шаг

Имена ниже фиксируют направление первой реализации, **ещё не существуют**:

- `encodeCampaignSave(inputState: unknown)` → `{ok:true, json:string}` либо `{ok:false, code, message}`. Проверяет полную сессию, формирует текущий строгий конверт, сериализует, проверяет размер. Не принимает версию/quote/дату от caller, не читает часы/Phaser/storage.
- `decodeCampaignSave(inputJson: unknown)` → `{ok:true, state:CampaignSession}` либо `{ok:false, code, message}`. Проверяет строку/размер → JSON → конверт/версии → полную сессию. Возвращает независимый state, не меняет активную партию.
- Кодек — отдельный domain-модуль, без циклического импорта в campaignSession. Новая wrapper-схема использует campaignSessionSchema; старая команда не узнаёт о save.

| Код отказа | Значение/порядок |
| --- | --- |
| `INVALID_SAVE` | Вход decode не строка, JSON синтаксически неверен, root не объект или неверен конверт/format/типы версий/набор полей |
| `SAVE_TOO_LARGE` | Сырой текст больше byte cap до JSON parse; либо закодированный документ превышает cap до записи |
| `UNSUPPORTED_SAVE_VERSION` | Конверт имеет верную форму, но положительная целая schemaVersion не1 |
| `UNSUPPORTED_RULES_VERSION` | schemaVersion поддержана, положительная целая rulesVersion не1 |
| `INVALID_STATE` | Поддерживаемый конверт, но session не проходит полную схему; либо encode получил неверную сессию |

Конверт проверяется структурно с `session` как обязательным unknown-полем (отсутствие поля явно проверять), затем schemaVersion, rulesVersion, затем содержимое session. При нескольких ошибках соблюдать этот порядок. Например: unsupported schema + invalid session → UNSUPPORTED_SAVE_VERSION; missing session даже с будущей версией → INVALID_SAVE. JSON null в обязательном session → INVALID_STATE при поддержанных версиях. Вложенные лишние поля → INVALID_STATE, а не молчаливое удаление. Штатные ошибки JSON/валидации/сериализации возвращаются результатом, не необработанным исключением. Сообщения русские, без полного содержимого save и сырых stack traces.

## 7. Хранилище — последующий отдельный шаг

Выбран отдельный ключ `orion_campaign_v1`, один ручной слот. Новый репозиторий кампании использует внедряемый порт `getItem`/`setItem`; можно переиспользовать структурный тип StoragePort, но не методы/ключи/миграции ShipDesignManager. Версия в ключе не заменяет версию внутри документа. Нет перебора старых/других ключей при ошибке.

- `load()` читает один ключ один раз; null → `SAVE_NOT_FOUND`. Исключение доступа → `STORAGE_READ_FAILED`. Иначе вызывает decode и возвращает его результат. **Никогда не пишет**, не создаёт новую партию и не удаляет испорченный слот.
- `save(state)` сначала полностью выполняет encode без записи. Только успех вызывает один `setItem`; исключение → `STORAGE_WRITE_FAILED`, успех показывается только после успешного возврата. Ошибки чтения/квоты/записи не выдаются за успех. Активная сессия не меняется.
- Контракт порта: `setItem` атомарно заменяет значение или бросает без изменения прежнего; стандартный localStorage предоставляет такую границу одной записи. Произвольный тестовый/будущий порт обязан её соблюдать. Не заявлять транзакцию между несколькими ключами или между сценой и диском; не применять «remove → set», rollback-записи и cleanup чужих ключей.
- Явное ручное сохранение может заменить существующий, в том числе нечитаемый слот, **после подтверждения пользователем в будущем UI**. Отказ чтения для определения занятости отменяет операцию. Не пытаться «вылечить» слот чтением/автосохранением.
- Межвкладочные конфликты в v1 не решены: last successful writer wins. Нет CAS, блокировки, storage-event синхронизации или обещания отсутствия потери изменений между вкладками. Не добавлять скрытое автообновление текущей партии.

JSON import/export UI, multi-slot, удаление слота и миграции — последующие задачи. Сам кодек обеспечивает формат, но кнопки обмена файлами не считаются реализованными.

## 8. Будущая интеграция со сценой и атомарная замена

Первые кнопки — ручные «Сохранить кампанию»/«Загрузить кампанию» в MainScene, не изменение кнопок верфи. При входе по-прежнему новая партия; загрузка только по явному запросу. Сохранение разрешено при наблюдении неактивной стороны, записывает **обе** стороны целиком и не выдаёт NOT_ACTIVE_FACTION: это операция владельца локальной партии, не команда фракции.

Загрузка: прочитать/декодировать кандидат в отдельную переменную **до** предложения заменить партию. При ошибке текущий state, панели/выбор/черновики и слот остаются прежними; допускается только показ сообщения ошибки. После успешной проверки показать подтверждение потери текущей несохранённой партии. Отмена/ESC удаляет только кандидат/pending; подтверждение применяет именно проверенный снимок, без повторного чтения изменившегося слота.

Пока открыто подтверждение, блокировать команды/переключение/повторный save/load/reset. Сохранение поверх занятого слота также требует подтверждения; если слот изменился к подтверждению, это ограничение last-writer-wins, не гарантированная блокировка. Снимок для записи фиксировать при запросе. Для async-файлов в будущем нужен отдельный жизненный цикл; он не добавляется в синхронный localStorage шаг.

При успешном применении загрузки:

1. Не вызывать `endTurn`, `deploy`, `refuel` и не проигрывать журнал. Принять независимый проверенный state одной заменой владельца.
2. Удалить старые панели/callbacks/pending candidate, закрыть бюджет/production/travel/groups, очистить draft и страницы. `expectedTurn` новых callbacks берётся из загруженного state.
3. Наблюдать активную сторону загруженного turn. Выбор системы: первая собственная в порядке статического определения карты; если собственных нет — домашняя система этой стороны как допустимый ID, **не** выдавая ей ownership/exploration. Не сохранять наблюдение/выбор в save.
4. Сбросить кеш каталога для будущего ленивого чтения, не читать/не записывать библиотеку ради загрузки. Пустая/повреждённая библиотека не блокирует кампанию с автономными снимками.
5. Пересоздать own view/forecast; сообщение «Кампания загружена», без старой квитанции. Не сохранять ни paid, ни shortfall предыдущего хода.

Защита от поздних callbacks обязательна: загруженная партия может иметь **тот же turn**, поэтому expectedTurn недостаточно. Использовать уже существующий disposed старых панелей и отдельную неперсистентную идентичность операции/поколение сцены для подтверждения кандидата; reset/shutdown/успешная замена инвалидируют кандидат. При смене активного state до подтверждения — не применять устаревший кандидат. Это будущая защита UI, не поле CampaignSession/сетевой дедупликатор. Доменная загрузка проверяет state, но не обеспечивает сама lifetime сцены.

## 9. Альтернативы

| Вариант | Решение |
| --- | --- |
| Сохранить только own view | Нельзя восстановить противника, счётчики и скрытую галактику |
| Ссылки на library/design.id вместо снимков | Потеря автономности оплаченных проектов; библиотека изменяема |
| Только schemaVersion, без rulesVersion | Не защищает прежний срок/FIFO/refund от новых формул |
| Автоматически подставить missing fuel/fleets/версии | Угадывание истории и молчаливое изменение партии |
| Сохранять forecast/receipt/group route/active faction | Дублирование источника истины, устаревшие суммы и маршруты |
| Autosave или load при входе | Новые риски перезаписи/чтения повреждённых данных, отдельная задача |
| Сразу IndexedDB/мультислот/checksum | Не нужно для первой ручной записи; не устраняет ограничения валидации/версий |

## 10. Критерии будущей реализации

Все пункты ниже **ещё не выполнены для нового save API**. Существующие1136 регрессий проверяют игру, не этот контракт.

- [ ] Чистый codec: frozen input, два независимых decode; round-trip initial/оба turn parity/дефицит/пределы; русский Unicode/escaping, trim по общей схеме, даты/снимки/порядок массивов сохранны.
- [ ] Матрица входов: нестроки/null/array/сломанный JSON/неверный format/лишние поля/отсутствие session; все варианты версий и их приоритет; библиотечные v1/v2 и старый raw state отвергаются без миграции.
- [ ] Bytes: ровно5_000_000 и+1, whitespace-heavy JSON, кириллица/emoji; size до parse/до записи;200 ships+200 production records и40groups как отдельная валидная диагностическая граница. Не подменять benchmark проверкой схемы.
- [ ] Cross-state corruption: повтор ID, ship.id>lastOrderId, пересечение с production, частичный/разный transit группы, потеря участника/owner, незаконный progress ожидающего заказа, лишний receipt/route/fuel, invalid flight. Пропуски ID и несортированный completed разрешены как сейчас.
- [ ] Продолжение: сохранить после send до endTurn; загрузить и исполнить прежнюю последовательность команд, сравнить с не прерывавшейся веткой. Те же казны/FIFO/ID/дизайны/fuel/группы/квитанции, без повторного расхода топлива/начисления. Повторить для обеих сторон и preset/library; load не требует существования библиотечного проекта.
- [ ] StoragePort: отсутствует/сломанный JSON/будущая версия/read exception/quota write exception; ни одного лишнего чтения/записи, старый слот/все ключи библиотеки/активный state сохранны при отказе. Успех записи — ровно один setItem.
- [ ] UI: save/load/pending/отмена/перезапись занятого или испорченного слота, inactive observation, same-turn stale callback, reset/shutdown/reentry, кандидат не перечитывается при подтверждении; ошибка не сбрасывает текущую игру/панели.
- [ ] Настоящий браузер: явное save → reload страницы → явное load → продолжение, обе стороны/маршрут в пути, ошибка/отмена без потерь,1panel/1ESC/1canvas; библиотека неизменна. Не заменять это fake Phaser тестами.
- [ ] Полные test/typecheck/build, актуализация навыков и новый датированный отчёт на каждом реализованном шаге.
