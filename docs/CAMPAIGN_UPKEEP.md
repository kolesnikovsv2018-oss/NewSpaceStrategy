# S3.20 — Реализованный контракт содержания кораблей

- Дата решения: 2026-09-09.
- Статус: контракт S3.19 реализован в S3.20, 2026-09-09: расчёт, интеграция `endTurn`, квитанция и собственный прогноз. Полный бюджетный UI остаётся отдельным S3.21.
- История: [решение S3.19](../reports/2026-09-09/17-upkeep-contract.md); [реализация S3.20](../reports/2026-09-09/18-campaign-upkeep.md). Исторические отчёты не переписываются.
- Основание: открытый экономический пункт [плана](../reports/2026-09-07/plan.md), принятый мирный цикл S3.18 в [кампании](CAMPAIGN.md).
- Область: регулярный расход кредитов размещённых стратегических кораблей. Не ремонт, топливо, боезапас, груз, тактическая энергия, снабжение или плата за группу.

## Исходные условия решения S3.19 — историческая база

До внедрения содержания [campaignSession](../src/domain/campaignSession.ts) проверял state → command → expectedTurn → active faction. Собственный endTurn проверял MAX_TURN и валовую сумму ресурсов, начислял доход, продвигал FIFO и все собственные перелёты, передавал ход одним независимым state. В S3.20 после валовой проверки добавлено списание, порядок ниже. Доход колонии10 кредитов/5 минералов и начальная казна100/50 сохранены.

[campaignEconomy](../src/domain/campaignEconomy.ts) ограничивает оба ресурса целыми0..10⁹; отрицательная казна недопустима. [CampaignShip](../src/domain/campaignShips.ts) уже имеет уникальный ID, owner, snapshot, fuel/transit; всего до100 кораблей стороны. [Группа](../src/domain/campaignFleets.ts) содержит ссылки на корабли, не дополнительные экземпляры. Завершённые [производственные записи](../src/domain/production.ts) ещё не ships; deploy переносит запись в ships. Расформирование группы не удаляет корабли, команды утилизации нет.

Следствие: отказ endTurn из-за нехватки содержания способен навсегда остановить сторону с большим флотом и пустой казной. Disband это не исправляет. Нельзя вводить такой отказ без отдельного способа выхода; автоматические потери/долги потребовали бы новой модели.

## Выбранные правила v1

### Тариф и объект начисления

- Константа [домена содержания](../src/domain/campaignUpkeep.ts) `UPKEEP_CREDITS_PER_SHIP = 1`: **1 кредит за корабль за собственный успешный endTurn**. Минералы не расходуются.
- База — количество записей session.ships владельца на входе endTurn. Не стоимость проекта, корпус, масса, вооружение, топливо, название, количество групп или тактическая роль.
- Каждый ID считается ровно один раз: свободный/участник группы, стоящий/в пути, полный/пустой бак — одинаково. Не обходить fleet.shipIds для начисления и не суммировать local-colony lists: в пути корабль в них отсутствует.
- Orders/completed/библиотека/пресеты/тактические экземпляры не начисляют содержание. Новый deploy до endTurn входит в счёт сразу. Completed, полученный этим endTurn, не входит; его ещё нельзя разместить внутри той же команды.
- Create/disband/send/refuel сами не списывают содержание и не меняют ставку; отмена заказа возвращает только прежний production refund. На чужом endTurn свои ships не оплачиваются.
- Ни quote, ни ставка не хранятся в ShipDesign, CampaignShip, CampaignFleet или CampaignSession. Нет нового счётчика, таймера, флага «оплачен» или обязательного поля сохранения.

Предел начисления одной стороне100 кредитов за ход. Это намеренно простой предварительный тариф: большой корпус пока стоит столько же, сколько fighter. Ставка не считается сбалансированной и не выводится из реальной себестоимости; её смена требует отдельного решения и пересмотра численных тестов.

### Порядок расчёта и атомарность

Для активной стороны: T — казна до команды, I — валовой доход колоний, N — число её ships, U = N × 1 кредит.

1. Прежние state/command/stale/active проверки, затем MAX_TURN. При отказе ничего не происходит.
2. Рассчитать A = T + I для обоих ресурсов. **Проверить A через прежний treasurySchema до списания содержания.** Если A выходит за MAX_RESOURCE, прежний RESOURCE_LIMIT; расход не «спасает» переполнение и доход не насыщается до cap.
3. P = min(A.credits, U), D = U − P. Итог credits = A.credits − P, minerals = A.minerals. Все значения целые и неотрицательные.
4. На отделённом state записать итоговую казну, продвинуть оплаченный FIFO, одновременно завершить собственные групповые/одиночные перелёты как раньше, увеличить turn. Вернуть state и квитанцию этой команды одним успехом.

Не использовать для A treasurySchema с временным отрицательным балансом, не вычислять сначала T − U и не публиковать промежуточное начисление. Одновременные FIFO/arrival/доход/списание имеют одну командную границу. При любом отказе сохраняются казна, очереди, groups, ships, routes/fuel и turn, включая ранее потраченное успешной отправкой топливо.

Оплата берётся из казны **после** валового дохода. В момент произвольного enqueue/refuel резерв будущего содержания не блокируется: игрок может потратить средства до endTurn. Предыдущий expectedTurn после успеха даёт STALE_TURN; наблюдаемая старая сторона после передачи хода — NOT_ACTIVE_FACTION. Новая команда правильной стороны в её следующем окне действий — новый законный платёж, не дубликат.

### Нехватка: мягкий дефицит, не долг

Если D > 0, endTurn **успешен**, P списывается полностью, credits становится0. D — недофинансирование только этого хода. Оно показывается в квитанции/будущем UI, но не переносится на следующие ходы и не складывается в долг.

Производство и прибытия продолжаются полностью; корабли не теряются, не повреждаются, не выключаются, их топливо/проекты/состав не меняются из-за дефицита. Нет частичной оплаты по ID или «последних неоплаченных кораблей» — квитанция агрегатная. Следующий ход заново рассчитывает U/T/I, никакого погашения прошлого D.

Это не полноценная экономика банкротства: игрок может удерживать флот сверх дохода без потерь и тратить доступные кредиты перед endTurn. При U ≥ I.credits и пустой казне накопление кредитов невозможно, но завершение хода/колонизация/уже оплаченное производство/прибытия не блокируются. Будущие утилизация/долг/штрафы требуют отдельного дизайна, не скрытого усложнения v1. Технические блокировки MAX_TURN/RESOURCE_LIMIT по-прежнему существуют: обещание «без тупика» относится только к новому дефициту содержания.

## Альтернативы и причины отказа

| Вариант | Почему не выбран в v1 |
| --- | --- |
| Процент production cost/массы или тариф по корпусу | Смешивает регулярный расход с предварительными формулами покупки, меняет роли/баланс; сложнее объяснить и проверять. Отдельный будущий баланс |
| Один платёж за группу | Даёт скидку от UI-группировки и позволяет избежать расхода через disband; неверный объект начисления |
| Только стоящие ships | Участники в transit бесплатно избегают содержания; зависит от маршрута, хотя обслуживание ещё не моделируется |
| Отказ endTurn при нехватке | Нет команды удаления корабля и гарантированного пути к платёжеспособности; возможен тупик |
| Отрицательная казна/накапливаемый долг | Новая схема/миграция и правила лимита/погашения; не входят в ограниченный шаг |
| Уничтожение/заморозка неоплаченных ships | Новые потери/прерывание групп/маршрутов, порядок выбора жертв и риск утраты проектов |
| Всё или ничего: при нехватке не списывать ничего | Поощряет недоплату сильнее частичного списания; не выбран |
| Списание до дохода либо проверка cap только после расхода | Меняет доступность оплаты или прежнюю семантику RESOURCE_LIMIT. Сохраняем валовой cap до списания |

## Реализованные API и границы S3.20

API ниже реализованы; полноценное отображение бюджета ещё не подключено и относится к S3.21.

1. Чистый модуль [campaignUpkeep](../src/domain/campaignUpkeep.ts): константа ставки и `getUpkeepQuote(inputShips: unknown, inputFaction: unknown)` → `{shipCount, credits}`. Строго валидирует весь список существующей `campaignShipsSchema` и сторону через `factionIdSchema`, возвращает независимый объект; invalid query бросает ZodError. Не доказывает ownership колоний/согласованность групп — это session boundary. Импорта session нет.
2. `calculateEndTurnEconomy(treasury: Treasury, income: Treasury, quote: UpkeepQuote)` в том же модуле — чистый расчёт **уже проверенных типизированных входов**, не новый unknown-валидатор/обход команд. Возвращает `{ok:true, income, upkeep, treasuryAfter}` либо `{ok:false, code:'RESOURCE_LIMIT'}` после проверки валового A. Внутренний `economyFor` в сессии сначала проверяет MAX_TURN, затем вызывает этот расчёт; его используют и команда `endTurn`, и проекция, без дублирования формул в UI.
3. `SessionCommand.endTurn` неизменен: только kind/factionId/expectedTurn. Caller не передаёт count/price/paid/shortfall, лишние поля отклоняются strict schema. Только успешный endTurn возвращает неперсистентную `endTurnEconomy`: `{factionId, turn: завершённый номер, income: Treasury, upkeep: {shipCount, dueCredits, paidCredits, shortfallCredits}, treasuryAfter: Treasury}`. Остальные успешные команды этого поля не имеют; отказ не содержит state/квитанции. В успешной ветке `SessionResult` поле типизировано как optional `EndTurnEconomy`, поэтому перед чтением требуется проверка его наличия; совместимые ok/state сохранены. Казна возвращённого state отделена от квитанции.
4. `SessionView.income` остаётся **валовым** доходом. Обязательный собственный `economyForecast`: `{ok:true, income, upkeep, treasuryAfter}` либо `{ok:false, code:'RESOURCE_LIMIT'|'TURN_LIMIT'}`. Upkeep поля те же, что в квитанции; объекты detached от сессии, друг друга и результата команды. Forecast — «если владелец завершил бы ход по текущему state»; для неактивной наблюдаемой стороны это гипотетическая оценка, не разрешение выполнить команду. При MAX_TURN прогноз TURN_LIMIT имеет приоритет перед cap, как команда. NOT_ACTIVE_FACTION в прогноз не включён, даже неактивная сторона получает собственный расчёт или технический отказ.
5. Новый forecast после успешного endTurn описывает **следующий** расчёт на новом state, а не последний платёж. [MainScene](../src/scenes/MainScene.ts) показывает реально списанное только по `endTurnEconomy` результата, не восстанавливает его из forecast. `lastReceipt` в CampaignSession нет; это минимальное сообщение, не полноценный бюджетный UI.
6. Чужая казна/число ships/начисление/дефицит не передаются в view даже при разведанных колониях. Own preview доступен без выбранной своей колонии и учитывает все own ships. Локальная проекция не превращается в multiplayer security.

## Совместимость и явное изменение семантики

- Схемы persisted runtime state/ShipDesign v2/библиотеки не меняются, валидный state S3.18 принимается без default/миграции. Старые state без обязательных ships/fleets/fuel остаются INVALID_STATE. Сохранение кампании не добавляется.
- **Структурная совместимость не означает прежние суммы:** с S3.20 следующий endTurn ранее созданной партии начисляет содержание всем её ships. Перерасчёта прошлых ходов/задолженности нет. Для воспроизводимой приёмки начать новую партию; новой версии правил в runtime пока нет.
- Нулевая флотилия полностью сохраняет прежнюю экономику. Минералы/покупки/возвраты/refuel/send/deploy/groups сохраняют формулы. На команду deploy отдельного платежа не добавлять.
- Принятый цикл S3.18 при точном прежнем порядке действий с двумя ships теперь платит2 кредита на каждый из6 собственных endTurn после deploy (включая ход после disband). Текущие тесты S3.20 для обоих preset/library вариантов и обеих сторон подтверждают казны каждого: turn47 =188/258 вместо исторических190/258; turn55 =230/286 вместо240/286; turn57 =248/296 вместо260/296. Turn29/45 до размещения неизменны. Предварительный ручной расчёт S3.19 подтверждён автоматизированными регрессиями; полный групповой браузерный цикл S3.18 заново не повторялся.
- Предыдущий одиночный цикл S3.11 теперь заканчивается на turn21 с114/139 у каждой стороны вместо исторических115/139: один deployed ship оплачивается один раз. ID/проекты и топливо2 после перелёта сохранены. Эти числа подтверждены тестами и новым браузерным пресетным циклом обеих сторон.
- Здесь turn57 означает начало окна57 после завершения56, не завершённый57. Blue платит при завершении45/47/49/51/53/55; red —46/48/50/52/54/56. Первый deploy уже включён в свой endTurn45 или46, отсрочки до следующего собственного окна нет. На начале55 обе стороны завершили по5 начислений, на начале57 — по6; суммы симметричны. Не переносить первое начисление на47/48 и не ослаблять точные ожидания до диапазона.
- S3.20 адресно обновил затронутые численные ожидания, сохранив все проверки input immutability/приватности противника/FIFO/fuel. Сквозной независимый oracle endTurn проверяет экономику и квитанции вместе с прежним продвижением. Исторические отчёты не переписываются.

## Критерии приёмки реализации S3.20

- [x] Quote:0/1/2/100 own ships, обе стороны, смешанные корпуса/стоимость/топливо; одинаковая ставка, invalid lists/faction/duplicate ID отвергаются. Перестановки ships/членства не меняют сумму; frozen input неизменен.
- [x] Свободные/групповые/летящие учитываются один раз; create/disband/send/arrival не создают скидки/дополнительного платежа. Group ID limit/production ID limit не влияют на расчёт.
- [x] Только own успешный endTurn, включая только что deployed ship; orders/completed не начисляют. FIFO-completion в этом ходу не начисляет до deploy. Доход/quote берутся из input state.
- [x] Примеры таблицы, точная/недостаточная оплата, ноль доступных средств в чистом расчёте, повторный дефицит без долга; ни один корабль/группа не теряется/не замораживается.
- [x] При D>0 всё равно продвигаются FIFO/free/group arrivals и turn; при stale/inactive/invalid/turn cap/gross credit или mineral overflow нет даже частичного продвижения/квитанции. Прежнее потраченное send fuel не возвращается.
- [x] Quote/forecast/receipt/result state глубоко независимы. Прогноз активной стороны совпадает с квитанцией следующего endTurn, если между ними не было изменения state. Forecast неактивной стороны не выдаёт права на команду; после успешного deploy/refuel/colonize прогноз пересчитывается.
- [x] Никаких persisted upkeep/receipt/debt полей: valid S3.18 accepted, missing required state invalid. Strict command запрещает подмену quote. Приватность own view, frozen/replay и детерминированность.
- [x] Сохранены все147 UI-контрактов с адресной корректировкой чисел, два preset/library сквозных цикла получают248/296 на turn57. Добавлены явные дефицитные интеграции и cap-before-debit regression, а не только подмена ожиданий; теперь150 сценовых тестов.
- [x] Полные test/typecheck/build прошли. Минимальное сообщение MainScene использует фактическую квитанцию; отсутствие полноценного бюджетного UI явно документировано.
- [x] Актуализированы проектный и корабельный навыки, создан отдельный [отчёт S3.20](../reports/2026-09-09/18-campaign-upkeep.md) с проверками и ограничениями.

После endTurn — turn22, синяя казна0/15, paid25 из due100, shortfall75; все101 корабль сохранены, группа целиком прибыла в Сол с fuel0. Это не полный mouse E2E и не повторная полная групповая браузерная приёмка. Групповые preset/library циклы с новыми суммами проверены автотестами; физический ESC остаётся прежним ограничением. Полноценный бюджетный UI и баланс тарифа этими проверками не подтверждаются.

## Следующие границы

S3.20 реализован в домене и интеграции endTurn с квитанцией/own forecast и регрессиями. **Следующий ограниченный S3.21** — явный UI валового дохода/начисления/ожидаемого списания/дефицита/остатка, гипотетический inactive-preview, ошибки и браузерные проверки. Сейчас работает лишь сообщение фактического платежа, не весь бюджетный интерфейс. S3 и родительский экономический пункт остаются открыты.

Не входят: резервирование будущей платы, утилизация корабля, кредит/долг, автоштрафы/потери, содержание колоний/заказов/групп отдельно, дифференцированный тариф, технологии, автоматический ремонт/заправка, AI, победа/save, лечение проблемы физического ESC. Мягкий дефицит и cap-before-debit — явные ограничения выбранного v1.
