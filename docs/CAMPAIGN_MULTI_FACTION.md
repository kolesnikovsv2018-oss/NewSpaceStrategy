# Н17 — многосторонняя кампания: игровой контракт

- Дата решения: 2026-11-06.
- Статус: контракт этапа [Н17](../plans/tasks-2026-10-09/n17-multiple-factions.md), решения утверждены пользователем. Реализация — подэтапы [Н17.2–Н17.8](../plans/tasks-2026-10-09/n17/README.md). Этим документом runtime не меняется.
- Основание: [CAMPAIGN_CONQUEST.md](CAMPAIGN_CONQUEST.md) (бои, захваты, победа all-planets-v1), [CAMPAIGN_DIPLOMACY.md](CAMPAIGN_DIPLOMACY.md) (двухсторонняя дипломатия Н16), [GALAXY_GENERATOR.md](GALAXY_GENERATOR.md) (профиль, участники 2–8), [CAMPAIGN_CONTROL.md](CAMPAIGN_CONTROL.md), [CAMPAIGN_SAVE.md](CAMPAIGN_SAVE.md). Задание контракта: [n17-01-campaign-contract.md](../plans/tasks-2026-10-09/n17/n17-01-campaign-contract.md).

## Область

Контракт фиксирует продуктовые решения многосторонней военной кампании до кода: диапазон участников, идентичность и metadata, расписание ходов, elimination и пропуски, политику встреч, дипломатию на парах, контроллеры, пределы и версии форматов. Не входит: новые условия победы (Н18), сетевой мультиплеер, безусловные альянсовые флоты, новый импорт карт в UI, миграции прежних сохранений.

## Диапазон участников

- P ∈ 2..8 — диапазон уже поддержан генератором и форматом карты (`MIN_PARTICIPANTS`/`MAX_PARTICIPANTS` в [galaxyMap](../src/domain/galaxyMap.ts)). Более широкий диапазон — отдельное изменение профиля генератора, в Н17 не входит.
- Минимум миров: `worldCount ≥ 3 × P` — enforced генератором; граница кампании (Н17.6) проверяет то же условие при старте. Нижний предел миров в UI — `max(6, 3 × P)` (при P=2 остаётся 6).
- Идентичность: стабильные `player-01..player-0P` из снимка карты; порядок участников — порядок массива `participants` снимка. Enum `blue`/`red` остаётся только в мирной песочнице и исторических форматах; новая политика не выводит участников из enum.
- Опубликованная игровая граница остаётся P=2 до Н17.6: Н17.2–Н17.5 меняют платформу состояния, не расширяя диапазон.

## Metadata участников

- Save-блок `participants` — массив `{ id: 'player-NN', name, color }`.
- `name` берётся из снимка карты (`participants[i].name`); `color` — фиксированная палитра по позиции (индекс в массиве), не от seed и не меняется в партии:
  1. `0x55baff` (синий, преемник текущего blue), 2. `0xf08070` (коралловый, текущий red), 3. `0x7fd76a`, 4. `0xf2d24b`, 5. `0xb07fe8`, 6. `0x4fd6c0`, 7. `0xe86bb0`, 8. `0x9aa8c0`.
- UI — карта, списки, бой, standings — берёт цвет и имя только из metadata; вывод цветов/имён из enum blue/red в многосторонней кампании запрещён.

## Расписание ходов

- Блок расписания в состоянии кампании (Н17.2): ordered participants, активная позиция/фаза, монотонные turn/revision, round.
- Активная сторона определяется расписанием, не чётностью turn; `turn % 2` удаляется из активной логики.
- `turn` растёт монотонно на каждый выполненный **или пропущенный** ход — слот расписания сгорает и при пропуске.
- `round` — полный круг: инкрементируется после того, как круг доходит до последнего участника списка; каждая живая сторона получает ровно одно развитие/начисление за круг.
- Дипломатический раунд Н16 (пара ходов с точкой истечения после endTurn красных) до Н17.4 сохраняет принятую однопарную семантику; с Н17.4 раунд дипломатии — полный круг расписания с единой точкой истечения после endTurn последнего участника круга. Цены, сроки и гейты Н16 не меняются.

## Elimination и пропуски

- Сторона выбывает только при отсутствии **и колоний, и кораблей** (включая в транзите); ноль колоний сам по себе не устраняет сторону с кораблями.
- Elimination — производное состояние снимка (вычисляется при проверках), без отдельного сохраняемого флага.
- Исключённые стороны пропускаются расписанием: их слот продвигает turn/round, полный круг и сроки договоров не застревают.
- Победа остаётся `all-planets-v1` — владение всеми пригодными мирами карты, включая нейтральные; «последний выживший» не побеждает автоматически; новых условий нет (процентная/научная/дипломатическая победа — Н18).
## Встречи (encounter policy)

- Маркер политики: отдельное поле схемы кампании `encounterPolicy: 'conquest-encounters-v2'`; прочие значения отклоняются явно. `battlePolicy` (`campaign-v2`) и `tacticalRules` (`design-combat-v1`) сохраняются — маркер описывает разрешение многосторонних встреч, не тактику.
- Политика: детерминированная последовательность двухсторонних боёв реальным BattleManager. Три и более сторон в системе разрешаются парами; одновременного многостороннего боя нет.
- Порядок пар: по порядку участников из расписания (`player-01` → `player-0P`); циклы повторяются до отсутствия враждебных сторон. Инициатива пары — из RNG-стрима, привязанного к паре участников и seed'у, а не к монете blue/red; RNG-стримы кораблей — `campaign-ship:participantId:shipId`.
- Граница честности: отчёт боя перечисляет только фактические пары (participants/destroyed/winner по парам); результат никогда не объявляется одновременным, если он последовательный.
- Захват: только когда после боёв в системе осталась одна сторона и выполнены условия её пары; до Н17.4 действует принятый однопарный gate перемирия, с Н17.4 — treaty gate по паре конкретного боя/захвата.

## Дипломатия на парах

- Отношения Н16 — контакт, предложения, договоры, война, культура — переводятся на неупорядоченные пары участников; цены, сроки, коды и гейты Н16 сохраняются на каждую пару.
- Лимиты per pair, при P=2 семантика идентична принятой Н16: pending ≤ 1 на сторону **на пару**; история предложений 24 на пару; договоры 12 на пару; журнал 64 на пару.
- `proposeDiplomacy` получает явного получателя `player-NN`; предложение раскрывает получателю отправителя; обмен атомарен per pair с pre-check вместимости казны получателя.
- Treaty gate во встречах — по паре: перемирие с A не блокирует бой/захват против B; захват при coexistence/timeout выполняется только при соблюдении всех условий своей пары, не просто «в системе >1».

## Контроллеры

- Один актуальный формат: `{ mode: 'local' }` либо `{ mode: 'campaign', human: 'player-NN', aiPolicy: 'conquest-v1' }` — один человек + остальные AI. При P=2 это эквивалент принятого human-blue/AI-red (`human: 'player-01'`).
- Прежний формат `human-vs-ai` после bump версий отклоняется явно, без миграций и fallback.
- Takeover → `local`: идемпотентен, не выполняет команд, не меняет расписание.
- Авторизация по расписанию и контролю до действий: человек не командует чужими AI-сторонами, команды AI-сторон от человека отклоняются (`CONTROLLER_FORBIDDEN`); observers не меняют active/control и видят own-only данные.
- AI-последовательность: один bounded пакет на активного AI (≤24 действий, один endTurn — как принято), один captured cancellable ticket в сцене, без рекурсивной синхронной цепочки всех сторон; ни один load не запускает scheduler/AI.
## Пределы и каталоги

- Per-faction пределы прежних значений: 100 кораблей на сторону, 20 групп на сторону, действующие пределы проектов Н05а на сторону.
- Глобальные пределы массивов — фиксированные константы «per-faction × MAX_PARTICIPANTS» (800 кораблей, 160 групп) вместо множителя «×2», закодированного под две стороны; caps проверяются per faction и globally.
- Records казен, знаний, исследований, журналов и каталогов — по участникам с инвариантом «ровно участники кампании, никаких чужих/недостающих ключей»; каждый участник видит только собственные проекты и доступное оборудование.

## Мирная песочница

- campaignMatch и сценарий `joint-survey-v1` не мигрируют: принятый формат match-сохранений, blue/red и кодек остаются прежними; [CampaignMatchSaveManager](../src/utils/CampaignMatchSaveManager.ts) не меняется. Второй актуальный формат военных сохранений не появляется.

## Версии форматов

- Стартовые (факт кода на 2026-11-06): save 18 / rules 15 ([ConquestSaveManager](../src/utils/ConquestSaveManager.ts)), rulesSnapshot 13 ([campaignRules](../src/domain/campaignRules.ts)).
- Целевые: save 19 / rules 16 / rulesSnapshot 14; финальные номера подтверждаются по факту изменений Н17.2–Н17.5 и фиксируются в их отчётах.
- Сохранения прежних версий после bump получают явный типизированный отказ без изменения state или файлов; миграций, version-specific readers и fallback нет. Мирная песочница вне этого bump.

## Диагностика

- Принятый двухсторонний cutoff 200 (baseline Д13–Д16) не переписывается.
- Горизонты для P=3/max (worldCount, окна, метрики, прогрессия) согласуются отдельно в Н17.7 до прогонов и фиксируются отчётом; автоматически от двухсторонних не наследуются.
- Диагностика убирает blue/red/parity: участники и active берутся из расписания/metadata; метрики `ownEnds` — по собственным ходам каждой стороны; проверяются per-faction/global caps, все участники и расписание без starvation.
