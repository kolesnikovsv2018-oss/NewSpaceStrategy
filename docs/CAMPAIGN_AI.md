## 1. Выбор и ограниченный смысл AI v1

Это **одно ручное поручение текущей активной стороне**, blue или red, а не назначение постоянного компьютерного противника. Поручение строит фиксированный план по исходному собственному наблюдению: до одной колонизации уже разведанной системы, до одной разведки, затем ровно один успешный `endTurn`. Новые сведения разведки используются только следующим явно запрошенным AI-ходом. Нельзя автоматически запустить вторую сторону или следующий раунд.

Такой первый этап полезен в существующей модели: расширяет разведанную область и владение, увеличивает реальный доход; собственный `endTurn` продолжает уже оплаченное производство и маршруты. [Географические команды](../src/domain/campaign.ts) не требуют корабля, оплаты, технологий или службы scanner/mining. Добавлять вымышленные миссии колонизатора ради AI нельзя.

**Вне v1:** постановка/отмена/размещение заказов, конструирование проектов, refuel/sendShip, создание/расформирование/отправка групп, поиск многозвенного маршрута, нападение/захват, исследования, оценка угрозы, победа/поражение. Производство/deploy — возможное отдельное расширение после S3.29 с новым ограниченным контрактом; групповые перелёты не являются обязательной частью первого AI. Нет оптимальности, сложности поиска, стратегической памяти, обучения или обещания сбалансированного противника.

Причина не включать производство сейчас: корабль не нужен для разрешённых географических действий, боя/угрозы кампании нет, а бессмысленная покупка создаёт содержание. Дополнительно [ProductionCatalog](../src/utils/ProductionCatalog.ts) читает общую изменяемую библиотеку, создаёт семь новых пресетов; это не фракционные технологии и не детерминированный вход. [createCombatDesign](../src/domain/combatPresets.ts#L47-L58) вызывает `createDesign`/`newId`/`installComponent`; [ID и даты](../src/domain/shipDesign.ts#L131-L155) зависят от часов и модульного счётчика. RNG здесь не обнаружен, но отсутствие RNG не означает детерминированность фабрики. Будущее производство должно получать заранее фиксированный независимый flight-валидный снимок с фиксированными ID/датами, не создавать пресет во время планирования. В v1 нет даже такого дополнительного параметра или зависимости.

## 2. Проверенные исходники и граница знания

| Источник | Факт, существенный для контракта |
| --- | --- |
| [campaignAiPlanner.ts](../src/domain/campaignAiPlanner.ts) | Только стираемые type-imports, минимальный `DeepReadonly`-снимок, один детерминированный план по исходному наблюдению |

| [campaignSession.ts](../src/domain/campaignSession.ts) | `executeSessionCommand(unknown, unknown)` проверяет state → command → expectedTurn → active faction → действие. Успех detached, отказ без state. Turn — окно одной стороны: нечётный blue, чётный red |
| [собственная проекция сессии](../src/domain/campaignSession.ts#L296) | Поля `galaxy`, `turn`, `activeFactionId`, own `treasury`, `income`, `economyForecast`, `production`, `ships`, `fleets`. Сторона наблюдения находится в `galaxy.factionId`, не в корне |
| [production.ts](../src/domain/production.ts) | В view только own orders/completed, **нет lastOrderId**. Предоплата, FIFO по одному head каждой своей колонии, без переноса прогресса |
| [campaignShips.ts](../src/domain/campaignShips.ts), [campaignFleets.ts](../src/domain/campaignFleets.ts) | Только own ships/fleets в session view, **нет lastFleetId**. В пути systemId — источник; маршрут хранится у ships, группа требует согласованных маршрутов участников |
| [campaignUpkeep.ts](../src/domain/campaignUpkeep.ts) | Forecast готовый, свой, условный даже для inactive. Не разрешает командовать; дефицит не запрещает endTurn, gross cap запрещает |
| [MainScene](../src/scenes/MainScene.ts), [CampaignPanel](../src/ui/CampaignPanel.ts) | Сцена доверенно владеет полной сессией, панель получает только SessionView. Смена наблюдения не меняет active; обычный execute сразу принимает каждый успех — не готовая batch-транзакция |
| [кодек](../src/domain/campaignSave.ts), [менеджер](../src/utils/CampaignSaveManager.ts) | Полная schema/cross-state проверка, независимый load-кандидат. Save содержит скрытые данные обеих сторон; его нельзя передавать планировщику |

`CampaignSystemView` у неизвестной системы содержит **только** id/name/x/y/visibility; полей ownerId/habitable нет, не null и не false. После своей разведки доступны текущие ownerId/habitable; разведка постоянная, не last-seen снимок. `exploredBy` противника не передаётся никогда. Свои колонии всегда explored по инвариантам сессии; отсутствие колоний допустимо, схема не гарантирует вечное владение домом или историческую достижимость.

Планировщику запрещены `CampaignSession`, `CampaignState`, `getGalaxyDefinition()`, чужая проекция, save JSON, каталог/библиотека, глобальные счётчики и callbacks запросов к полной модели. Не угадывать пригодность/владение по известному имени, ID, координатам, домашней системе или стартовой раскладке. ID используются только для идентичности и общего порядка; lanes — только из выданной проекции. Нельзя пробовать `colonize` неизвестной системы для получения ошибки-разведки. Пропуски глобальных ID не являются multiplayer-защитой; v1 вообще не передаёт эти ID планировщику.

Это архитектурное разграничение доверенного локального кода, **не sandbox/сетевой античит**. Исполнитель обязан читать полный state для валидации/выполнения, но не для оценки кандидатов. Проверка полного state может отклонить повреждение скрытой части как общий `INVALID_STATE`, без подробностей; сравнение приватности ниже относится к двум **валидным** состояниям.

## 3. Реализованные типы и API S3.28

Чистые модули [планировщика](../src/domain/campaignAiPlanner.ts) и [исполнителя](../src/domain/campaignAiExecutor.ts) разделены; существующий session API не расширен новым игровым kind. Ниже — фактические экспорты S3.28. Планировщик не имеет runtime-imports; исполнитель использует прежние схемы и команды, не подключён к игровому entry.

| Реализованный символ | Сигнатура/форма и ответственность |
| --- | --- |
| `AiTurnRequest` | Ровно `{factionId: CampaignFactionId, expectedTurn: number}`; нет policy/config/budget/view/plan/design от caller |
| `AiObservation` | `DeepReadonly<Pick<CampaignSessionView, 'galaxy' \| 'turn' \| 'activeFactionId' \| 'economyForecast'>>`. Собственные казна/доход/списки не передаются отдельно; успешный forecast уже содержит own income/upkeep/treasuryAfter |
| `AiCommand` | `Extract<SessionCommand, {kind: 'colonize' \| 'explore' \| 'endTurn'}>`; payload строго прежний |
| `AiPlan` | `{commands: readonly AiCommand[]}` с дополнительными инвариантами раздела4; максимум3, последний и единственный endTurn |
| `planAiTurn(view: AiObservation, context: Readonly<AiTurnRequest>)` | Чистый типизированный запрос → `{ok:true, plan:AiPlan}` либо `{ok:false, code:'STALE_TURN' \| 'NOT_ACTIVE_FACTION' \| 'TURN_LIMIT' \| 'RESOURCE_LIMIT'}` |
| `AiPlanResult` | Экспортированный union результата `planAiTurn` по `ok`; отказ не содержит план или сообщение зависимости |
| `executeAiTurn(inputState: unknown, inputRequest: unknown)` | Единственный runtime-вход пакета → `AiTurnResult`; сам создаёт observation/план, не принимает сторонний planner callback/план |
| `AiTurnResult` | Успех: `{ok:true, state:CampaignSession, summary:AiTurnSummary}`; отказ: `{ok:false, code:AiTurnErrorCode, message:string}` **без state/summary/частичного плана** |
| `AiTurnSummary` | `{factionId, turn: завершённый, commands: AiCommand[], endTurnEconomy: EndTurnEconomy}`. Только выполненные команды≤3 и фактическая собственная квитанция, независимые от state/плана |
| `AiTurnErrorCode` | `SessionErrorCode \| 'AI_PLAN_INVALID' \| 'AI_EXECUTION_FAILED'`; неверная форма request — существующий `INVALID_COMMAND` |

`DeepReadonly` экспортирован планировщиком и означает рекурсивную readonly-типизацию. Сам тип не замораживает runtime: исполнитель явно копирует разрешённые поля из `getCampaignSessionView(validState, request.factionId)` **на каждом уровне** и рекурсивно замораживает независимые observation/context. Не передаёт весь объект через type cast/структурное присваивание: лишние runtime-поля иначе останутся. Неизвестная система копируется без ownerId/habitable даже при загрязнённой проекции; лишние поля galaxy/forecast/income/upkeep/treasuryAfter также не проходят. Все вложенные массивы/tuple/object заморожены, исходная проекция не замораживается и не меняется. Сортировка только локальной копии.

Отдельная **runtime-схема AiObservation в v1 не нужна**: это внутренний производный снимок от проверенной сессии, не импортируемый JSON/API. Публичный typed planner пригоден для unit-тестов/чистого выбора, но не авторизует подделанный view и не обещает обработать произвольный JS-ввод. Непроверенный результат planner никогда не считается разрешением изменить игру. Если появится внешний view-вход, потребуется отдельная схема, а не объявление TypeScript runtime-валидатором.

В `executeAiTurn` обязательны: вся существующая `campaignSessionSchema.safeParse` (в try из-за возможных исключений refinement), строгая request-схема с `factionIdSchema` и целым expectedTurn1..MAX_TURN без coerce/default; затем stale, active. Не проверять только own-фрагмент и не подставлять отсутствующие ships/fuel/fleets. Схемы сессии/проектов не ослабляются. `safeParse` не гарантирует отсутствие исключений пользовательских refinement; parse ошибок запроса/состояния возвращает общий код без issue paths/сырого exception. Входная область — JSON-совместимые plain-данные, не гарантия безопасности произвольных getters/proxy/ресурсного истощения.

## 4. Детерминированная политика и бюджет

План строится **один раз по исходному view**, без симуляции полных состояний, повторной оценки после команд или дерева вариантов. Context — только захваченные factionId/expectedTurn, без истории предыдущих запусков. Проверки planner: несовпадение context.expectedTurn с view.turn → STALE_TURN; context.factionId с view.galaxy.factionId либо activeFactionId → NOT_ACTIVE_FACTION; затем неуспешный economyForecast → его TURN_LIMIT/RESOURCE_LIMIT. Это не заменяет проверок исполнителя.

Далее:

1. Собрать множество собственных колоний: только `visibility === 'explored' && ownerId === factionId` в исходном view.
2. Кандидаты colonize: explored, ownerId ровно null, habitable ровно true, прямой lane к исходной собственной колонии. Выбрать минимальный ID; добавить **не более одной** команды colonize.
3. Кандидаты explore: visibility unknown и прямой lane хотя бы к одной **исходно** explored системе. Владение/пригодность соседа не ограничивают разведку. Выбрать минимальный ID; добавить **не более одной** команды explore. Не предсказывать скрытые свойства цели.
4. Добавить endTurn последней командой независимо от наличия первых двух. Всем командам поставить одни и те же request.factionId/expectedTurn. У endTurn нет systemId.

Порядок команд всегда **colonize → explore → endTurn**, отсутствующие действия пропускаются. Неизвестную цель этой разведки нельзя колонизировать в том же пакете. Исходно разведанная нейтральная система, получившая соседа-колонию только на первом шаге пакета, также ждёт следующего запроса. Это сознательное ограничение, а не недостающая ветка реализации.

Порядок кандидатов — лексикографический по ASCII `SystemId`, сравнением `<`/`>` (не `localeCompare`/названием/порядком массива). Для текущих ID: dust, eden, nexus, rift, sol, vega. Это общий порядок ключей, не таблица полезности фиксированной карты. Разворот lanes, перестановки систем/переходов, имена/координаты не меняют выбор при той же географии/видимости. Никакого BFS с неявным tie-break, RNG/seed, Date/performance/timer, счётчика модульных вызовов или библиотечного порядка.

**Фиксированный бюджет v1:** ≤1 colonize + ≤1 explore + ровно1 endTurn, итого1..3 команды в успешном плане; один вызов planner, ≤3 попыток `executeSessionCommand`, ≤1 попытки endTurn и ≤1 его успеха. Бюджет не передаётся пользователем, не расходуется в игровых ресурсах и не ограничивает обычные ручные команды. Все циклы ограничены длиной массивов (карта6 систем/6 lanes, план≤3). Нет `while` до успеха, повторов после ошибки, бесконечного ожидания денег, продолжения следующей стороны или квоты миллисекунд. Это доказательство конечности по числу шагов, не обещание FPS/времени полной schema-проверки.

Пустых планов/результата «успех без завершения хода» нет. Нет подходящих целей, всё разведано/занято, нет колоний или explored-систем → пропустить невозможные географические действия и endTurn. При нуле колоний разведка всё ещё возможна от своих explored-систем; colonize без собственной соседней колонии невозможен. Дом/разведка не восстанавливаются автоматически, поражение не объявляется.

## 5. Исполнение: атомарность всего пакета

Исполнитель синхронный, чистый, без IO/Phaser/storage/библиотеки и внешних callbacks. Полный state — только доверенная рабочая копия, не вход политики.

1. Проверить полный inputState, получить detached candidate; проверить request → stale → active. State error приоритетнее malformed request, malformed request приоритетнее stale, stale приоритетнее inactive; TURN_LIMIT раньше RESOURCE_LIMIT через существующий forecast.
2. Построить и заморозить разрешённую own observation из candidate; один раз вызвать planner. Его отказ немедленно завершает пакет без команд. Исполнитель не подсказывает policy цель по полному state.
3. Проверить **весь** план до первой команды: строгий объект с единственным полем commands,1..3 strict `sessionCommandSchema`-валидных команд, только разрешённые kind, одна сторона/исходный expectedTurn, необязательные colonize/explore ровно в указанном порядке/не более одного каждого, обязательный единственный завершающий endTurn. Нарушение → AI_PLAN_INVALID. Разобранные команды независимы от выхода planner и рекурсивно заморожены перед dispatch. Внутренний бюджет проверяется также перед каждым dispatch; он не может быть расширен результатом planner. API исполнения произвольного готового плана не экспортирован.
4. Выполнить конечный проход плана: `executeSessionCommand(candidate, command)`. **Только** при ok заменить локальный candidate на result.state. Нельзя вызывать `executeCampaignCommand`, advanceProduction/advanceShipTravel или менять владельца/казну/turn вручную. Нет catch-and-continue, смены цели при отказе или повторного endTurn.
5. При первом доменном отказе отбросить весь candidate/предварительный журнал, вернуть код отказа и безопасное фиксированное сообщение. Исключение внутри planner/projection/dispatch → AI_EXECUTION_FAILED без сырого exception. Ошибки первичной полной схемы → INVALID_STATE. Ни один отказ не возвращает частично изменённый state/receipt/план/проекцию.
6. После успешного последнего endTurn повторно проверить **полную** `campaignSessionSchema`, строгую форму квитанции и turn=исходный+1. Квитанция не допускает лишние поля, включая вложенные. Сохранённая казна непосредственно перед endTurn, итоговый own income и `getUpkeepQuote` используются в прежнем `calculateEndTurnEconomy`: проверяются сторона/завершённый ход, оба дохода, число кораблей, начисление/фактическая оплата/дефицит, оба остатка и их совпадение с итоговой казной. Это проверка реального платежа, **не сравнение с прогнозом следующего хода**; итоговая проекция не передаётся обратно планировщику. Любое расхождение → AI_EXECUTION_FAILED без частичного результата. Единый success содержит заново разобранный detached state, отдельную квитанцию и копии команд summary. Caller принимает state **одной заменой**, затем строит UI view. Между внутренними командами ничего не публикуется и не сохраняется.

При RESOURCE_LIMIT на окончательном endTurn откатываются **включая colonize и explore этого пакета**. Ранее успешные ручные команды до его входа не откатываются: уже потраченное send fuel остаётся. Для этого нельзя использовать текущий scene.execute по каждой команде: он немедленно публикует каждый успех. Нужна отдельная граница пакета над существующим чистым session API.

После предварительно успешного forecast колонизация может увеличить доход и сделать окончательный endTurn недопустимым: **весь пакет — отказ**, без fallback «только endTurn»/уменьшения бюджета/тайного skip colonize. Игрок может явно завершить обычный ход без этой колонизации или отдельно потратить средства законной командой и заново попросить AI; автоматически лечить cap v1 не умеет. При исходном ошибочном forecast planner отказывает до любых действий. MAX_TURN блокирует весь пакет, хотя отдельные ручные не-endTurn команды в игре там ещё допустимы; MAX_TURN−1 допускает один успех до MAX_TURN.

Атомарность относится к **игровому state**, не к нескольким ключам storage или восстановлению процесса. Повтор на исходном снимке воспроизводит тот же результат; caller обязан принять результат. Повтор со старым expectedTurn на новом state → STALE_TURN. Same-turn замена партии/старый callback защищаются владельцем сцены, а не expectedTurn; request-id/дедупликации/сетевой revision нет.

## 6. Реальная экономика и технические пределы

Правила не меняются. [Ресурсы](../src/domain/campaignEconomy.ts): каждое целое0..1_000_000_000; [turn](../src/domain/campaignSession.ts):1..1_000_000_000. Старт100 credits/50 minerals каждой стороне; одна текущая собственная колония приносит10/5 на собственном endTurn, в том числе основанная этим пакетом. Ноль колоний → нулевой доход, не поражение.

- Explore/colonize бесплатны. Нулевая казна/недостаток средств на покупку не запрещают их; AI v1 не покупает и не должен ждать денег или возвращать INSUFFICIENT_RESOURCES за эти действия.
- Содержание1 credit за каждый own размещённый ship, включая свободных/участников/летящих/fuel0, один раз; orders/completed не учитываются. При доступных A=T+I платёж min(A.credits, shipCount), дефицит не долг/потери/запрет FIFO или arrival. Минералы на содержание не списываются.
- **Оба валовых A проверяются на cap до списания**. Точное равенство допустимо, +1 отклоняет весь endTurn и наш пакет. AI не резервирует деньги, не обрезает доход, не выдаёт субсидий и не считает forecast разрешением обойти command API.
- Существующий endTurn продвигает один own FIFO-head каждой колонии и все own free/group transit, даже при дефиците; чужие казны/production/ships/fleets не меняются. Разведка меняет только знание запрошенной стороны, колонизация — видимое свободное владение.
- [Производство](../src/domain/production.ts): credits=ceil(stats.cost/100), minerals=ceil(stats.mass/10), turns=max(1,ceil(credits/50)); полная предоплата; refund каждого ресурса=floor(cost×remaining/total). До3 pending/колонию,100 pending+completed/сторону, ID≤10⁹. AI v1 их не создаёт/не отменяет; старые оплаченные записи прогрессируют обычным endTurn.
- [Корабли](../src/domain/campaignShips.ts):100/сторону отдельно от производства, deploy сохраняет ID и бесплатно выдаёт fuel3; send расходует1, refuel недостающей единицы стоит5/2. Прибытие не заправляет. [Группы](../src/domain/campaignFleets.ts):20/сторону,2..10 участников, ID≤10⁹ отдельно. Пределы ID не присутствуют в own view; v1 не требует дополнительных флагов доступности, поскольку не создаёт сущности. Исчерпанные счётчики/полные списки не запрещают сам endTurn, если остальная сессия валидна.

## 7. Приватность результата и детерминизм

Фиксированный план не читает промежуточные own-проекции после explore. Поэтому изменение скрытого владельца или чужой разведки не меняет даже **полный список команд** при равном исходном own view/context. Unknown-цели разведываются независимо от их пригодности/владельца; колонизация касается только исходно открытых сведений. Новая собственная разведка видна caller только в окончательном успешном state и обычной own-проекции, не через отладочный канал.

Summary публикуется только после commit-ready success: factionId/завершённый turn,≤3 выполненных команд с публичными ID, реальная own квитанция. Не включать полный state/save/вражеские финансы/списки/счётчики/exploredBy, предварительные кандидаты, новые свойства разведанной системы или сырой текст исключения. При отказе — только общий код и короткое фиксированное русское сообщение из безопасного справочника; не отдавать Zod issues/path, transcript или snapshot. Даже если внутренняя разведка успела выполниться, её результат при отказе нигде не отображается/не логируется. Фактическая квитанция не заменяется прогнозом следующего хода.

Для двух валидных полных состояний с одинаковой AiObservation/context: одинаковый план и статус/summary пакета, но равенство полного success state не требуется (минимальная AiObservation не включает даже собственные FIFO/ships/fleets). В парных тестах приватности зафиксирована **вся исходная own SessionView**, меняются только скрытые данные. После **успешной** разведки новые own view закономерно различаются при разном скрытом владельце цели — это заработанное знание, не утечка. Изменение чужой казны/очереди/кораблей/групп или глобальных счётчиков в допустимых пределах не влияет на выбор и собственный результат. Проверен весь план/outcome/summary и отсутствие логов на успехе и при позднем cap; отдельная пара с равной минимальной observation, но разными собственными FIFO/маршрутами подтверждает равенство summary при разных полных результатах.

Для одинакового канонического полного state/request и той же версии политики: полностью равные state/summary/ошибки независимо от даты выполнения, числа прежних вызовов и наличия библиотеки. Планировщик не создаёт проектов и не обновляет их даты, исполнитель только сохраняет/продвигает существующие snapshots командами. Нет неявных часов, RNG, генерирования ID или стабильности порядка каталога.

## 8. Save/load и будущий UI

**Форматы остаются schemaVersion=1/rulesVersion=1**, ShipDesign v2 и ключ `orion_campaign_v1` прежние. Политика выбирает уже существующие команды, а не меняет механику/формулы/схемы. Нет persisted controller, назначения стороны, AI config, курсора плана/счётчиков шагов, журнала или seed; сериализовать нечего. Обозначение «политика v1» — контракт реализации, не новое поле save. Смена самой политики не обещает старых будущих решений после обновления клиента; совпадение loaded/uninterrupted гарантируется при одной версии политики/правил. Изменение игровых правил всё ещё требует отдельного rulesVersion по [контракту сохранения](CAMPAIGN_SAVE.md#3-версия-правил-и-совместимость).

Сохранение разрешено только внешнему владельцу до/после пакета, никогда между его командами; сам executor не читает/пишет слот. Ошибка отдельного save **после** принятого AI-хода не откатывает его, старый слот остаётся по контракту порта; это две разные операции. При load применяется полный проверенный снимок без команд, содержания, прогресса, повторной оплаты или автоматического AI. Constructor/entry/reset/render/load не запускают AI. Нет демона/update-loop, setTimeout, автопродолжения после ошибки, autosave и «AI управляет red навсегда».

S3.29 должен добавить явное действие «AI: один ход» для **наблюдаемой активной** стороны. Для другой стороны пользователь сперва переключает наблюдение; нельзя молча поручать чужую видимому игроку сторону. Перед выполнением — inline подтверждение, что AI завершит текущий ход; отмена/ESC ничего не выполняют. Блокируются остальные команды/save/load/reset во время pending. Captured factionId/expectedTurn дополняются существующими operation/generation/source identity/disposed: старые callbacks после redraw/load/reset/shutdown не меняют даже новую партию с тем же turn.

При подтверждении строится план по актуальной проверенной исходной сессии, если source identity всё ещё та же; preview/выполнение до подтверждения не нужны. Синхронный пакет не прерывается Escape посреди команд; cancel действует до запуска. Success принимается одной заменой сессии, очищает draft/страницы/вложенные панели/старую квитанцию, показывает summary стороне, завершившей ход; наблюдение автоматически не переключается и следующая сторона не запускается. Отказ сохраняет сессию/выбор/допустимые drafts, меняет только сообщение. При смене наблюдения/load/reset/shutdown старый summary убирается. Это **будущие** требования UI, не выполненные S3.27/S3.28.
