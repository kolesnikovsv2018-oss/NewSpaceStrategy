# 22 — Чистый кодек сохранения кампании

- Дата: 2026-09-09
- Пункт плана: S3.24
- Статус: выполнено в границах чистого JSON-кодека

## Цель и границы

Реализовать encode/decode по [контракту S3.23](../../docs/CAMPAIGN_SAVE.md), не подключая хранилище или UI. Сериализация полной сессии и проверяемое восстановление работают; **игрок пока не может сохранить партию в слот**. S3.25/S3.26, родитель сохранения/AI/победы и S3 остаются открытыми.

## Изменения и решения

- Новый [campaignSave.ts](../../src/domain/campaignSave.ts): четыре константы формата/версий/предела, `encodeCampaignSave`, `decodeCampaignSave`, типизированные результаты и ошибки.
- Строгий корень `format='orion-campaign'`, `schemaVersion=1`, `rulesVersion=1`, обязательная `session`. Проверка присутствия session явная: одного `z.unknown()` недостаточно для обязательного ключа.
- Decode проверяет строку и UTF-8 размер → JSON → форму конверта → версию структуры → версию правил → целую существующую `campaignSessionSchema`. Старые форматы/библиотека/лишние поля не мигрируются и не исправляются.
- Encode получает независимо разобранную сессию, создаёт компактный JSON и проверяет размер результата. Предел5_000_000 байт включительный; `.length` используется только для быстрого отказа, точный размер — через TextEncoder.
- Существующие схемы, формулы и правила игры не изменены. Trim имён прежний; даты, порядок массивов, счётчики, маршруты и снимки не обновляются. Разные decode возвращают глубоко независимые значения.
- `INVALID_SAVE`, `SAVE_TOO_LARGE`, `UNSUPPORTED_SAVE_VERSION`, `UNSUPPORTED_RULES_VERSION`, `INVALID_STATE` содержат русское сообщение, без частичного state и сырого исключения. Внутренний `readSession` перехватывает исключения проверок, encode — сериализации; decode JSON syntax имеет отдельную границу отказа.
- Модуль не обращается к localStorage, часам, RNG, Phaser, каталогу/библиотеке и не вызывает игровых команд. Его результат — кандидат состояния, не замена владельца сцены.

Добавлен [campaignSave.test.ts](../../tests/campaignSave.test.ts), обновлены [README](../../README.md), [кампания](../../docs/CAMPAIGN.md), [содержание](../../docs/CAMPAIGN_UPKEEP.md), контракт и [план](../2026-09-07/plan.md). Зависимости, lock-файл, существующие исходники и прежние тесты не менялись.

## Регрессии

**299 новых тестов**, прежние1136 сохранены:

- Конверт/приоритеты ошибок/типы версий/обязательные поля, нестроки и malformed JSON; валидные библиотечные v1/v2 и raw state/view отвергаются как чужой формат.
- Повреждения полной сессии через оба API: IDs/счётчики/пересечения, очереди/прогресс, ownership, состав и общий transit, flight-проекты, обязательное fuel/fleets, лишние forecast/receipt/runtime-поля. NaN/±Infinity на encode и буквальные1e400/−1e400 в session JSON отвергаются.
- Frozen input, повторные decode, независимость компонентов/shipIds/transit/снимков с одинаковым design.id; несортированные completed/ships и пропуски ID допустимы. Русский текст/emoji/escaping/trim и даты сохранны.
- Точный UTF-8 предел и+1, включая строки короче5M UTF-16 единиц и whitespace; oversized отклоняется до JSON.parse. Для encode построен **валидный по прежней схеме** снимок с длинной дробной частью datetime: ровно5MB принимается,5MB+1 отвергается без изменения schema.
- Отдельная диагностическая максимальная сессия:200 ships+200 production records (400 снимков) и40groups. Terminal/resource cap/дефицит остаются прежними: decode не платит, не перемещает и не «лечит» состояние.
- Два **оплаченных обычными командами** preset/library цикла обеих сторон: колонизация → накопление turn29/380/190 → по два заказа → FIFO до45/170/248 → deploy/group/send → round-trip до каждого own endTurn. Восстановленная и непрерывная ветви совпадают по всему state и квитанциям; итог turn47/188/258 каждой стороне, группы в целях, fuel2. Библиотечный проект сохранён настоящим ShipDesignManager во временный порт, затем изменён и удалён из этой библиотеки; оплаченные снимки остаются автономными. Игровое состояние в этих двух циклах не подставлялось.
- Два fault-mock теста отдельно проверяют перехват исключений `safeParse` и `JSON.stringify`. Это проверка exception-ветвей, не доказательство реальной валидации. Остальная матрица использует реальные схемы/команды; spies наблюдают отсутствие запрещённых обращений.

### Браузерная проверка — не persistence E2E

В новой вкладке dev-сервера импортированы только модули кодека/сессии. В локальной переменной создана новая партия, настоящими командами обе стороны колонизировали соседние системы и завершили ход до turn3. Encode/decode сохранил полное состояние; следующий endTurn восстановленной/исходной ветви совпал целиком. Текст дополнен пробелами ровно до5_000_000 байт — успех; ещё1 байт — SAVE_TOO_LARGE. Поддержанная schemaVersion с rulesVersion2 и null session дала UNSUPPORTED_RULES_VERSION до проверки состояния.

Сцена не изменялась, сохранение в browser storage не выполнялось, сериализованное пользовательское хранилище осталось прежним. Предыдущий page ID оказался недоступен, новая вкладка работала. Это smoke **чистого модуля**, не нажатия будущих кнопок, не save→reload→load и не повтор полного группового цикла браузером. Физический ESC, quota и производительность не проверялись. Все пограничные/оплаченные групповые сценарии выше — регрессии Node, не браузерная приёмка UI.

## Оставшиеся вопросы и следующий шаг

**Далее только S3.25:** отдельный однослотовый `CampaignSaveManager`/репозиторий с внедряемым getItem/setItem, ключом `orion_campaign_v1`, read/write/quota/atomicity тестами. Он должен использовать готовый кодек, не дублировать схемы и не затрагивать ShipDesignManager. Никаких автоматических операций при входе и UI в этом шаге.

S3.26 отдельно подключит ручное сохранение/загрузку, подтверждения замены/перезаписи и защиту same-turn callbacks, затем настоящий save→reload→load→продолжение. Byte cap не обещает доступную browser quota или сохранение любого runtime-valid state; миграции/автосохранение/несколько слотов/межвкладочные конфликты/облако остаются вне первой реализации.
