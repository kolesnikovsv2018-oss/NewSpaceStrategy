# 03 — S3.5: чистая очередь производства колоний

- Дата: 2026-09-09
- Пункт плана: S3.5
- Статус: выполнено в границах модели; S3 целиком открыт

## Цель и границы

Добавить строгие команды заказа/отмены, оплату, независимый снимок проекта и прогресс производства по собственным ходам. Завершение должно выдавать ровно одну готовую запись без создания runtime-корабля. [План](../2026-09-07/plan.md), [контракты стратегии](../../docs/CAMPAIGN.md).

Производственный UI, размещение флотов, AI, стратегический бой, перелёты, содержание и save не входят. Начальные ресурсы/доход и формулы корабля не менялись. Существующая карта остаётся с прежними тремя действиями; новый endTurn умеет продвигать заказы, но создать их из UI пока нельзя.

## Изменения и решения

- Новый [production.ts](../../src/domain/production.ts): строгие схемы очереди/готовых записей, getProductionQuote, getProductionRefund, advanceProduction. Нет Phaser, времени/RNG, ID из часов или создания ShipRuntime.
- Новый [campaignEconomy.ts](../../src/domain/campaignEconomy.ts): общие ресурсы/Treasury/MAX_RESOURCE без циклической зависимости. Прежние импорты из [campaignSession.ts](../../src/domain/campaignSession.ts) сохраняются реэкспортом.
- [campaign.ts](../../src/domain/campaign.ts): экспорт существующего systemIdSchema для переиспользования, без изменения географических правил.
- CampaignSession обязательно содержит production; новые enqueueProduction/cancelProduction и общий endTurn. Дополнительный cross-check требует свою колонию для каждой ожидающей/готовой записи. Видимость production ограничена запрошенной стороной; глобальный счётчик не передаётся.
- [CampaignPanel](../../src/ui/CampaignPanel.ts): только тип разрешённых действий сужен до explore/colonize/endTurn, вместо автоматического расширения до любого SessionCommand.kind без payload. Производственные кнопки/отрисовка не добавлены.
- [campaignSession.test.ts](../../tests/campaignSession.test.ts): ожидаемые state/view дополнены production. Новый [production.test.ts](../../tests/production.test.ts) — 58 тестов.

### Правила и инварианты

| Область | Принятое решение |
| --- | --- |
| Проект | Независимый schemaVersion2 ShipDesign, общий validateDesign(flight); гражданский без оружия допустим, battle не ослабляется |
| Цена | ceil(canonical stats.cost/100) кредитов и ceil(stats.mass/10) минералов |
| Срок | max(1,ceil(credits/50)) собственных завершений хода |
| Оплата | Полностью при постановке до будущего дохода; нехватка любого ресурса отменяет всю команду |
| FIFO | До3 pending на колонию; один head каждой своей колонии получает1 шаг, без переноса остатка следующему |
| Отмена | Только pending своего ID/колонии, возврат floor(cost*remaining/total) по каждому ресурсу |
| Готовность | Удаление pending и добавление completed с тем же ID/проектом/колонией/стороной; не корабль/флот на карте |
| Лимиты | До100 pending+completed на сторону, место готовности резервируется при заказе; ID1..1e9 монотонный в партии, отменённые ID не переиспользуются |

Заказ содержит id/factionId/systemId/design/remainingTurns, completed — без remainingTurns. Производные стоимость/масса/срок не сохраняются и не принимаются из команды. Поздние правки верфи/каталога не меняют проект заказа. Изменение расчётных формул потребует будущего решения о версиях правил; runtime-схема сейчас не является форматом сохранения.

Strict проверяет схемы проектов, целые ограниченные ID/progress, уникальность ID между списками, порядок pending по выданным ID, счётчик, лимиты, отсутствие прогресса у ожидающих за head. Сессия проверяет владельца колонии; механики захвата пока нет. Quote/refund-запросы бросают ZodError при неверном входе; команды возвращают typed failure.

Общие проверки state/command/expectedTurn/active выполняются до нового действия. Для чужой/нейтральной/неизвестной цели одинаковый NOT_OWN_COLONY без раскрытия деталей. Остальные новые отказы: INVALID_DESIGN, INSUFFICIENT_RESOURCES, QUEUE_FULL, PRODUCTION_LIMIT, ORDER_NOT_FOUND, ORDER_ID_LIMIT; malformed структура — INVALID_COMMAND/INVALID_STATE.

`endTurn` сначала проверяет предел хода/доход, затем на отдельной копии начисляет доход, продвигает производство и передаёт ход. Переполнение отменяет также прогресс/готовность. Переполнение возврата сохраняет заказ и обе казны. MAX_TURN блокирует только endTurn, не все действия; предел ID блокирует новые заказы, но не отмену. Готовые записи не удаляются/не развёртываются; достижение100 блокирует новые заказы, не завершение уже зарезервированных.

Два корректных enqueue одного проекта в одном ходу — два отдельно оплаченных заказа. Это не request-id-дедупликация; будущий UI должен блокировать старые callbacks. Повтор cancel уже удалённого ID отвергается; stale endTurn не выдаёт готовность повторно. ProductionView не раскрывает чужие проекты и счётчик; собственные глобальные ID могут иметь пропуски, это не защита от анализа косвенных признаков multiplayer.

### Браузер и ограничения проверки

В текущем dev-браузере выполнен программный smoke настоящего Phaser: вход из меню в новую партию с пустой production, endTurn1→2 с кредитами blue110, подтверждённый reset к turn1 и пустым спискам. Одна панель/один canvas. Ручные шаги игры и запись localStorage не использовались. Карта оставлена с новой партией.

При первом обращении инструмент показал ранее накопленное пустое событие pageError периода HMR; текста для установления причины не было. После создания новой партии smoke прошёл без новых сообщений pageError. Это не доказательство бесшовной совместимости HMR: прежний state без production новой схемой отвергается. Сохранения кампании отсутствуют, миграция не реализована.

Производственные заказы/отмена/готовность проверены Node-тестами, не отсутствующим UI. Полный браузерный E2E, производительность/баланс и завершённая партия не проверялись. Формулы цены предварительные; расходы в обычном UI пока недоступны.
