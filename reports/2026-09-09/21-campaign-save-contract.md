# 21 — Контракт сохранения кампании

- Дата: 2026-09-09
- Пункт плана: S3.23
- Статус: выполнено **только проектирование**

## Цель и границы

Определить версионированный формат полной мирной партии, проверки данных и атомарную загрузку отдельно от библиотеки кораблей. [Контракт](../../docs/CAMPAIGN_SAVE.md) подготовлен; кодек, репозиторий, кнопки save/load и миграции **не реализованы**. Работающая игра остаётся на уровне S3.22. S3 и родительский пункт сохранения/AI/победы открыты.

## Изменения и решения

- Новый документ задаёт строгий конверт `format='orion-campaign'`, `schemaVersion=1`, `rulesVersion=1`, полную `session`. Без даты сохранения/часов, UUID, checksum и преждевременного журнала команд.
- Сохраняются обе стороны, казны, галактика, счётчики, FIFO/готовые записи, ships/fuel/transit и membership групп. Оплаченные ShipDesign v2 автономны от изменяемой библиотеки. Forecast/receipt/каталог/UI/тактический runtime не сохраняются.
- Отдельная версия правил нужна не только из-за формы JSON: текущие формулы заново вычисляют срок и возврат заказа. Первая реализация принимает только пару1/1, без угадывания версий и автоматического ремонта старых данных.
- Выбран предел5_000_000 **байт UTF-8**, проверяемый до JSON parse и до записи. Это самостоятельное ограничение, не обещание вместимости любого state или доступности квоты браузера.400 полных снимков при максимальных ship/production лимитах, Unicode/escaping и даты без `.max()` не позволяют обосновать фиксированный «типичный максимум».
- Зафиксированы API encode/decode, порядок ошибок конверта/версий/сессии, отдельный будущий ключ `orion_campaign_v1`, одно чтение/одна атомарная запись и отсутствие fallback/удаления данных при ошибке. Реализация хранилища отделена от чистого кодека.
- Будущий UI валидирует кандидат до подтверждения замены, не перечитывает его при подтверждении, очищает устаревшие панели/черновики/квитанцию только при успехе. Same-turn загрузка требует защиты lifetime/callbacks сверх `expectedTurn`. Сохранение не является командой фракции и разрешено при неактивном наблюдении.
- Load не меняет ход/доход/FIFO/fuel/содержание. Валидные состояния с дефицитом, терминальным ходом или будущей ошибкой cap не «исправляются». Новый бюджет рассчитывается из загруженной сессии.

Обновлены [README](../../README.md), [описание кампании](../../docs/CAMPAIGN.md), [границы содержания](../../docs/CAMPAIGN_UPKEEP.md) и [план](../2026-09-07/plan.md). Исходники, тесты, зависимости и lock-файл не менялись.

### Сверка с реализацией

Прочитаны актуальные campaignSession/production/campaignShips/campaignFleets/campaign/shipDesign, границы MainScene и ShipDesignManager. В контракте явно сохранены:

- `ship.id <= production.lastOrderId`, отсутствие пересечения с production; счётчики нельзя уменьшать до максимума оставшихся записей.
- Допустимость согласованного группового transit: systemId — источник, не требование стоять в колонии. Маршрут хранится только у участников.
- FIFO-порядок только orders; completed и ships не сортируются. Неголовной заказ не может иметь частичный прогресс.
- Строгий отказ от лишних полей; существующий trim имён признан нормализацией общей схемы, не обещано байтовое равенство сырого JSON.
- Schema не доказывает историческую достижимость и вечное домашнее владение. Если у загруженной стороны нет колонии, будущий UI выбирает домашний ID без выдачи ownership.

Дополнительное read-only ревью не выявило противоречия с инвариантами. Замечания об отсутствии runtime-кодека/нового выбора системы не являются дефектами проектного шага. Добавлять `.max()` к датам либо сортировать completed ради save не требуется: самостоятельный byte cap и сохранение порядка уже выбраны контрактом.
