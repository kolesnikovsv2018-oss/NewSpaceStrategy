# 26 — Профиль боёв и воспроизведения Conquest

- Дата: 2026-10-08
- Пункт плана: S4 — профиль целевых размеров флота
- Статус: профиль выполнен; оптимизация не потребовалась по измеренному сценарию

## Цель и границы

Проверить время `resolveConquestBattle` на репрезентативных размерах до установленного лимита 100 кораблей на сторону, включая полный 120-секундный timeout, и оценить стоимость replay максимального реального боя. Тактические формулы, сцены и правила кампании не менялись. Это не равностоимостный баланс и не общий benchmark FPS.

## Измерения

Использовался настоящий детерминированный `resolveConquestBattle`, один seed 12345, одинаковый fighter design, прогрев и пять замеров каждого случая:

| Размер / сценарий | Медиана | Разброс | Результат |
| --- | ---: | ---: | --- |
| 1v1 | 1.6 ms | 1.1–4.5 ms | обычное завершение |
| 4v4 | 2.9 ms | 2.1–7.5 ms | обычное завершение |
| 16v16 | 10.7 ms | 8.8–18.6 ms | обычное завершение |
| 50v50 | 32.0 ms | 25.1–37.2 ms | обычное завершение |
| 100v100 | 78.3 ms | 64.2–87.7 ms | обычное завершение, 182 уничтожено |
| 100v100, безоружный timeout | 459.8 ms | 427.1–489.5 ms | полный лимит2400 тактов, 121 кадр |

Node — v24.21.0. Timeout был намеренно безоружным worst-case для проверки полного лимита, не типичной боевой композицией.

В настоящем Phaser `ConquestScene` использованы 17 кадров, полученных реальным resolver для 100v100: 200 кораблей на кадр, максимум256 событий на кадр. На canvas 549×359 измерены300 ручных `game.step` calls: median0.6ms, p95 1.2ms, максимум21.3ms; `Graphics.clear` вызван300 раз. Сцена после диагностики возвращена в меню, canvas остался один, слот кампании не записывался.

Принудительный `game.step` включает работу scene/update/render path для этой browser page, но не является естественным RAF/FPS тестом, тестом разных устройств или полноценным нагрузочным профилем. Проверена одна компоновка/seed, не вся матрица hulls, formations и случайных длительных боёв.

## Решение и проверки

Измерения не подтвердили узкое место, требующее пространственного индекса, worker, пула или немедленного кэширования replay-графики. Поэтому оптимизация без данных не вносилась. Отдельный temporary profiling probe удалён после замера.

| Проверка | Результат |
| --- | --- |
| Временный warmed Vitest scale probe | 5 размеров; 5 повторов на размер |
| Максимальный timeout probe | 100v100; полный лимит2400 шагов; 5 повторов |
| Phaser browser replay diagnostic | 300 принудительных шагов на реальных resolver frames; без записи сохранения |
| `tests/conquestBattle.test.ts` | 2/2 прошли после удаления probe |

Полный suite/typecheck/build не повторялись: production source и постоянные тесты не менялись в этой profiling-задаче. Последние полные gates зафиксированы в отчёте S4.11c. Стандартные Node/Yarn shims в этой среде блокируются `snap-confine`; benchmark использовал установленный Node напрямую.

## Актуализация навыков

Обновлены `orion-project` и `orion-combat`: измеренный верхний размер Conquest, результаты и ограничения benchmark. `orion-ship-design` не менялся, так как схемы проектов/кораблей не затронуты.

## Оставшиеся вопросы и следующий шаг

В плане закрыта только часть профилирования; cadence UI и cache статической графики оставлены открытыми до подтверждения bottleneck на более широком целевом устройстве/нагрузке. Equal-cost fleet balance остаётся отдельной открытой родительской задачей; эти тесты не сравнивали разные составы по равной стоимости.
