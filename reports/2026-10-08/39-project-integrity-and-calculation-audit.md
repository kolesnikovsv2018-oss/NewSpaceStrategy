## A1. Cooldown округляется не так, как предполагает fixed-step расчёт

Источники: [DesignedShip.attack](../../src/entities/DesignedShip.ts#L97), [DesignedShip.update](../../src/entities/DesignedShip.ts#L132), [calculateConquestDesignScore](../../src/domain/conquestAi.ts#L100). Аналогичное вычитание присутствует в [legacy CombatShip](../../src/entities/CombatShip.ts#L223), но отдельное численное воспроизведение legacy в этом аудите не выполнялось.

Атака устанавливает `cooldown = 1 / fireRate`; обновление вычитает `deltaTime` с ограничением снизу нулём. Следующая атака недоступна при любом `cooldown > 0`.

Для `fireRate=2` период равен 0.5 с. После десяти обновлений по 0.05 с остаётся:

```text
cooldown = 6.938893903907228e-17
attack после 10 шагов: null
attack после дополнительного 11-го шага: выстрел, damage=25
```

Это не согласованное округление периода до ближайшего допустимого тактического шага: 0.5 с уже кратно шагу 0.05 с. Ожидание добавляется только из-за положительного остатка IEEE-754.

### Диагностика на 120 секундах

Создан допустимый проект corvette с обычным двигателем и одним beam: damage25, range900, fireRate2, accuracy0.8. Цель стоит в100 единицах, движения нет, генерации достаточно. RNG0.99 даёт промахи, чтобы цель не погибла и оставалась доступной весь интервал; считаются ненулевые результаты атаки, а не нанесённый урон.

За2400 настоящих `update(0.05)` с последующей атакой:

| Величина | Результат |
| --- | --- |
| Фактические попытки стрельбы | 219 |
| Количество, предполагаемое AI для этого периода и нулевого approach | 240 |
| Попыток меньше относительно240 | 8.75% |
| `219 × 25 × 0.8`, номинальный ожидаемый output по измеренному числу попыток | 4380 |
| `calculateConquestDesignScore(...).expectedDamage` | 4800 |

4380 — пересчёт номинальной метрики, **не фактически снятые HP**: диагностические атаки промахивались. Ошибка не позволяет автоматически заключить, насколько меняется вероятность победы любого флота. Сравнение выполнено на свободном flight/battle-валидном проекте, не на полном оплаченно достигнутом кампанийном сценарии.

Минимальное воспроизведение:

```ts
const attacker = new DesignedShip(createDesign('corvette', true), 'blue', 'battle',
  { random: () => 0.5 });
const target = new DesignedShip(createDesign('battleship', true), 'red');
target.position = { x: 100, y: 0 };
attacker.attack(target);
for (let i = 0; i < 10; i++) attacker.update(0.05);
console.log(attacker.getWeaponState()[0].cooldown);
console.log(attacker.attack(target)); // null; выстрел появляется ещё через0.05с
```

### Рекомендация и критерии исправления

- Устранить именно погрешность достижения границы cooldown: устойчивое представление времени/дедлайна либо обоснованная обработка близкого к нулю остатка. Не обнулять произвольный малый положительный период без анализа допустимых delta.
- Согласовать фактический переход готовности и `cooldownSteps` в AI score; постоянные тесты должны считать точное число попыток, а не только сравнивать два score между собой.
- Проверить периоды, кратные и некратные0.05с, минимум/максимум fireRate, несколько орудий, отсутствие энергии и исчерпание ammo.
- Перезапустить paired/balance регрессии и повторяемость seed. Исправление меняет время атак и может изменить исход прежних seed: отдельно решить совместимость старых сохранений/версии battle policy, не обещать прежний результат молча.

## A2. Error-путь асинхронного импорта не проверяет disposed

Источники: [ShipBuilderPanel.import](../../src/ui/ShipBuilderPanel.ts#L163), [showMessage и destroy](../../src/ui/ShipBuilderPanel.ts#L181), [perform](../../src/ui/ShipBuilderPanel.ts#L102), [shutdown верфи](../../src/scenes/ShipyardScene.ts#L57).

Последовательность:

1. В панели верфи выбран импорт; `file.text()` ещё не завершился.
2. Происходит выход из сцены; `panel.destroy()` ставит `disposed=true` и уничтожает её container.
3. Пользователь возвращается в ту же Phaser-сцену, поэтому `scene.sys.isActive()` снова возвращает true. Старая панель остаётся уничтоженной.
4. Чтение файла завершается **отказом**.
5. `catch` проверяет только активность сцены, вызывает `showMessage`, а тот без проверки disposed вызывает `render()` старой панели.

Успешное завершение чтения защищено: `perform` сразу отказывает при disposed. Ошибочный исход проверяет другую, более слабую границу.

Диагностика использовала настоящий ShipBuilderPanel с отложенным Promise чтения и fake Phaser container. После destroy и повторной активности отказ чтения действительно дошёл до `removeAll` уничтоженного container. Подмена container явно бросила `Render on destroyed container`, чтобы сделать ошибочный вызов наблюдаемым. Записей в StoragePort: **0**.

Это доказывает неверный lifecycle-вызов. **Конкретный браузерный exception/crash настоящего Phaser не проверялся**; сообщение исключения в диагностике принадлежит проверочному container, не движку.

Рекомендация: одинаково защищать success/error-пути идентичностью панели/операции и disposed; не показывать сообщения через уничтоженный UI. Добавить постоянные async-регрессии: resolve/reject после shutdown, после reentry, два перекрывающихся чтения. Критерий: старое завершение не рендерит старую панель, не меняет новый UI и не пишет хранилище.

## Рекомендации без объявления их новыми ошибками

1. **Унифицировать диагностику ошибок Conquest.** [ConquestSaveManager](../../src/utils/ConquestSaveManager.ts) объединяет ошибки чтения, формата и версии в одно сообщение, а command/AI могут свести различные причины к «Недопустимые данные»/«Не удалось выполнить AI-ход». За основу взять типизированные отказы [CampaignMatchSaveManager](../../src/utils/CampaignMatchSaveManager.ts). Показывать безопасный код/причину без сырых скрытых данных; сохранить атомарность и отсутствие fallback.
2. **Согласовать единицы лимита библиотеки.** [ShipDesignManager.decode](../../src/utils/ShipDesignManager.ts#L102) проверяет `json.length`, UI импорта — `file.size`, кампанийные кодеки — UTF-8 bytes. Это разные величины для Unicode. Выбрать единый документированный бюджет и тесты exact/+1; не менять существующую совместимость скрытно. Доказательство конкретного большого принятого Unicode-документа в этом аудите не проводилось.
3. **Усилить проверку исторических battle reports.** [battleReportSchema и superRefine](../../src/domain/conquest.ts#L19) проверяют часть ссылочных инвариантов, но не всю семантику отчёта: разумно проверять `timedOut⇒winner=null`, победителя среди участников/выживших, безопасные ограниченные ID и порядок отчётов. Не пытаться восстановить всю историю боя из текущего state и не выдавать исторические IDs за обязательные текущие ships.
4. **Явно согласовать ограничения полевого ремонта.** [repairShip](../../src/domain/conquest.ts#L179) применяет сумму repairRate за команду, а не за прошедший тактический интервал или ход. Команд можно выполнить несколько при наличии ресурсов. Это соответствует текущему описанию «за команду», а не новая ошибка. Если требуется лимит на ход, нужен отдельный контракт; не вводить его как незаметный bug fix. В UI/документах разделять nominal HP/с и стратегическое восстановление за действие.
5. **Не считать зелёные тесты доказательством полного E2E или производительности.** После A1 заново проверить ограниченную role matrix; после A2 — async lifecycle и настоящий браузер. Сборка по-прежнему предупреждает о JS-chunk>500kB: текущий main1578.08kB/gzip425.47kB. Разделение загрузки имеет смысл измерять отдельно, но это не доказательство низкого FPS и не повод менять стек.

### Ограничения

- Браузер, сервер и реальный file chooser в этой задаче не запускались.
- Исключение fake-container не доказывает конкретный тип сбоя настоящего Phaser.

- Не проводились новые проверки browser quota, нескольких вкладок, мобильной раскладки, естественного RAF/FPS и безопасности.
- Временные тесты удалены; постоянный регрессионный набор3232 пока **не покрывает** обе новые находки. Для воспроизведения сохранены алгоритм, параметры и точные результаты выше.
