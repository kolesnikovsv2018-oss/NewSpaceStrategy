# 04 — Население, рост и основание колоний

- Дата: 2026-10-24
- Пункт плана: [Н06](../../plans/tasks-2026-10-09/n06-population.md)
- Статус: выполнено в границах базовой демографии; ограничения браузерного viewport ниже

## Цель и границы

Продолжить разработку после сверки проекта и восстановления Node/Yarn:
подключить население, вместимость, точный рост, источник/цену колонистов,
сохранение жителей при захвате, own-view/UI/AI и актуальный save.
Не вводить труд, points-based science, технологии роста, миграцию,
runtime-среду или новую экономику Н07. Прежние изменения документов и
отдельной задачи восстановления среды сохранены; коммит/push не выполнялись.

## Изменения и решения

Демографические правила предварительно согласованы пользователем:

- Хранимая единица1000 жителей, UI в миллионах. Дом5000 единиц/5 млн.
- Базовая/абсолютная вместимость habitable10000/20000, barren0/0.
  `K=min(base,absolute)` без ещё не реализованных улучшений.
- Рост2% на успешный own-end, целое P и остаток числителя0..99.
  Нулевое/полное/переполненное население не растёт и не убывает.
- Основание переносит1000 единиц из ближайшей own колонии с≥2000 и стоит20/10.
  Расстояние по hop публичных линий, tie по ASCII ID источника.
- Ручное основание при отказе атомарно; автоматическое откладывается,
  даёт faction/system/code notice и не останавливает ход.
- Захват сохраняет100% населения и остатка, без цены/повторного роста.
  Демографические данные видит только владелец.

Запись существует у каждого пригодного мира, нейтрального с P=0 в том числе;
barren не получает запись. Отдельного demographic owner нет.
Snapshot привязан к ID дерева партии; Conquest требует `effects=[]`.
Consumer population-v1 исполняет базовую демографию, но не активирует
библиотечные примеры ship-growth/policy-reference.

Порядок: прежние session economy/FIFO/arrivals → own population growth →
research → mining → encounters/основание/захват → validation/outcome.
Поздний mining overflow откатывает также рост. Автоматическая колония начинает
с1000 без дополнительного прироста, ручная существует до следующего own-end.
Доход10/5 и прежний FIFO намеренно сохранены до Н07.

Найдены и исправлены связанные регрессии:

1. Новый темп платных оснований проявил AI-loop dust↔nexus при одинаковых
   ближайших маршрутах и исчезающем наблюдении. Диагностика настоящих команд
   показала повтор выбора; равные цели распределены через
   `(ship.id - 1) % nearest.length`, без скрытой памяти/доступа к противнику.
   Пользователь отдельно утвердил это поведение и измеренную смену темпа.
2. Runtime-импорт Н04 сделал JSON fixture достижимым из main. Static graph test
   предполагал только TS; обход теперь проверяет JSON leaves, сохраняя
   прежние утверждения о графе, и проверяет достижимость default fixture.
3. Первоначальный подсчёт population через полные views в каждом baseline tick
   вызвал timeout256-world теста; конечные totals считаются напрямую один раз
   после прогона. Скрытые данные не передаются planner.

### Настоящий браузер

Локальный Vite dev-сервер с HTTP200, настоящий Phaser/домен/локальный storage.
Новая generated local6, без инъекции игровых state/казны/кораблей.
Мышью выполнен первый own-end; повторяющаяся подготовка — события UI-кнопок
и обычная граница scene.command, не полный mouse E2E.
Отображение продвигалось принудительными `game.step`, не естественный RAF benchmark.

1. Дом5/10 млн → blue-end:5,1 млн, red не развивался.
2. Обе стороны реально накопили деньги, оплатили fighter, прошли FIFO и deploy.
   На turn35 по одному кораблю, казны64/125, дома `{7001,6}`.
3. Перелёт blue в world-002, red в world-005 → оплаченные автоматические основания.
   На turn37 дома `{6141,8}`, новые миры `{1000,0}`, казны каждой стороны53/120:
   рост источника, перенос и цена совпали с независимой арифметикой.
4. UI save7/rules4 → реальный reload → явный load:
   весь state и следующий command oracle совпали. На turn38 blue колония1020,
   red1000, без чужого прироста при загрузке.
5. Оплаченным blue кораблём захвачена оставленная red столица:
   `{6263,90}` сохранилось без атакующего роста. Чужое P до захвата отсутствовало
   в blue view, после захвата появилось. Это захват без защитника;
   настоящий бой/захват отдельно проверен domain-тестом, не выдан за браузерный бой.
6. Второй save/reload/load после захвата вновь совпал целиком и по следующей
   команде; red-end до turn41 не изменил теперь blue население.

Host сохранил фактический viewport853×480; изменение viewport не дало
нативных1280×720/390×844. Для новых подписей проверены **логические** размеры
Phaser/camera1280×720 и390×844: P/K label305×16, x740/y261 и x12/y402,
без выхода за ширину или нижнюю границу зарезервированной области.
Это не повтор CSS-приёмки Н02, не физическое touch/ESC/quota/FPS.

Исходные значения только campaign/latest-map слотов восстановлены и сравнены;
