# Обязательный контракт исполнения каждого задания

Это часть каждого промпта в [комплекте](README.md), а также [задания генератора](../galaxy-generator-prompt-2026-10-09.md). Следуй этому контракту вместе с выбранным заданием; реализуй только его границы.

## 1. Вход и проверка предпосылок

1. Прочитай [правила репозитория](../../.github/copilot-instructions.md), [orion-project](../../.github/skills/orion-project/SKILL.md), [основной план](../plan-2026-10-09.md) и выбранное задание. Для кораблей прочитай [orion-ship-design](../../.github/skills/orion-ship-design/SKILL.md), для тактики — [orion-combat](../../.github/skills/orion-combat/SKILL.md).
2. Проверь git status. Не откатывай чужие/прежние изменения; в затронутых файлах интегрируй их. При конфликтующих неожиданных изменениях остановись и уточни.
3. Проверь завершённость прямых предпосылок по фактическому коду, тестам и отчётам, а не по существованию Markdown-файла. Если предпосылка не реализована — сообщи блокировку; не реализуй её молча внутри выбранного этапа.
4. Прочитай текущие реализации и связанные тесты только затрагиваемой области. Указанные в заданиях пути — опоры, не требование сохранить архитектуру любой ценой. Новые имена модулей и версии согласуй с уже принятыми предыдущими этапами.
5. До изменения игровых правил перечисли нерешённые продуктовые решения: формулы, пределы, цены, захват/отмена, сроки и новая схема данных. Предложи конкретный вариант и запроси подтверждение спорных вариантов. Не подменяй отсутствие решения скрытым default. Числа в тестовых примерах — иллюстрации расчёта, не согласованный баланс.

### Проверенная отправная точка на 2026-10-10

- Основной вход «Новая кампания» → ConquestScene уже использует общий CLI/browser генератор. Г01–Г04/Н05 реализованы: 6–256 миров в браузере, две стороны; CLI/формат поддерживают 2–8 участников, но игровая граница пока отвергает P>2. «Мирная песочница» и испытания находятся в демонстрациях; свободная верфь пока в основном меню, перенос относится к Н05а.
- [galaxyMap](../../src/domain/galaxyMap.ts): map schema/rules 1/1, `galaxy-generator-v1`, `balanced-start-v1`; линии — пары ID **без длины**. Координаты задают размещение/выбор ближайших целей, не стоимость или время перелёта. Бак 3, расход 1 за линию, arrival за own endTurn.
- [ConquestSaveManager](../../src/utils/ConquestSaveManager.ts): актуальный военный save 5/3 с tree2 и явным battlePolicy. `session.galaxy.map` — автономный начальный снимок; ownership/knowledge меняются в `systems`. Последняя карта хранится отдельно через [GalaxyMapRepository](../../src/utils/GalaxyMapRepository.ts); load кампании не читает этот слот и не генерирует карту.
- Население, труд, point-based science, изменяемая среда, объём оборудования, refit, дипломатия и новые победы не реализованы. Н05а тоже пока только задание; текущий production-каталог читает пресеты/общую библиотеку и кандидаты AI. Н01–Н04 не считать принятыми по наличию документов.
- Текущие Conquest-команды/репозитории возвращают преимущественно `ok/message`, а не общий `code/message`; machine-readable коды — требование новых границ, не уже существующая гарантия. Исторические мирные и библиотечные readers не переписывать под предлогом актуальной версии, если их формат не затрагивается этапом.

### Самодостаточность и порядок

Прямые предпосылки каждого задания и их транзитивное замыкание — единственные обязательные предыдущие Н-этапы. Номер или положение в таблице не означает зависимости от всех ранних строк. Нельзя требовать будущий handler, UI, fixture-runner или механизм из независимой непринятой ветви; если без него критерий невыполним, сначала исправь зависимости во всех трёх местах: задание, README и основной план.

Для каждого этапа зафиксируй «что уже есть / что вводит этот этап / какие действующие правила сохраняются». Проектные targets Н04 не требуют будущих исполнителей; новые поля и минимальные работающие потребители вводятся вместе в своём игровом этапе. Н03-runner расширяй, только если Н03 уже принят; иначе добавь самостоятельные регрессии текущего этапа, не делая Н03 скрытой предпосылкой. Н20 явно требует Н02 и Н03.

Все игровые этапы расширяют единственный Conquest, а не создают параллельный «новый режим» с запасной фиксированной картой. Сгенерированный старт, общая CLI/browser модель, обязательная запись карты до старта, own-view, автономный save и следующий ход после load остаются обязательными. Ручные контрольные карты — данные той же актуальной схемы для тестов/диагностики, не уже существующий пользовательский импорт или альтернативный reader. Изменяя карту/профиль/движение, обновляй генератор/checker/CLI/browser и проверки стартов каждого участника в той же поставке.

## 2. Код и границы

- Сохраняй TypeScript strict, существующий Phaser/Vite/Vitest/Zod и Yarn Classic с единственным yarn.lock. Не добавляй пакеты без необходимости; устанавливай после изменения manifest или подтверждённого отсутствия зависимости.
- Чистый домен не импортирует Phaser, DOM, localStorage, файловую систему, часы или глобальный RNG. IO, UI и CLI — адаптеры. Для воспроизводимости используй [seededRandom](../../src/domain/seededRandom.ts), стабильные ID и явную версию политики.
- Ищи существующие helpers/формулы прежде добавления новых. Разделяй Definition/Design/Stats/State/View. Не сохраняй производные прогнозы или UI-страницы как второе игровое состояние.
- Внешние границы принимают unknown и проверяют строгую runtime-схему без coercion/trim сверх принятого контракта. Числа конечные, диапазоны и межобъектные ссылки проверены. Не использовать `as any` или цепочки принудительных casts для обхода схем.
- Команда: полное состояние → строгий payload → captured revision/expectedTurn → активная сторона/контроллер → завершение/доменные условия → независимый кандидат → полная итоговая проверка → одна публикация. Сохраняй приоритет действующих ошибок там, где он является контрактом.
- Отказ — типизированный code/message без частичного состояния; UI показывает ошибку, CLI возвращает ненулевой exit code. Не молчать, не возвращать успех с fallback, не подставлять нули вместо ошибочного прогноза, не исправлять повреждённый save автоматически.
- Внутри хода прогноз и фактическое начисление используют один расчёт по исходному снимку. Экономический бонус завершённого открытия действует со следующего собственного хода; бой использует закреплённое оснащение.
- AI получает только detached own-view, ограниченный бюджет кандидатов/команд и детерминированные tie-breaks. Весь пакет атомарен, без retry по скрытому состоянию. После load AI не запускается автоматически.
- UI не вычисляет игровую формулу и не изменяет state. Captured payload/identity/generation/disposed защищают старые и асинхронные callbacks; pending блокирует фон; shutdown освобождает панели/обработчики/таймеры.
- Проверяй результаты установки оборудования и операций IO. Комментарии — только для неочевидной логики; изменения точные, без исправления постороннего долга.

## 3. Полнота и актуальная версия данных

Игровой этап включает домен, командную границу, own-view, прогноз/квитанцию, доступный UI, минимальную законную policy AI, save/read и непосредственно связанные документы. Политики других ещё не реализованных систем сохраняются в последней принятой версии; новый режим должен запускаться и играться сейчас.

Чтение, импорт, получение из внешнего источника и запись выполняются только в одной актуальной новой версии соответствующего формата. Schema и rules version фиксируй явно и проверяй согласованно; не угадывай будущие номера. При изменении формата обнови все его producers/consumers, примеры и тестовые fixtures в том же этапе. Версия, отличная от принятой текущей, получает явный типизированный отказ без изменения state или файлов. Не добавляй миграции, несколько version-specific readers, адаптеры прежних форматов или fallback к другому набору данных; не удаляй пользовательские файлы/слоты автоматически.

Оплаченный проект, корабль, карта, дерево и таблицы правил автономны от библиотеки и внешнего источника. Завершённая партия readonly для игровых действий; просмотр/save/load/new/menu/takeover сохраняются по контракту.

После [Н05а](n05a-campaign-shipyard.md) редактор и каталог проектов принадлежат стороне текущей кампании и сохраняются вместе с ней. Сохранение чертежа не создаёт корабль: только оплаченный заказ в своей колонии проходит production/FIFO/deploy. Свободная верфь остаётся в демонстрациях, не источником автоматических grants или внешней зависимости кампании. Последующие этапы расширяют этот путь, а не добавляют параллельные редакторы.

Публикуемость результата не требует будущих стадий, временных TODO-реализаций или отключения тестов. Для самостоятельного контрактного/инструментального этапа явно укажи, что он ещё не является новой игровой механикой.

## 4. Верификация и закрытие

1. Добавь регрессии точных требований: корректность числа/формы результата, exact/+1 границы, ошибка без мутации, frozen input, detached output, приватность, deterministic replay, сохранение после смены источников.
2. Запусти минимальный набор существующего runner, покрывающий изменение: `yarn test <пути тестов>`. Затем `yarn typecheck` и `yarn build`. Полный `yarn test` нужен при общей схеме/ходе/кодеке/формулах или перед интеграционной приёмкой; не дублируй без причины одинаковые прогоны.
3. Для UI проверь настоящий браузер на 1280×720 и 390×844: pointer/keyboard, длинные имена, ошибки, save/reload/load, cancel и reentry. Заглушки Phaser и временные StoragePort — отдельные проверки, не browser E2E. Реальную quota/FPS не объявляй измеренной без такого измерения.
4. Для документационного этапа тесты приложения не нужны, если runtime не менялся; проверь ссылки, согласованность контрактов и полноту матрицы приёмки.
5. Выполни [актуализацию навыков](../../.github/skills/orion-skill-maintenance/SKILL.md), затем [отчёт](../../.github/skills/orion-task-report/SKILL.md) в reports по фактической дате, новым номером. Обнови статусы только в проверенных границах.
6. Финал: результат, изменённые поверхности, реальные проверки/предупреждения, ограничения и следующий допустимый этап. Не коммить и не пушь без прямого запроса; при отдельном запросе коммита используй принятый Co-authored-by trailer.
