**Дата:** 2026-10-09. **Статус:** задание на разработку, генератор не реализован.  
**Обязательная часть промпта:** [контракт исполнения](tasks-2026-10-09/00-execution-contract.md).  
**Связь:** [основной план](plan-2026-10-09.md), Н05/Н14/Н17 и [указатель заданий](tasks-2026-10-09/README.md).
**Отчёт о подготовке:** [02 — Генератор и этапные промпты](../reports/2026-10-09/02-generator-and-stage-prompts.md).

**Данные:** генерация, кодирование, чтение и импорт используют только актуальную новую версию карты/профиля/правил. При смене версии обновляются все потребители и fixtures; иной формат получает явный отказ без преобразования или fallback.

## 1. Задача для исполнителя

Разработай детерминированный генератор карты Orion. На вход обязательно передаётся количество миров. Готовая карта содержит ровно это число миров **включая стартовые**, имеет связную топологию и честные стартовые условия. Результат каждого успешного вызова пользовательского CLI обязательно записывается в отдельный JSON-файл.

Пользователь подтвердил:

- У каждого участника, включая оппонентов, ближайшие миры достижимы **из его собственного стартового мира** с начальными возможностями его колонизационных кораблей.
- Основное сохранение — **JSON-файл на диске через CLI**. Браузерная библиотека, export/download и localStorage не заменяют это требование.

Генератор не обязан сразу вводить население, научную экономику или многосторонний бой. Г01–Г03 — самостоятельный инструмент; Г04 подключает уже проверенную карту к действующим границам нового режима.

## 2. Подтверждённые факты и решения перед кодом

Текущая [campaign.ts](../src/domain/campaign.ts) жёстко задаёт шесть ID и две стороны. Текущие [campaignShips.ts](../src/domain/campaignShips.ts) и Conquest используют соседние линии, fuel 3, расход 1, прибытие за свой ход; расстояние UI не определяет доступность. Отдельной утверждённой модели «колонизационного двигателя» пока нет. [getFlightEstimate](../src/domain/flightEstimate.ts) оценивает тактическую энергию и не годится для стратегической достижимости.

До реализации утверди:

1. В первой игровой версии один мир = одна система с одной планетой; worldCount считает эти записи. Несколько планет в системе — будущая версия.
2. Первая CLI-конфигурация — две стороны с равными начальными возможностями; больше участников подключаются к кампании только после Н17.
3. Предлагаемый профиль `balanced-start-v1`: минимум **два** ближайших нейтральных мира на участника, пригодных для начальной колонизации; это параметр профиля `k`, а не случайное пожелание алгоритму.
4. При P участниках и k гарантированных мирах требуется `worldCount >= P × (k + 1)`. Для P=2/k=2 минимум 6. Если пользователь запросил меньше — явный отказ, а не увеличение числа миров или тихое уменьшение k. Другой профиль k=1 можно утвердить отдельно.
5. Максимальное число миров, область размещения, минимальное разделение, доли типов, JSON byte cap и лимит попыток/операций задаются профилем с документированными пределами. Не выдавай непроверенный размер за поддерживаемый.

Новый формат/профиль проектируй так, чтобы Н05 мог его использовать. Если Н05 уже выполнен, расширь его общую модель, а не создай второй несовместимый формат. Если нет — выдели самостоятельную модель данных без импорта фиксированного campaign enum.

## 3. Вход, результат и ошибки

Предлагаемая чистая граница `generateGalaxy(unknown)`:

```text
request = {
  worldCount, seed, generatorVersion, profile
}
result = {ok:true, map}
      | {ok:false, code, message}
```

Имена уточни по repository patterns; strict request не принимает лишние поля. worldCount — конечный safe integer в пределах профиля; seed — целый 1..0xffffffff. Профиль содержит число/ID участников, начальные возможности, k и ограничения топологии/среды. CLI позволяет передать только worldCount при явно документированном профиле по умолчанию; seed создаётся **один раз на IO-границе** и обязательно попадает в вывод/JSON. Чистый домен всегда получает явный seed.

Отдельная граница `generateAndSave`/CLI отвечает за кодирование и запись. Чистая генерация для тестов не выполняет IO; пользовательский успех выдаётся только после успешной записи файла.

Предусмотри различимые ошибки: неверный запрос, невозможные стартовые ограничения, неизвестный профиль/версия, исчерпанный конечный бюджет, недопустимая карта, слишком большой JSON, отказ чтения/записи, существующий выходной файл. Ошибка не возвращает fallback-карту и не объявляет сохранение успешным.

## 4. Точный критерий достижимости

Для каждого home участника a:

- Найди k ближайших **нейтральных** миров по физическим координатам карты; ties — стабильный ASCII ID. Экранные координаты/масштаб canvas не участвуют. Стартовые миры исключаются из списка кандидатов, но не из worldCount.
- Каждый такой мир имеет разрешённую начальной технологией среду, свободен и связан с home прямой разрешённой линией.
- Вызови общую чистую функцию доступности маршрута с **реальным начальным стратегическим профилем** этого участника. Она учитывает правила перехода, запас топлива, начальные открытия, а в метрической версии — длину перехода и расход.
- Резервируемые стартовые миры разных участников не пересекаются. Достижение не требует исследования, заправки в несуществующей колонии, пересечения вражеского дома или захвата.
- Достижимость означает прибытие и возможность последующей законной колонизации, а не бесплатную разведку из debug-состояния. Мир может сначала требовать разведки; начальная разведка/сканирование не должны делать маршрут недоступным навсегда.

**До Н14:** поддержать явно названную `initial-lanes-v1`: одна прямая линия, начальный бак/расход текущего стратегического правила, допустимая среда. Не выводить метры или скорость из тактического двигателя. Физическая близость задаёт порядок соседей, но не стоимость полёта в этой версии.

**После Н14:** заменить актуальную политику на `initial-distance-v1` с общим runtime-калькулятором пути, начальным snapshot двигателя/бака и distances. Обновить формат, генератор, checker, импорт и fixtures согласованно; новые карты проверять тем же predicate, который реально разрешает отправку в кампании. Для игры по обновлённым правилам генерировать JSON заново.

Не писать отдельную более мягкую проверку только для генератора. Отдельные unit oracle проверяют арифметику доступности, интеграционные тесты — настоящие команды отправки/прибытия/колонизации.

## 5. Построение карты

1. Проверить возможность всех ограничений до RNG/IO.
2. Использовать [seededRandom](../src/domain/seededRandom.ts) с отдельными потоками placement/topology/world-types; никакого Date.now/Math.random в генераторе. ID — стабильные `world-...`, не UUID по времени.
3. Разместить стартовые области с заранее зарезервированными k мирами. Сначала конструктивно обеспечить гарантии старта, затем добавлять оставшиеся миры.
4. Разместить дома достаточно раздельно; не допустить, чтобы случайный мир оказался ближе зарезервированных, но был непригоден/недостижим. Финальный nearest-k считается заново по всем нейтральным мирам.
5. Стартовые пакеты сделать равными по числу достижимых пригодных миров и начальной вместимости/ресурсам согласно профилю. Геометрическое разнообразие не объявлять доказанным балансом.
6. Создать обязательные линии к ближайшим мирам и связующий остов всей карты, затем дополнительные линии с ограничением степени. Нет петель, дубликатов обратных линий и ссылок на отсутствующие ID.
7. Глобальная связность не означает, что весь космос доступен начальному флоту: дальние области могут требовать новых технологий, но старт не блокируется.
8. Применить типы/характеристики миров по сохранённой таблице профиля, не подменяя гарантированные стартовые цели непригодными.
9. Провести полную независимую валидацию, включая exact count, nearest-k, достижимость, связность и стартовую симметрию возможностей.
10. Ограничить попытки и число операций. Исчерпание возвращает ошибку, не бесконечный retry и не подмену seed.

Порядок обхода, округление физической дистанции, равные расстояния и порядок массивов должны быть каноничны. Один input/seed/версия дают одинаковые JSON bytes; не включать в канонический файл дату создания или случайное имя пути.

## 6. JSON и файловый адаптер

Предлагаемый envelope:

```text
{
  format: "orion-galaxy-map",
  schemaVersion,
  generator: {version, seed, worldCount, profileSnapshot},
  map: {
    worldTypes,
    worlds: [{id, name, physicalPosition, worldTypeId, ...}],
    lanes: [{fromId, toId, distance}],
    starts: [{factionId, homeWorldId, initialCapabilities}],
    initialTravelPolicy
  }
}
```

Это формат для согласования, не готовая схема и не привязка к будущим номерам версий. Каждое поле должно иметь диапазон/назначение. В JSON хранится **полная карта**, а не только seed, ссылка на каталог или state партии. Владение после начала игры, исследования, UI-флаги и receipt сюда не входят.

Кодек: UTF-8 byte cap до parse, strict version/shape, уникальные ID, известные ссылки/типы, конечные координаты, положительные distances, один дом на участника, отсутствие повторных линий, полный генерационный инвариант. Не доверять заверению `validated:true` внутри файла. Encode тоже проверяет весь map.

CLI-интерфейс для реализации:

```text
yarn generate:galaxy --world-count 40 --seed 12345 --output maps/galaxy-40-12345.json
```

Команда пока не существует; добавь её в package.json на Г03. Если путь не задан, создавай отдельный файл в документированном каталоге generated maps. Не перезаписывай существующий файл автоматически; для повторов выбери свободное имя на IO-границе либо верни понятный конфликт. Каталог и расширение `.json` проверяются, произвольный shell-code не строится.

Используй поддерживаемый существующим toolchain способ запуска TS-инструмента без второго lockfile. Node native TypeScript не гарантирует поддержку текущих extensionless imports — проверь выбранный runner/сборку реально. Новые зависимости вводи только при доказанной необходимости.

Файловый порт позволяет тестировать отказ записи. Запись полного файла: безопасный временный файл в том же каталоге → flush/close по принятой гарантии → атомарная публикация без перезаписи чужого файла → успех. Не использовать небезопасное read-exists-then-overwrite; учесть конкурентное создание destination. Временные файлы очищаются точечно при отказе. Не обещать устойчивость к отключению питания, если проверена только атомарная видимость.

JSON round-trip сохраняет всю карту; CLI печатает seed/версию/число миров и фактический путь только после завершения IO. При запрете записи — stderr и ненулевой exit, нет успешной «сгенерированной и сохранённой» карты.

## 7. Самостоятельные этапы разработки

### Г01 — карта, профиль и проверка достижимости

**Предпосылки:** нет; при выполненном Н05 используй его модель.  
Реализуй общий чистый format/schema/codec, профиль двух сторон и `initial-lanes-v1`, checker nearest-k/стартовых возможностей. Добавь валидный ручной fixture и повреждённые случаи. Результат — документированный проверяемый API, а не новый игровой режим. Не подключай будущие метрические характеристики.

**Приёмка:** strict reject всех неверных ID/ссылок/count/версий; exact/+1 размера; detached round-trip; тест с ближайшим непригодным или недостижимым миром действительно отклонён.

### Г02 — детерминированный генератор

**Предпосылки:** Г01.  
Реализуй чистый генератор с конструктивными стартовыми пакетами, связностью, заданным worldCount и конечным бюджетом. Не делать IO и не менять текущую кампанию.

**Приёмка:** минимум допустимого N и N+1, верхняя принятая граница, 100 фиксированных seed для каждого из малого/среднего/максимального профилей; каждый успех проверен полным checker, неверный input rejected. Каждый заведомо поддерживаемый профиль обязан успешно сгенерироваться на этой контрольной матрице; ошибку не считать успешным покрытием. Повтор seed даёт равные bytes, смена порядка сторон не создаёт привилегию первого ID.

### Г03 — CLI и обязательное сохранение

**Предпосылки:** Г02.  
Добавь yarn-команду, строгие arguments, файловый адаптер и docs использования. Успех — только валидный реальный JSON-файл, открываемый кодеком; никаких browser-зависимостей.

**Приёмка:** настоящие subprocess-прогоны с world-count/seed/output и только world-count; новый процесс читает тот же файл; повтор не портит его; write failure/конкурентный конфликт/invalid input дают ненулевой exit и не оставляют опубликованный partial JSON. Все тестовые файлы создавай в отдельном temp-каталоге и убирай только их.

### Г04 — карта в кампании и версионированные расширения

**Предпосылки:** Г03 и Н05; для метрической политики дополнительно Н14; для P>2 дополнительно Н17.  
Добавь выбор/import готового JSON актуального формата при старте новой кампании, используя полную проверенную карту как snapshot. Import не заменяет уже начатую игру без подтверждения, поздние file callbacks инертны. Ручные карты и сценарии также используют актуальный формат. UI не запускает Node filesystem.

**Приёмка:** сгенерировать CLI → импортировать → каждой стороной настоящими командами разведать/долететь/колонизировать одну гарантированную цель → save/reload/load → тот же следующий результат. Ошибки map/read/rules сохраняют текущую партию. Для metric-v1 тест отдельно меняет начальную дальность и доказывает, что checker/команда согласованы.

## 8. Не входит и завершение

Не вводить одновременно сетевую игру, БД, редактор карт, бесконечную галактику, сложную физику орбит или новую модель боя. Большие карты не объявлять быстрыми без измерений.

По каждому Г-этапу выполнить общий контракт проверок/закрытия. В отчёте указать подтверждённые диапазоны N, матрицу seed, политику достижимости и реальные проверки файлов отдельно от browser. Публикуемость — отсутствие зависимости от следующих Г-этапов; реальный push только по запросу.
